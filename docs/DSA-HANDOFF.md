## 1. What this is

`src/content/docs/DSA with Python/` is a 129-page interview-prep course being
brought to a uniform **13-section page spine** and backed by a generated problem
database. Target: a single stop for big-tech interview prep, covering every
pattern the major companies ask, with interactive visualizations, real LeetCode
ladders mapped to the public study sheets, and progress tracking.

The design doc lives in this conversation's history; the operational state lives
in the repo and in `docs/dsa-coverage.md`, which is regenerated by the audit.

**Constraints from the repo owner: never run `npm run build`, and never start
`npm run dev` either.** ~800 content pages, so a build exceeds 10 minutes; the owner
runs the dev server themselves when they want to look at the site. A backgrounded
`npm run dev` was killed with "never build the project, only add content and other
things". Verify with:

- `npx tsc --noEmit --strict --skipLibCheck --target es2020 --module esnext
  --moduleResolution bundler --jsx react-jsx <file>` on any `.ts`/`.tsx` you touch
  (the flags are needed because a bare `tsc <file>` ignores the project tsconfig).
- the `dsa:*` scripts (`merge` → `validate` → `audit`).
- **a Python oracle for every number a page states.** Brute-force the property over
  small inputs and compare, and `exec` each exercise's `solution={...}` block to
  confirm its printed output matches the `# expect …` comment. This has caught real
  errors — a dry-run table for 0-1 BFS that had the improvement order wrong, and a
  Multi-source BFS wave order that looked right and was not.
- **`npm run dsa:lint`** (`scripts/lint-dsa-mdx.mjs`) — the only check in this repo that
  catches build-time MDX errors without building. Two of them: an unescaped backtick
  inside a JSX template-literal attribute, and a component used but never imported. It
  found `<Quiz>` unimported on `Phase-05/Cyclic Sort.mdx` — a page the audit had scored
  as **complete**. Run it after every page. It is now part of `npm run dsa`.

**8 sketches on 6 pages**, every number measured on this machine before the sketch was drawn:

| Page | Measured, then drawn |
| --- | --- |
| Asyncio `Coroutines and await` | calling an `async def` runs nothing — body starts only on `await`; and the loop only changes hands at a visible `await` |
| Asyncio `Tasks (create_task) and gather` | sequential `1.091 s` against gathered `0.109 s`, **10.0x**, same list both ways; plus the create_task ordering below |
| Sync `Locks (Lock vs RLock)` | second `acquire()` from the same thread returns **False** on a `Lock`, **True** on an `RLock` |
| Sync `Semaphores` | `Semaphore(2)`: peak in-flight exactly **2**, `0.31 s` against a `0.30 s` ideal; `Semaphore(3)`: peak 3, `0.21 s` |
| Sync `Deadlocks` | opposite lock order: **0 of 2** threads completed; same order: **2 of 2** |
| MP `Process Pool` | sequential `5.48 s`, 4 threads `5.94 s` (**0.92x — slower**), `Pool(4)` `2.80 s` (**1.96x, not 4x**) |

**Two measurements worth keeping.** First, `ThreadPoolExecutor` on CPU-bound Python is
*slower than sequential* — 0.92x, not merely "no faster". Second, `Pool(4)` gave **1.96x, not
4x**, on 8 cores: spawn re-imports the module and every argument and result is pickled. Both
are stated on the page rather than rounded up to the tidy claim.

**A teaching point the page was missing**, found by measuring rather than reading:
`asyncio.create_task` **schedules but does not start**. With two tasks created and a `print`
between them, the print runs *first*; the observed order was
`after create_task, start 1, start 2, end 1, end 2`. Added to the page as a `:::caution` with
the real output, since the practical consequence — an un-awaited task can be garbage-collected
mid-flight — is why `TaskGroup` exists.

**Fourth batch — language mechanics.** Three more sketches, on the three pages where the
measured answer contradicts the folklore:

| Page | Measured, then drawn |
| --- | --- |
| `Python Strings / Concatenation` | building 100k chars: `join` **3.52 ms**, `s += "x"` **8.90 ms**, and `s +=` **with a second reference held 114.38 ms** — 13x worse |
| `Python Operator / Identity Operators` | the small-int cache is exactly `-5 .. 256`: `int('256') is int('256')` is True, `257` is False; string literals share objects, constant folding covers `"a" + "b"`, a runtime `join` does not |
| `Python Errors and Exceptions` | key PRESENT: try/except **29.4 ns** beats `if k in d` **46.0 ns**; key MISSING: try/except **129.7 ns** loses to **18.0 ns** |

**The `+=` folklore is wrong and the page now says so.** "String concatenation in a loop is
quadratic" is not what CPython does — it resizes in place, so the loop is merely slower than
`join`, not quadratic. The cliff is the **aliasing** case: the in-place path needs a refcount of
exactly 1, and any second reference (a debug list, a previous-value variable, a closure capture)
turns every `+=` into a full copy. Added to the page as a `:::note` with all three numbers,
because "just use join" without the mechanism is advice people correctly ignore.

**A test of mine that lied, caught before it shipped.** The first identity check used
`"".join(["hello world!"])` to build a runtime string — but a **one-element join returns the
same object**, so it reported `is` as True and would have taught the opposite of the truth.
Rebuilt with a two-element join, which correctly gives `is` False and `==` True. A
demonstration that agrees with your expectation is exactly the one to re-check.

**Fifth batch — stdlib and object model.** Four sketches, four pages:

| Page | Measured, then drawn |
| --- | --- |
| `Standard Library / Itertools and Functools` | `fib(30)`: plain **733.669 ms** vs `@lru_cache` **0.02853 ms** = **25,713x**; plain makes **2,692,537 calls** to evaluate 31 distinct values |
| `Standard Library / Collections` | 50k front-inserts: `list.insert(0)` **2164.31 ms** vs `deque.appendleft` **11.94 ms** = **181x**; `Counter` **1.810 ms** beats a manual tally **5.436 ms** |
| `Modern Python / Dataclasses` | per instance: plain class **344 B** (48 object + 296 `__dict__`), `__slots__` **48 B** — **86% saved**; a `@dataclass` is **still 344 B** unless you pass `slots=True` |
| `OOPS / Dynamic Binding and Typing` | `D(B, C)` MRO is `D, B, C, A, object`; `class X(A, B)` raises `TypeError`; and `super()` follows the MRO, so with `L4(L2, L3)` the result is `['L4','L2','L3','L1']` |

**The `super()` result is the one worth the sketch.** `L2`'s only base is `L1`, yet `L2`'s
`super()` lands on **`L3`** — a class `L2` knows nothing about. That is the MRO of the *object*,
not the class tree, and it is why cooperative multiple inheritance requires every class in the
chain to call `super()`.

**Also worth stating: a `@dataclass` saves no memory.** It is an ordinary class with a
`__dict__`, so it measured identically to a hand-written one (344 B). Only `slots=True`
(3.10+) or an explicit `__slots__` changes that. Easy to assume otherwise.

Two of the three call counts in the `lru_cache` sketch were derived from `2*fib(n+1)-1` rather
than measured; both were then confirmed empirically (21,891 and 242,785) before shipping.

**Two accuracy bugs caught before anything was written:**

1. The first resolver matched any `obj.method()` whose name existed on any class in the file.

2. Truncation originally kept the **highest-degree** edges. Since the entry point calls almost

   It now keeps the edges from the *rarest* callers.

Edges were spot-checked against the sources by hand before the write: `self.load_data()` in

**Two myths corrected rather than repeated.**

- **Tuples are not faster to read.** Indexing measured **13.1 ns against a list's 12.7** — a
  tie, and if anything the tuple is a hair slower. They are ~5.5x faster to *build*, because a
  literal is stored as a constant. The sketch says to choose a tuple for hashability and
  meaning, not for speed.
- **`readlines()` is the worst of both.** It is slower than iterating *and* holds the whole
  list. A plain `for line in f:` gives the same lines for free.

**The two thread results now bracket each other.** The `Process Pool` page has CPU-bound
threading at **0.92x** (slower than sequential); this page has I/O-bound threading at **9.2x**.
Same pool, same machine, opposite verdicts — which is the actual lesson, and neither page can
give it alone. Each now points at the other.

### Tier B, batch 6 — Flask Phases 7/8/9, 6 diagrams + 3 verified notes

Diagrams: a blueprint before and after registration, the two contexts, what a view may return,

**Three verified behaviours, all of them things people get wrong from the docs alone.**

1. **Blueprint endpoints are namespaced.** With an app-level `/users` *and* an `admin`

### Tier B, batch 8 — Python Automation and Scripting, 6 diagrams + 3 verified notes

Diagrams: the three things `glob` quietly does not do, which `shutil` function keeps what,
what `argparse` does before your code runs, the dry-run pattern, implicit against explicit
waits, and the checks to make before a scraper's first request.

**`glob` and `pathlib.rglob` disagree, and the difference is measurable.** On a tree of
`a.txt`, `b.TXT`, `.hidden.txt`, `sub/c.txt`, `sub/deep/d.txt`:

| Call | Returns |
| --- | --- |
| `glob("*.txt")` | `a.txt`, `b.TXT` |
| `glob("**/*.txt")` | `sub/c.txt` — **one level**; `**` behaved like `*` |
| `glob("**/*.txt", recursive=True)` | all four |
| `Path(".").rglob("*.txt")` | the same **plus `.hidden.txt`** |

Three traps in one table, and all three fail *silently*:

1. **`**` does nothing without `recursive=True`** — the pattern is accepted either way, so the

2. **Dotfiles are invisible to `glob`** but **are** returned by `rglob`.
3. **Case sensitivity belongs to the filesystem, not the pattern.** `b.TXT` matched `*.txt`
   here on Windows and would not on Linux — so the same script processes a different set of
   files depending on where it runs.

**`shutil.copy` loses the modification time; `copy2` keeps it.** Verified. That decides whether
a backup or sync keeps any record of when files were written — and since `copytree` uses
`copy2` internally, a directory copy preserves timestamps while a hand-rolled loop using `copy`
does not.

**`argparse` exits rather than raising.** `-n abc` prints usage and raises `SystemExit(2)`, not
`ValueError` — correct for a CLI, wrong inside a library or a test. And `--dry-run` is read as
`ns.dry_run`; the dash-to-underscore rename is why a flag can appear to be ignored.

| `List / Access the list` | `L[10]` raises `IndexError`; **`L[10:20]` returns `[]`** — slicing never raises. `L[3:1]` is `[]`, `L[-10:99]` is the whole list. Slice assignment changes length: `a[1:3] = [9]` gives 4 elements, `b[1:2] = [7,8,9]` gives 7 |
| `File Handling / File Methods` | size **immediately after `open()`** on an existing 8-byte file: `r` 8, **`w` 0**, `a` 8, `r+` 8, **`w+` 0**, `x` raises `FileExistsError` |
| `Operator / Relational Operators` | `f(1) < f(2) < f(0)` called each function **once** (`calls == [1,2,0]`); `1 < 2 > 0` is legal; `False == 0`, `True == 1`, `1 in [True]` all True |
| `Set / Set Methods` | `union` returns a set and leaves the original; **`update` returns `None`** and mutates |
| `Threading / Daemon Threads` | same worker: `daemon=True` printed **nothing** (killed at shutdown), `daemon=False` printed `FINISHED` |
| `Tuple / Unpack the Tuple` | `a,*rest=(1,)` gives `rest == []`; wrong arity raises `ValueError` with the counts |

**Three of these are data-loss traps, not curiosities.**

- **`open(path, "w")` empties the file before you write a byte.** Measured size 0 straight after
  the call. A program that opens in `w` and then raises while computing the content has already
  destroyed the original.
- **`s = s.update(x)` sets `s` to `None`.** Nothing raises at that line; the failure arrives
  later as `TypeError: argument of type 'NoneType' is not iterable`.
- **An out-of-range slice returns `[]` instead of raising**, so an off-by-one travels several
  steps before it is noticed.

### `scripts/lint-p5.mjs` — new, wired into `npm run dsa`

Nothing on the build path ever parses a p5 sketch: `lib/p5/remake.ts` base64-encodes it and
`public/scripts/p5-viz.js` evals it in the browser. A broken sketch is an empty panel plus a
console message, and with 359 of them that needed closing. Five checks per sketch:

1. it parses, inside the same `with (p) { … }` wrapper the runtime uses;
2. it defines `setup()`;
3. every top-level function is a p5 hook or is **referenced** somewhere;
4. `setup()` actually **runs** against a stub p5 without throwing (3 s timeout);
5. the fence carries a `title=`.

**Findings on the existing corpus: 1 real bug**, a dead `mouseOut()` on
`Machine Learning/Phase 01/Artificial Intelligence vs Machine Learning vs Deep Learning.mdx`.
The runtime only re-binds the hooks in its `HOOKS` list and `mouseOut` is not one, so it never
fired. Harmless in effect — `mouseMoved` already cleared the flag — so it was removed.

**Two checks I got wrong first, both worth recording because the failure mode is the same:**

- **A "no backticks" rule.** Wrong. A lone backtick is a JS template literal and does not close
  a markdown fence — only ` ``` ` at the start of a line does. It fired on ~every sketch.
- **"declared but never called".** Wrong. Sketches pass helpers as values (`{ fn: relu }`), so
  six legitimate sketches were flagged. Count **references**, not call sites.

The lesson: a check that fires on a large fraction of a working corpus is almost certainly the
thing that is broken. Verify one finding by hand before believing the report.

**Known limitation of check 4:** it does not catch undefined identifiers. The stub answers for
every name it is asked about, so a stray `total += 1` yields `NaN` where a browser would throw a
`ReferenceError`. Closing that needs a real p5 API allowlist instead of a catch-all proxy.

### Verifying that a sketch draws the *right* number

Parsing is a low bar. Two throwaway harnesses in the scratchpad run a page's sketches under a
stub p5 and assert their derived values against the oracle — `check_cheatsheet.mjs` (19 checks)
and `check_matrix.mjs` (15 checks), both passing. The trick is the proxy's `has` trap:

```js
has: (t, k) => k in t || !(k in globalThis),
```

Returning `true` unconditionally makes `with (p)` swallow `Math` too, so `Math.floor` resolves to
a no-op and the sketch dies in a way the browser never would. A real p5 instance does not own
`Math`, so the stub must not claim to either.

This pattern is worth promoting into a real test if the sketches keep growing — it is the only
thing that would have caught the garbled bar-width expression and the two `>= 1e9` thresholds
that bisection (which converges to 999,999,999) could never satisfy.

### Content quality bar

The sections are not boxes to tick. What makes these pages worth reading:

- **The cue teaches recognition**, not the algorithm — how do you know from the
  problem statement alone that this is the pattern, and when is it the *wrong*
  pattern.
- **The dry run traces something the code hides.** Monotonic Stack counts pops and
  pushes explicitly (14 stack ops for 8 elements, not 64) because that is the only
  way "why is a `while` inside a `for` still O(n)" becomes convincing. Prefix Sum
  shows the `{0: 1}` sentinel earning its keep at step 2.
- **Pitfalls are specific failures**, with the symptom. "A node-keyed visited set
  returns a plausible wrong answer, not a crash" is useful; "be careful with
  indices" is not.
- **Follow-ups are real interview questions** with the answer that scores.
- **Quiz explanations teach**, they do not just confirm. Wrong options should be
  the mistakes people actually make.

## 7. Gotchas learned the hard way

Each of these cost real time. They are listed in the order you will hit them.

### Backticks inside template literals

Markdown is full of inline-code backticks. Every one terminates a JS template
literal. `.replace(/`/g, '"')` does **not** save you — the backtick breaks parsing
before the regex runs. Cost four separate debugging rounds.

**Fix:** in batch scripts, build bodies as arrays of double-quoted lines:

```js
const md = (...lines) => lines.join("\n");
body: md("## Dry run", "", "Trace with `target = 9`:", ...)
```

Double quotes do not care about backticks. Batch 3 uses this and had zero issues.

**Correction to the previous version of this file, which said the trap does not
apply to `.mdx`: it does.** Not in prose or fenced code, but in every JSX attribute
written as a template literal — `hint={` … `}`, `code={…}`, `solution={…}`,
`sct={…}`. An inline `` `+ tight` `` inside a `hint` ends the literal and breaks the
page. Hit twice in one session. Prose and `<Quiz>` option strings are fine, because
those are double-quoted.

**`npm run dsa:lint` now checks this**, escape-aware (a `\`` inside the literal is
legal and common — several older pages rely on it). The audit does not, and cannot: it
only greps for headings.

Separately, `exec(compile(body, "sol", "exec"), {})` over each page's `solution={…}`
bodies runs every exercise and prints its real output — which is how you confirm the
`# expect …` comments are true rather than plausible. Worth doing per page; there is no
script for it because the harness differs per page.

### An unquoted `: ` in frontmatter breaks the whole build

`description: The default modern sheet: 150 problems across 18 categories` is **not valid YAML** —
the second colon makes it a nested mapping. `astro sync` then fails the entire build with

```
incomplete explicit mapping pair; a key node is missed; or followed by a non-tabulated empty line
```

and a stack trace that **names no file**. With ~1,070 content files that is expensive to locate by
hand. Shipped once, on `Phase-00/Sheet - NeetCode 150.mdx`.

**Fix:** double-quote any frontmatter value containing `: `, `#`, a leading `*`/`&`/`?`, or a
trailing `:`. **`npm run dsa:lint` now parses every page's frontmatter with `js-yaml`** and reports
the file and reason, so this cannot reach a build again. It is the first check the linter runs.

### A `|` inside a markdown table cell splits the cell

The variant maps and follow-up tables are markdown tables, and DSA content is full of
bitwise and boolean operators. `` `mask | (1 << i)` `` inside a table row ends the cell
early — the row silently renders with an extra column and the text after the pipe lands in
the wrong place. **Backticks do not protect it**; GFM splits cells before it parses inline
code.

Write `\|` inside table cells: `` `mask \| (1 << i)` ``. Found one shipped instance on
`BFS and Dijkstra with Extra State.mdx` (a follow-up row about key bitmasks) and nearly
shipped two more in the knapsack dry run. `npm run dsa:lint` now checks this.

### `overrides.yaml` duplicate keys

Flat YAML. Appending a second entry for an existing slug is a **hard parse error**
that points at a line number, not the slug. Hit three times.

**Fix — check before appending:**

```python
existing = set(l.split(':',1)[0] for l in s.split('\n')
               if l and not l.startswith(('#',' ')) and ':' in l)
add = [k+': '+v for k, v in new.items() if k not in existing]
skip = [k for k in new if k in existing]   # extend these IN PLACE instead
```

**Worth doing:** restructure `overrides.yaml` as a *list of objects with a `slug`
field*, so duplicates become a validation warning instead of a parse failure.

### Overrides can create rows, but need `lc` + `title`

An override normally only *patches* an existing row. Tagging a problem the corpus
never linked and no sheet lists **silently no-ops**, and the only symptom is an
"empty ladder" warning several steps later. Supply `lc` and `title` and
`merge-sheets.mjs` creates the row (it reports which it created).

### Batch scripts insert in array order

A section anchored to a heading that a *later* section will insert falls through to
append-at-end. Eight pages ended with `## The cue` sitting after `## Recap`. The
audit passed them — it checks existence, not position.

**Fix:** anchor only on headings present in the **original** page, and match whole
lines, not substrings (`## Practice` is a substring of
`## Practice -- real LeetCode problems`, which silently skipped one ladder).
`dsa-fix-placement.mjs` repairs both; its header documents them.

### Pattern slug convention

The canonical pattern slug is **the page's own filename slug**. Frontmatter
`patterns:` entries after the first are aliases. `companies.yaml` and `sheets.yaml`
reference page slugs, so a page declaring only short aliases makes those render
empty — this bug made every Amazon board empty until caught.

### Astro content schema

New frontmatter fields must be declared in `src/content/config.ts`. All DSA fields
are already there and **optional**, so the other ~700 site pages are unaffected.

### W12 — `MockInterview` + `DrillDeck` — ✅ **DONE**

**`DrillDeck`** — `src/components/dsa/DrillDeck.{tsx,astro}` + `useDrill.ts`.

The deck is **generated from the pages**, not authored: `scripts/gen-recall-deck.mjs`
walks every `## Recall card` and emits `src/data/dsa/recall.yaml`. A prompt therefore
cannot drift from its page. Wired in as `npm run dsa:recall`, part of `npm run dsa`.

Scheduling is **SM-2-lite**: SM-2's actual mechanism (a repetition counter driving an
expanding interval, reset on a lapse) with the easiness factor dropped, because the reader
self-grades and self-grading is too noisy to justify six buttons. Intervals
`1, 3, 7, 16, 35, 75, 160` days; three grades; `localStorage` under `pch:dsa:drill:v1`,
deliberately separate from `useProgress`'s `pch:dsa:v1` so resetting one cannot damage the
other. `schedule()` is pure and has **13 passing unit checks** (ladder climb, cap at the top
rung, "hard" repeating rather than advancing, "again" resetting and counting a lapse, and a
cold "again" not going negative).

**Two Recall-card shapes, found the hard way.** The generator first assumed every bullet was
`- **Aspect** — content` and matched **37 of 152 pages**. The other shape is
`- **The claim itself** — elaboration`, where showing the bold would hand over the answer —
so those become **cloze deletions** with the claim blanked. Handling both finds **140 cards
and 1,107 prompts** (614 aspect, 489 cloze, 4 bold-only) across 22 phases. The 13 pages that
still contribute nothing are the 8 Phase-00 sheet trackers and 5 Phase-20 problem sets, none
of which has a Recall card at all.

**`MockInterview`** — `src/components/dsa/MockInterview.{tsx,astro}`.

45 minutes, segmented into the playbook's four phases (5 clarify / 8 approach / 22 code /
10 test) with a needle showing actual against intended. A problem is drawn at random from the
**424 non-premium** problems (83/269/72 easy/medium/hard); premium ones are excluded because a
timed round on a statement you cannot open is worse than none.

The judge is Pyodide, **shared** with the site playground: `public/scripts/python-playground.js`
now exposes its loader as `window.__pchPyodide` (a ~10 MB runtime, so a second `loadPyodide()`
would be a second interpreter). Output is captured by redirecting `sys.stdout` **inside Python**
rather than via the playground's global JS stdout hooks, which belong to the playground and
would otherwise fight with the island.

**There is deliberately no hidden test suite.** Only the reader's own assertions run. Writing
the case that catches your own bug is the skill the testing phase scores, and a judge that
supplies the edge cases removes it. The page says plainly that a green run therefore does not
mean a correct solution. The 8-line rubric is self-scored and is shown only after the timer
stops — a rubric read while coding stops measuring behaviour and starts prompting it.

**Known gap:** the rubric being self-scored is the weakest part of this and the page says so.
There is no per-problem judge, and adding one for 446 problems is a separate project.

**Two things the component reports on purpose**, because they are what makes most study plans
dishonest:

1. **What it defers.** The whole syllabus is 104 pages / 444 problems — 57 weeks at 10 h/week,

   pages, and the deferred list is rendered rather than dropped. The full-syllabus figure is
   **computed from the passed budget**, not hardcoded, so it cannot drift.
2. **"New problems", not "problems".** Each problem is attributed to the *first* page claiming
   its pattern, so **15 of the 104 pages contribute 0 new problems** — they still need
   studying, but add no fresh practice. Labelling the column "problems" would have implied
   those pages are free.

Verified by porting `buildStudyPlan` to a standalone script against the real YAML (the `?raw`
imports mean bare `tsc` cannot resolve the data module — pre-existing for all four YAML files).
Invariants checked: no problem scheduled twice, every week has >= 1 page, teaching order
preserved across week boundaries, and `weeks=1 hoursPerWeek=1` still schedules a page.

## 9. Suggested session shape

1. `npm run dev`, load the three pages in §3, fix anything broken, report.
2. `npm run dsa:audit` and read `docs/dsa-coverage.md` for the current queue.
3. Pick **one** track (new pages, or one retrofit batch). Do not interleave.
4. After each page or batch: `dsa:merge` → `dsa:validate` → `dsa:audit` → raise
   `BASELINE`.
5. When context runs low, **stop and update the task list** rather than starting a
   page you cannot finish. A truncated `.mdx` with an unclosed `<Quiz>` breaks the
   page and passes no check.

**Budget reality:** one spine-complete page ≈ 300–400 lines ≈ one substantial work
unit. A session realistically produces 4–6 new pages or one retrofit batch. Plan
against that rather than promising ten.

**Measured, most recent session:** four new pages (Digit DP, 0-1 BFS, Morris, Binary
Lifting), which included three new viz traces and a Python oracle per page. Pages
needing a new trace cost noticeably more than pages that reuse one — Binary Lifting,
which reused `lca`, was the cheapest of the four. Budget three-plus-one rather than
five if each page needs its own trace.

## 10. Open decision for the repo owner

The original plan was 165 pages. 34 are spine-complete. The infrastructure is
finished — 15 viz components, 79 traced algorithms, a 432-problem database with
four sheets count-verified, and an audit that cannot regress. What remains is
content volume at roughly one page per work unit, i.e. many more sessions.

Worth deciding explicitly whether to continue to all 165 or narrow the target —
for example, the ~50 pages carrying the most interview weight (Phases 03, 05, 09,
10, 12, plus Phase 14 design and Phase 19 strategy) rather than the
competitive-programming tail in Phases 16–17. Deciding by attrition is the worse
outcome.
