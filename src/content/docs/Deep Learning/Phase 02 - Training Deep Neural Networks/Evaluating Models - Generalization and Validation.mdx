## What you'll learn

- why you need three data splits (train, validation, test), not two
- information leaks — how tuning on the validation set slowly corrupts it
- simple hold-out validation vs K-fold vs iterated K-fold
- the canonical overfitting curve: training loss down, validation loss turns up
- three common evaluation mistakes: unshuffled data, time leaks, and duplicate rows

## Why not just train/test?

The obvious approach — split data into training and test sets, train on one,
score on the other — has a hidden flaw. Developing a model always means tuning
its configuration: how many layers, how wide, which learning rate. You choose
those settings by watching performance on some held-out data. That watching
*is a form of learning* — a search through configuration space — so if that
held-out data is your test set, you'll unconsciously overfit to it, one small
decision at a time.

The fix is a third split: keep a **validation set** for every tuning decision
during development, and a **test set** you touch exactly once, at the very end.

```mermaid title="Three-way data split" desc="Tune against validation as much as you like; touch the test set only once, at the end."
flowchart LR
  D["All labeled data"] --> T["Training set<br/>(fit the weights)"]
  D --> V["Validation set<br/>(tune everything:<br/>architecture, hyperparameters)"]
  D --> S["Test set<br/>(touch once, at the end)"]
```

## Information leaks

Every time you tune a hyperparameter based on validation performance, a tiny
bit of information about the validation set leaks into the model. Do this once
and it's harmless. Do it hundreds of times across a long tuning campaign, and
your model quietly overfits *to the validation process itself* — even though
it was never directly trained on that data. That's exactly why the test set has
to stay untouched until the very end: it's your only unbiased read on how the
model will behave on truly new data.

## Simple hold-out validation

Set aside a chunk of data as validation, train on the rest:

```python title="Simple holdout validation" showLineNumbers{1}
import numpy as np

data = np.arange(20)
np.random.seed(0)
np.random.shuffle(data)

num_validation_samples = 4
validation_data = data[:num_validation_samples]
training_data = data[num_validation_samples:]

print("train size:", len(training_data), "val size:", len(validation_data))
```

Simple and fast — but if you don't have much data, your validation set may be
too small to be statistically representative. A telltale sign: reshuffling the
data before splitting gives you noticeably different validation scores each
time.

## K-fold validation

Split the data into `K` equal partitions. For each partition, train on the
other `K - 1` and validate on the one left out; the final score is the average
across all `K` runs. This is the right call once a single hold-out split feels
unstable.

```mermaid title="K-fold cross-validation (K=3)" desc="Every fold takes one turn as the validation set; the final score is the average across the three runs."
flowchart TD
  D["Full dataset<br/>(shuffled)"] --> F1["Fold 1: validation<br/>Folds 2, 3: train"]
  D --> F2["Fold 2: validation<br/>Folds 1, 3: train"]
  D --> F3["Fold 3: validation<br/>Folds 1, 2: train"]
  F1 --> S["Average the<br/>3 validation scores"]
  F2 --> S
  F3 --> S
```

```python title="K-fold cross-validation with scikit-learn" showLineNumbers{1}
import numpy as np
from sklearn.model_selection import KFold

X = np.arange(12).reshape(6, 2)
kf = KFold(n_splits=3)

for fold, (train_idx, val_idx) in enumerate(kf.split(X)):
    print(f"fold {fold}: train={len(train_idx)} val={len(val_idx)}")
```

## Iterated K-fold validation

For the rare case where you have very little data and need the most reliable
score possible: run K-fold validation `P` times, reshuffling the data before
each run, and average all `P × K` scores. It's expensive — you train that many
models — but it's the gold standard when a single K-fold run still looks noisy.

```python title="Averaging P repeats of K-fold validation" showLineNumbers{1}
import numpy as np

# each entry: the mean validation score from one full K-fold run
run_scores = [0.81, 0.83, 0.80]
iterated_kfold_score = np.mean(run_scores)
print(round(iterated_kfold_score, 3))
```

## Three ways to leak information without noticing

- **Unshuffled data.** If your samples are ordered by class and you slice off
  the last 20% as your test set, you may end up training only on classes 0–7
  and testing only on classes 8–9. Always shuffle before splitting — unless...
- **The arrow of time.** For time-ordered data (tomorrow's weather, stock
  prices), shuffling is exactly wrong: it lets the model train on the future
  and get "tested" on the past. Test data must always come *after* training
  data chronologically.
- **Redundant rows.** If the same sample (or a near-duplicate) appears in both
  the training and validation sets, you're partly validating on data the model
  has already memorized. Deduplicate before splitting.

## Visualize it: the canonical overfitting curve

Every model type, on every dataset, tends to produce the same shape: training
loss falls smoothly and keeps falling, while validation loss falls too — until
it hits a floor and starts climbing back up. That turning point is the best
generalizing version of the model you're going to get; training past it only
makes things worse.

```p5 title="The canonical overfitting curve" desc="Watch an epoch counter sweep left to right: training loss keeps falling, but validation loss bottoms out and turns upward — that's the point to stop training." height="280"
function setup() {
  createCanvas(600, 280);
  textFont("monospace");
}
function trainLoss(t) { return 0.9 * Math.exp(-3 * t) + 0.05; }
function valLoss(t) {
  const floor = 0.9 * Math.exp(-3 * t) + 0.05;
  const rise = 0.5 * Math.pow(Math.max(0, t - 0.35), 2);
  return floor + rise;
}
function draw() {
  background(13, 17, 23);
  const gx = 54, gy = 20, gw = width - 90, gh = height - 60;
  stroke(60, 70, 84);
  strokeWeight(1);
  line(gx, gy + gh, gx + gw, gy + gh);
  line(gx, gy, gx, gy + gh);
  noStroke();
  fill(160);
  textSize(11);
  text("epoch 0", gx, gy + gh + 16);
  text("epoch T", gx + gw - 34, gy + gh + 16);
  text("loss", gx - 38, gy + 6);

  // one training run: sweep an epoch counter across the x-axis, hold at the
  // end for a beat so the final curve is readable, then loop back to epoch 0
  const sweepFrames = 165, holdFrames = 55, period = sweepFrames + holdFrames;
  const localT = frameCount % period;
  const tHead = constrain(localT / sweepFrames, 0, 1);

  function plot(fn, col) {
    stroke(col[0], col[1], col[2]);
    strokeWeight(2.5);
    noFill();
    beginShape();
    for (let i = 0; i <= 100; i++) {
      const t = i / 100;
      if (t > tHead) break;
      const y = constrain(fn(t), 0, 1);
      vertex(gx + t * gw, gy + gh - y * gh);
    }
    endShape();
    noStroke();
    fill(col[0], col[1], col[2]);
    ellipse(gx + tHead * gw, gy + gh - constrain(fn(tHead), 0, 1) * gh, 7, 7);
  }
  plot(trainLoss, [75, 139, 190]);
  plot(valLoss, [255, 211, 67]);

  const tStar = 0.35;
  if (tHead >= tStar) {
    const xStar = gx + tStar * gw;
    stroke(120, 200, 120, 180);
    strokeWeight(1.5);
    line(xStar, gy, xStar, gy + gh);
    noStroke();
    fill(120, 200, 120);
    textSize(11);
    text("stop here", xStar + 6, gy + 14);
  }

  fill(75, 139, 190);
  textSize(12);
  text("training loss", gx + gw - 110, gy + 40);
  fill(255, 211, 67);
  text("validation loss", gx + gw - 110, gy + 58);
}
```

:::tip[From the book]
Chollet's summary of why tuning is dangerous: "every time you use feedback from
your validation process to tune your model, you leak information about the
validation process into the model." That's harmless the first few times, but
repeated over a long tuning campaign it eventually inflates your validation
score beyond what the model will actually achieve on genuinely new data — which
is exactly why the test set must stay locked away until the very last check.
:::
