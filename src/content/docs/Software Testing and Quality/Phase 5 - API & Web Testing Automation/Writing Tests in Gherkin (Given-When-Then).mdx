## Gherkin structure

A `.feature` file contains:

- Feature
- Scenario
- Steps (Given/When/Then)

## Example feature

```gherkin title="login.feature"
Feature: Login
  As a registered user
  I want to login
  So that I can access my account

  Scenario: Valid login
    Given I am on the login page
    When I login with username "alice" and password "secret"
    Then I should see the dashboard
```

## Example step definition

```python title="steps/login_steps.py" showLineNumbers{1}
from behave import given, when, then


@given("I am on the login page")
def step_open_login(context):
    # open browser or call app
    pass


@when('I login with username "{username}" and password "{password}"')
def step_login(context, username, password):
    pass


@then("I should see the dashboard")
def step_dashboard(context):
    pass
```

## Tips

- Keep steps reusable
- Don’t put too many details in Gherkin
- Use Gherkin for business behavior, not technical design

## Keywords, briefly

- **Feature**: a name and short description of a capability.
- **Scenario**: one concrete example.
- **Given**: the starting state.
- **When**: the action the user or system takes.
- **Then**: the observable outcome.
- **And / But**: continue the previous type of step.
- **Background**: steps shared by every scenario in the file.
- **Scenario Outline** with an **Examples** table: the same scenario with several data rows.

## Bad versus good style

The most common mistake is to write Gherkin like a script of UI actions:

```gherkin title="login_bad.feature"
Scenario: Login
  Given I open "https://staging.example.com/login"
  When I type "alice" into the field with id "username"
  And I type "secret" into the field with id "password"
  And I click the button with css "button[type=submit]"
  Then I see an h1 that says "Dashboard"
```

Every locator change now needs a feature file edit, and business readers cannot see what matters. State the intent:

```gherkin title="login_good.feature"
Scenario: Registered user signs in
  Given a registered user "alice"
  When she signs in with the correct password
  Then she sees her dashboard
```

The details of clicks and locators go into step definitions, or better, into page objects.

## Scenario Outline for data variations

```gherkin title="shipping.feature"
Scenario Outline: Shipping cost by order total
  Given a cart with a total of <total>
  When I check the shipping cost
  Then the shipping cost is <cost>

  Examples:
    | total | cost |
    | 30    | 5    |
    | 99    | 5    |
    | 100   | 0    |
```

This is the Gherkin version of `pytest.mark.parametrize`. The rows also show the boundary at 100 to non-programmers.

## Matching steps in Python

behave uses parse-style patterns. `{total:d}` captures an integer, and `<total>` in the outline is replaced before matching:

```python title="steps/shipping_steps.py" showLineNumbers{1}
from behave import given, when, then


@given("a cart with a total of {total:d}")
def step_cart(context, total):
    context.total = total


@when("I check the shipping cost")
def step_check(context):
    context.cost = 0 if context.total >= 100 else 5


@then("the shipping cost is {cost:d}")
def step_cost(context, cost):
    assert context.cost == cost
```

## Rules of thumb

- One behaviour per scenario, and about three to six steps.
- Write in the business language, in the present tense, in third person.
- Do not test every edge case here. Keep a few clear examples and leave the rest to unit tests.
- Reuse step wording so the number of step definitions stays small.

## What goes wrong

Scenarios that depend on each other, steps whose wording differs by a word so they need duplicates, and feature files nobody outside the team reads. If the business never reads them, the extra layer has no value. The BDD lesson explains when it is worth doing.
