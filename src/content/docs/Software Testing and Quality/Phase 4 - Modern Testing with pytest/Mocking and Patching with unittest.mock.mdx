After that there are two names pointing at the same function, and replacing the original does nothing to the copy the code under test actually calls. This is the single most common reason a mock appears to be ignored."
flowchart TD
  A["svc.py defines now()"] --> B["app.py does: from svc import now"]
  B --> C["app.now and svc.now both point at the same function"]
  D["patch('svc.now')"] --> E["replaces the name in svc"]
  E --> F["app.now still points at the ORIGINAL"]
  F --> G["greet() returns 'hello REAL' -- the mock did nothing"]
  H["patch('app.now')"] --> I["replaces the name app actually looks up"]
  I --> J["greet() returns 'hello FAKE' -- the mock works"]
```

:::caution[Measured: the same mock, two targets, two outcomes]
`svc.py` defines `now()`. `app.py` does `from svc import now` and `greet()` calls it.

| Patch target | `greet()` returns |
| --- | --- |
| `patch("mk.svc.now")` — where it is *defined* | `hello REAL` — **the mock had no effect** |
| `patch("mk.app.now")` — where it is *used* | `hello FAKE` |

`from x import y` binds `y` into the importing module. Patching the original leaves that binding
untouched, so the code under test keeps calling the real thing — and the test passes for the
wrong reason, or fails with a confusing message about the real function.

The rule: **patch the name in the module under test**, not the module that defined it. If you
prefer not to think about it, `import svc` and call `svc.now()` — then the lookup happens at
call time and patching `svc.now` works as expected.
:::

## Why mock?

You mock when a dependency is:

- slow
- flaky
- external (network, API)
- expensive to set up

## Example: patch a function call

```python title="service.py" showLineNumbers{1}
import requests


def fetch_status(url: str) -> int:
    return requests.get(url, timeout=10).status_code
```

```python title="test_service.py" showLineNumbers{1}
from unittest.mock import patch

import service


def test_fetch_status_mocked():
    with patch("service.requests.get") as get:
        get.return_value.status_code = 200
        assert service.fetch_status("https://example.com") == 200
```

## Using autospec

`autospec=True` helps match real signatures.

```python title="patch_autospec.py" showLineNumbers{1}
from unittest.mock import patch


def sample(a, b):
    return a + b


with patch("__main__.sample", autospec=True) as fn:
    fn.return_value = 10
    assert sample(1, 2) == 10
```

## Tips

- mock at the *import location used by the code under test*
- keep mocks minimal; prefer real unit logic

## A fuller example: mock the failure, not only the success

The real value of mocks is reaching situations that are hard to create for real, such as a timeout or a 500 response. This is a test you could not write reliably against a live server.

```python title="client.py" showLineNumbers{1}
import requests


def get_username(user_id: int) -> str:
    try:
        r = requests.get(f"https://api.example.com/users/{user_id}", timeout=5)
        r.raise_for_status()
        return r.json()["name"]
    except requests.RequestException:
        return "unknown"
```

```python title="test_client.py" showLineNumbers{1}
from unittest.mock import patch, Mock

import requests

import client


def test_returns_name_on_success():
    fake = Mock()
    fake.json.return_value = {"name": "Ana"}
    with patch("client.requests.get", return_value=fake) as get:
        assert client.get_username(7) == "Ana"
    get.assert_called_once_with("https://api.example.com/users/7", timeout=5)


def test_falls_back_on_timeout():
    with patch("client.requests.get", side_effect=requests.Timeout):
        assert client.get_username(7) == "unknown"
```

`return_value` sets what the call gives back, and `side_effect` makes it raise. `assert_called_once_with` checks that the code called the API the way you meant, including the timeout.

## Mocks that lie

A plain `Mock` accepts any attribute and any arguments, so it can pass even when the real function would fail. If someone renames a parameter of the real function, a plain mock does not notice. `autospec=True` (or `create_autospec`) copies the real signature and raises `TypeError` when the call does not match. Use it by default.

## What goes wrong in practice

- **Patching the wrong name.** The diagram at the top of this page shows the most common cause: patch the name where it is looked up.
- **Over-mocking.** If a test mocks five collaborators, it checks wiring instead of behaviour and breaks on every refactor. Mock at the edge (network, clock, filesystem), and use real objects inside.
- **Asserting on calls too much.** Checking every call and its order ties the test to the implementation.
- **Mock never proves the real thing works.** The mock reflects your belief about the API. Add a small integration or contract test to check that belief against reality.

## Where it fits

Mocks make unit tests fast and deterministic, which the unit testing lesson requires. pytest also offers `monkeypatch` for simple replacements, and libraries such as `responses` for HTTP. Fixtures, in the neighbouring lesson, are a good place to build a patched object once and share it.
