## What is a fixture?

A fixture is a reusable function that provides a value to tests.

Use fixtures for:

- test data factories
- temporary resources
- dependency setup (clients, config)

## Basic fixture

```python title="test_fixture_basic.py" showLineNumbers{1}
import pytest


@pytest.fixture
def user():
    return {"name": "Alice", "role": "admin"}


def test_user_role(user):
    assert user["role"] == "admin"
```

## Fixture scope

You can control how often fixtures run:

- `function` (default)
- `class`
- `module`
- `session`

```python title="fixture_scope.py" showLineNumbers{1}
import pytest


@pytest.fixture(scope="module")
def expensive_resource():
    return [1, 2, 3]
```

## Yield fixtures (cleanup)

```python title="fixture_yield.py" showLineNumbers{1}
import pytest


@pytest.fixture
def temp_config_file(tmp_path):
    p = tmp_path / "config.json"
    p.write_text('{"mode": "test"}')
    yield p
    # cleanup happens automatically for tmp_path
```

## Visualize it

A yield fixture runs its setup code, hands the value to the test, and then resumes after the test to run its teardown code.

## Why not just call a helper?

A plain helper function works for simple cases. Fixtures add three things: they are injected by name so tests stay short, they can run teardown code after the test even if it fails, and they have a scope, so an expensive setup can be shared. pytest also lets fixtures depend on other fixtures, and shows the dependency in error messages.

## Fixtures that depend on fixtures

```python title="test_fixture_chain.py" showLineNumbers{1}
import sqlite3

import pytest


@pytest.fixture
def conn():
    c = sqlite3.connect(":memory:")
    c.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT)")
    yield c
    c.close()


@pytest.fixture
def alice(conn):
    conn.execute("INSERT INTO users (name) VALUES ('Alice')")
    return conn.execute("SELECT id FROM users WHERE name = 'Alice'").fetchone()[0]


def test_alice_exists(conn, alice):
    row = conn.execute("SELECT name FROM users WHERE id = ?", (alice,)).fetchone()
    assert row[0] == "Alice"
```

The test asks for `alice`, and pytest first builds `conn`, then `alice`. Because both are function-scoped, every test gets a fresh database, and `conn.close()` runs after the test whether it passes or fails.

## Choosing a scope

- `function` (default): fresh for each test. Safest, and right for anything mutable.
- `module` or `session`: created once. Use for expensive read-only or resettable resources, such as a started server or a loaded model.

Widening a scope trades isolation for speed, so a wider fixture must not be modified by tests, or must be reset by a function-scoped fixture.

## Sharing with conftest.py

Put fixtures in a file called `conftest.py` and every test in that directory can use them without importing. Keep fixtures near the tests that use them, and move them up a folder only when a second directory needs them.

## Built-in fixtures worth knowing

`tmp_path` gives a fresh temporary directory, `monkeypatch` changes environment variables or attributes and restores them, and `capsys` captures printed output.

## What goes wrong

- **Hidden magic.** A test that uses ten fixtures is hard to read. Keep each fixture focused.
- **Shared state at a wide scope.** A `session` fixture that tests modify makes results depend on test order.
- **Doing assertions in fixtures.** A failure there is reported as an error in setup, not as a test failure, which is confusing.
- **Autouse overuse.** `autouse=True` runs for every test, including those that do not need it.

## Connections

Fixtures are pytest's answer to `setUp` and `setUpClass` from Phase 3. They combine well with parametrize (data) and with mocks (patched dependencies built once). The diagram above shows the setup, yield and teardown order.
