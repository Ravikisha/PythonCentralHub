## Why parameterize?

Instead of repeating similar tests, parameterize inputs.

## Example

```python title="test_parametrize.py" showLineNumbers{1}
import pytest


def add(a, b):
    return a + b


@pytest.mark.parametrize(
    "a,b,expected",
    [
        (1, 2, 3),
        (0, 0, 0),
        (-1, 1, 0),
    ],
)
def test_add(a, b, expected):
    assert add(a, b) == expected
```

## Parametrize with ids

```python title="test_parametrize_ids.py" showLineNumbers{1}
import pytest


@pytest.mark.parametrize(
    "s,expected",
    [("10", 10), ("0", 0)],
    ids=["ten", "zero"],
)
def test_int_parse(s, expected):
    assert int(s) == expected
```

## The problem it removes

Without parametrize you end up with tests like this:

```python title="test_repetitive.py" showLineNumbers{1}
def test_add_positive():
    assert add(1, 2) == 3


def test_add_zero():
    assert add(0, 0) == 0


def test_add_negative():
    assert add(-1, 1) == 0
```

They are the same test three times. The list of cases is also hard to review and easy to leave incomplete. With `@pytest.mark.parametrize` the logic is written once and the data is a table. Each row becomes its own test with its own result.

## Reading a failure

Suppose `add` had a bug for negative numbers. The output would list the cases separately:

```text
test_parametrize.py::test_add[1-2-3] PASSED
test_parametrize.py::test_add[0-0-0] PASSED
test_parametrize.py::test_add[-1-1-0] FAILED
```

You know exactly which input failed, and you can rerun only that one with `pytest "test_parametrize.py::test_add[-1-1-0]"`. A `for` loop inside one test would stop at the first failure and report a single result.

## Good ids and stacked parameters

Generated ids such as `-1-1-0` are hard to read for complex data, so use `ids=` (shown above) or `pytest.param(..., id="...")`:

```python title="test_param_ids.py" showLineNumbers{1}
import pytest


def is_valid_username(name: str) -> bool:
    return 3 <= len(name) <= 12 and name.isalnum()


@pytest.mark.parametrize(
    "name, ok",
    [
        pytest.param("ana", True, id="min-length"),
        pytest.param("ab", False, id="too-short"),
        pytest.param("a" * 13, False, id="too-long"),
        pytest.param("ana_b", False, id="symbol"),
    ],
)
def test_username(name, ok):
    assert is_valid_username(name) is ok
```

Stacking two decorators multiplies the combinations. Two lists of three values give nine tests, which is useful for checking every combination of, say, browser and locale.

## Expected exceptions in a table

You can include failure cases by checking the error inside the test, or by using `pytest.raises` in a separate parametrized test that lists only the bad inputs. Keeping success and failure in separate tests keeps each one simple.

## What goes wrong

- **Computing the expected value in the test.** If the expected column calls the same code as the function, the test cannot fail. Write the expected values by hand.
- **Huge tables.** Hundreds of rows that nobody reads. Choose cases around boundaries and equivalence classes.
- **Hiding a complicated branch inside the test** with `if` statements. If rows need different logic, they belong in different tests.

## Connections

The boundary and equivalence ideas come from the principles lesson. Fixtures, next, supply objects, while parametrize supplies data. The two are often used together.
