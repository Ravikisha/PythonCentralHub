## Why class-level setup?

Sometimes setup is expensive:

- loading a large fixture file
- initializing test data

Use `setUpClass` to run once per class.

## Example

```python title="setupclass_teardownclass.py" showLineNumbers{1}
import unittest


class TestExpensiveSetup(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        cls.data = list(range(1000))

    @classmethod
    def tearDownClass(cls):
        cls.data = []

    def test_sum(self):
        self.assertEqual(sum(self.data), sum(range(1000)))

    def test_len(self):
        self.assertEqual(len(self.data), 1000)
```

## Caution

- Don’t share mutable state between tests unless read-only.
- Tests should not depend on run order.

## When to use it

`setUp` runs before every test, which is right for most cases because each test starts from a clean state. When creating the state is slow, such as parsing a big file, starting a server or building a database schema, repeating it for every test wastes time. `setUpClass` runs once before the first test in the class, and `tearDownClass` once after the last.

The order for a class with two tests is: `setUpClass`, then `setUp`, `test_a`, `tearDown`, then `setUp`, `test_b`, `tearDown`, then `tearDownClass`.

## A more realistic example

```python title="setupclass_db.py" showLineNumbers{1}
import sqlite3
import unittest


class TestOrders(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        cls.conn = sqlite3.connect(":memory:")
        cls.conn.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, total REAL)")

    @classmethod
    def tearDownClass(cls):
        cls.conn.close()

    def setUp(self):
        self.conn.execute("DELETE FROM orders")

    def test_insert(self):
        self.conn.execute("INSERT INTO orders (total) VALUES (9.5)")
        count = self.conn.execute("SELECT COUNT(*) FROM orders").fetchone()[0]
        self.assertEqual(count, 1)

    def test_starts_empty(self):
        count = self.conn.execute("SELECT COUNT(*) FROM orders").fetchone()[0]
        self.assertEqual(count, 0)
```

The expensive part, the connection and schema, is created once. The cheap part, clearing the table, still runs in `setUp` before every test, so the two tests cannot affect each other.

## Rules that keep it safe

- The methods must be decorated with `@classmethod`, and they receive `cls`. Attributes set here are shared by all tests in the class.
- Only share things that are read-only or that you reset in `setUp`, as above.
- If `setUpClass` raises, none of the tests in the class run, and `tearDownClass` is not called. Use `cls.addClassCleanup(...)` when a resource must be released even if setup fails partway.
- Module-level equivalents exist: `setUpModule` and `tearDownModule`.

## What goes wrong

The common failure is shared mutable state. One test appends to a list created in `setUpClass`, and another test reads it and passes or fails depending on run order. Random ordering and running a single test on its own expose it. If a test only works when run after another, the state is leaking.
