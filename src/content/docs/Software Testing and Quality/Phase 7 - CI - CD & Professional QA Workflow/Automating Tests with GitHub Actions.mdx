## What GitHub Actions is

GitHub Actions runs workflows on:

- push
- pull_request
- schedules

## Minimal Python test workflow

Create `.github/workflows/tests.yml`:

```yaml
name: tests

on:
  pull_request:
  push:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Run tests
        run: |
          pytest -q
```

## Tips

- cache pip if workflows are slow
- upload coverage/html reports as artifacts
- run lint/type checks as separate jobs

## How a workflow is organised

A workflow is a YAML file in `.github/workflows/`. It has **triggers** (`on:`), one or more **jobs**, and each job has **steps**. Each job starts on a fresh virtual machine, so nothing carries over from your laptop or from a previous run. That is the point: if the tests pass there, they do not depend on your machine.

Reading the workflow above from the top: `actions/checkout` fetches your code, `setup-python` installs the interpreter, then two `run` steps install dependencies and start pytest. If any step exits with a non-zero code, the job fails and the pull request shows a red cross.

## Testing on several Python versions

A matrix runs the same job for each combination. This catches code that works on 3.12 but not on 3.10.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.10", "3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest -q --cov=app --cov-report=xml
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: coverage-${{ matrix.python-version }}
          path: coverage.xml
```

`cache: pip` reuses downloaded packages between runs. `fail-fast: false` lets the other versions finish so you see every failure, not only the first. `if: always()` uploads the report even when tests fail, which is when you need it most.

## Making it a gate

The workflow only checks. To enforce it, open the repository settings, add a branch protection rule for `main`, and mark the `test` job as a required status check. Without that, people can merge a red pull request.

## What goes wrong

- **Unpinned dependencies.** Tests pass locally with an old version and fail in CI with the newest. Pin versions in `requirements.txt` or a lock file.
- **Missing files.** A config file that was never committed makes CI fail, which is the useful discovery.
- **Secrets in logs.** Store tokens in repository secrets and read them as `${{ secrets.NAME }}`. Never echo them.
- **Slow workflows.** Split lint, type check and tests into separate jobs so they run in parallel, and cache dependencies.
- **Tests that need a service.** Use the `services:` key to start Postgres or Redis for the job instead of skipping those tests.
