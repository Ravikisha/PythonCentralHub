## What pre-commit does

`pre-commit` runs checks before a commit is created.

This helps:

- keep formatting consistent
- avoid committing broken code

## Example .pre-commit-config.yaml

```yaml
repos:
  - repo: https://github.com/psf/black
    rev: 24.10.0
    hooks:
      - id: black

  - repo: https://github.com/pycqa/flake8
    rev: 7.1.1
    hooks:
      - id: flake8
```

## Install and run

```bash
pre-commit install
pre-commit run --all-files
```

## Tip

Still keep CI checks—hooks are helpful but not a replacement.

## What is happening under the hood

Git can run a script before it creates a commit, in `.git/hooks/pre-commit`. If the script exits with an error, the commit is refused. Writing and sharing such scripts by hand is awkward, because `.git` is not part of the repository. The `pre-commit` tool solves this: you list hooks in `.pre-commit-config.yaml`, which is committed, and each developer installs it once.

## Setup from scratch

```bash
pip install pre-commit
pre-commit install
git add .pre-commit-config.yaml
```

After `pre-commit install`, every `git commit` runs the hooks on the staged files only, which keeps them quick. The first run downloads and caches each hook environment, so it is slower.

Here is a slightly fuller configuration than the one above:

```yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files

  - repo: https://github.com/psf/black
    rev: 24.10.0
    hooks:
      - id: black

  - repo: https://github.com/pycqa/flake8
    rev: 7.1.1
    hooks:
      - id: flake8
```

## What happens on a failing commit

If Black reformats a file, the hook reports "files were modified" and the commit stops. Your files are now fixed but unstaged. Run `git add` again and commit, and it passes. This surprises everybody the first time. Flake8 does not fix anything, so you edit the lines it reports.

Useful commands:

- `pre-commit run --all-files` checks the whole repository, which you should do once when adding a hook to an existing project.
- `pre-commit autoupdate` moves each `rev` to the latest release.
- `git commit --no-verify` skips the hooks for one commit. Use it rarely, for example for a work-in-progress commit on your own branch.

## Which checks belong in hooks

Keep hooks to things that take a second or two: formatting, lint, whitespace, secrets detection. Do not run the whole test suite there, because people will start using `--no-verify`. The slow checks belong in CI.

## What goes wrong

- **Hooks are optional.** Nothing forces a new teammate to run `pre-commit install`, and `--no-verify` bypasses everything. This is why CI must run the same checks.
- **Version mismatch.** If the hook uses Black 24 and CI uses Black 23, they disagree. Run `pre-commit run --all-files` in CI so both use the pinned versions.
- **Slow hooks** lead to skipped hooks.

## Connections

Pre-commit is the fast, local layer of the quality gate, with CI as the enforced layer. The Black and Flake8 lessons explain the tools used above.
