## A good bug report answers

- What happened?
- What should have happened?
- How can we reproduce it?
- How severe is it?

## Recommended template

- **Title**: short and specific
- **Environment**: OS, browser/app version
- **Steps to reproduce**: numbered steps
- **Expected result**
- **Actual result**
- **Evidence**: screenshots/logs/videos
- **Impact**: users affected, frequency

## Example

**Title**: Checkout fails when coupon contains spaces

**Steps**:
1. Add item to cart
2. Open checkout
3. Enter coupon `SAVE 10`
4. Click Apply

**Expected**: Discount applied

**Actual**: 500 error

## Tip

If you can include:

- HAR file
- request/response sample

…it speeds up debugging.

## The goal: another person can reproduce it in five minutes

A report is useful only if the reader sees the same failure. Most bad reports fail because they leave out something the reporter took for granted: the account type, the browser, the data they had, the step they did without noticing.

## Weak versus strong

Weak:

> Checkout is broken. Please fix ASAP.

Strong:

> **Title:** Checkout returns 500 when coupon code contains a space
> **Environment:** staging, build 2024.11.3, Chrome 130 on Windows 11, logged in as a standard user
> **Steps:**
> 1. Add any product to the cart
> 2. Open checkout
> 3. Enter coupon `SAVE 10` and click Apply
> **Expected:** the 10 percent discount is applied, or a message says the coupon is invalid
> **Actual:** a full-page 500 error. The cart is emptied
> **Frequency:** always, 5 out of 5 attempts. `SAVE10` (no space) works
> **Evidence:** screenshot, and the log line `ValueError: coupon not found` at 10:42:17
> **Impact:** any customer who mistypes a coupon loses their cart

The strong version contains the trigger, the comparison between expected and actual, and a clue (the coupon works without the space) that narrows the search.

## Turning the report into a test

A good report converts directly into a regression test. This is how the coupon report above becomes code:

```python title="test_coupon_regression.py" showLineNumbers{1}
import pytest

from checkout import apply_coupon


def test_coupon_with_space_is_handled():
    # Bug #412: 500 error on "SAVE 10"
    result = apply_coupon("SAVE 10")
    assert result.code == "SAVE10"


def test_unknown_coupon_reports_invalid():
    with pytest.raises(ValueError, match="invalid"):
        apply_coupon("NOPE")
```

If you cannot write the test from the report, the report is missing something.

## Reduce first

Before filing, remove steps until only the essential ones are left. "It fails when I have three items, a coupon, and a saved address" often turns out to be just "it fails when there is a coupon". A minimal repro halves the debugging time.

## Evidence that helps

Screenshots or a short screen recording, console errors, the request and response (a HAR file or a curl command), and log lines with timestamps. Remove passwords and personal data before attaching anything.

## What goes wrong

- **Several bugs in one report,** so it cannot be closed cleanly. File one issue per problem.
- **Opinions instead of facts:** "the page is terrible" gives the developer nothing.
- **Missing frequency.** "Sometimes" needs a count, for example 3 out of 10, and any pattern you noticed.
- **Blame in the title.** Describe the behaviour, not the person or team.
- **Changing the report silently.** Add comments when you learn more.

## Connections

The defect life cycle lesson shows where the report goes next, and severity and priority are set in triage. Regression testing keeps the bug from coming back.
