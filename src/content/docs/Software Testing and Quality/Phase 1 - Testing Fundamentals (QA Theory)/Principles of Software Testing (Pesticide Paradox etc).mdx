## 1) Testing shows presence of defects

Testing can prove bugs exist.

It cannot prove there are **no bugs**.

## 2) Exhaustive testing is impossible

You can’t test every input combination.

So you prioritize:

- risk
- critical paths
- common user workflows

## 3) Early testing saves time and money

Shift-left testing:

- clarify requirements early
- test during development

## 4) Defect clustering

Most bugs appear in a small number of modules.

This helps you focus on:

- hotspots
- high-change areas

## 5) Pesticide paradox

If you run the same tests forever, they stop finding new bugs.

You must:

- refresh test cases
- add tests for new risks
- include exploratory testing

## 6) Testing is context-dependent

Testing strategies differ for:

- banking apps
- games
- embedded devices

## 7) Absence-of-errors fallacy

A “bug-free” app that doesn’t meet user needs is still a failure.

## Principles in practice

Each principle changes a decision you make, so here is how they show up in real work.

**Exhaustive testing is impossible.** A function that takes two 32-bit integers has about 1.8 times 10 to the 19th combinations. You choose inputs by technique instead: boundary values, equivalence classes and risk.

```python title="test_boundaries.py" showLineNumbers{1}
import pytest


def is_adult(age: int) -> bool:
    return age >= 18


@pytest.mark.parametrize("age, expected", [(17, False), (18, True), (19, True), (0, False)])
def test_is_adult_boundary(age, expected):
    assert is_adult(age) == expected
```

Four inputs around the edge tell you more than four hundred random ones.

**Defect clustering.** If the payments module produced most of last quarter's bugs, it deserves more tests this quarter. Bug trackers and `git log` on the files that change most will tell you where.

**Pesticide paradox.** A suite that is always green may only be repeating the same questions. Review it now and then. Add tests for each new bug, write new scenarios for new risks, and keep some time for exploratory sessions. Mutation testing tools take this further by breaking your code on purpose and checking that a test fails.

**Absence-of-errors fallacy.** A team can ship software with zero open defects that nobody wants. Validation with real users, covered later in this phase, is the counterweight.

## Mistakes teams make

- Reporting "all tests pass" as "no bugs". Passing tests only show that those checks passed.
- Spreading effort evenly across modules instead of following risk.
- Waiting for a finished build before reading requirements. Ambiguity found in a meeting costs minutes, and the same ambiguity found in production costs days.
- Copying one strategy everywhere. A game and a bank need different tests, so use the context-dependence principle.
