## Smoke testing

A smoke test answers:

- “Does the build basically work?”

It’s a quick suite that checks:

- app starts
- critical endpoints respond
- major screens load

Often run:

- after deployment to staging
- after CI build

## Sanity testing

A sanity test answers:

- “Does this specific change look OK?”

It’s narrower and focused on a particular area.

Example:

- after a checkout fix, sanity test checkout only

## Quick comparison

- smoke: broad and shallow
- sanity: narrow and deep

## Tip

Keep smoke tests small and reliable.

## Two quick checks, two different questions

Smoke and sanity tests are both fast, and people mix them up because of that. The difference is what triggers them and how wide they look.

- **Smoke test** is run on a new build or deployment. It asks whether the thing is worth testing at all. If the app cannot start or the login page returns a 500, there is no point in running the detailed suite.
- **Sanity test** is run after a small change or fix. It asks whether that change behaves sensibly, and it looks at one area closely.

## A smoke test in code

A smoke suite calls the few endpoints that must always work. It should take seconds.

```python title="test_smoke.py" showLineNumbers{1}
import os
import pytest
import requests

BASE = os.environ.get("APP_URL", "http://localhost:8000")


@pytest.mark.smoke
@pytest.mark.parametrize("path", ["/health", "/login", "/api/products"])
def test_endpoint_responds(path):
    r = requests.get(BASE + path, timeout=5)
    assert r.status_code < 500
```

Run it after each deployment with `pytest -m smoke`. If any check fails, the pipeline stops and the deployment is rolled back or blocked. You would register the `smoke` marker in `pytest.ini` to avoid warnings.

A sanity check after the coupon fix would instead be a handful of checkout cases: apply a coupon with spaces, apply an expired one, remove it, and check the total. It does not touch the profile or search pages.

## What goes wrong

- **A smoke suite that grows.** Once it takes ten minutes, nobody waits for it. Keep it to critical paths.
- **Flaky smoke tests.** If they fail at random, people learn to override them, which defeats the purpose.
- **Treating sanity as a replacement for regression.** A fix can break a distant feature, and only a regression run catches that.
- **Testing production with destructive actions.** Smoke tests that run against production must be read-only, or use a dedicated test account.

## Where they fit

Order of use after a build: smoke first (is it alive), then sanity on the changed area, then regression (did anything else break). The previous lesson covers regression, and the CI lessons show how to run smoke tests as a pipeline stage.
