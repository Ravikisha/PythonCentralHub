## What is a “unit”?

A unit is the smallest testable piece of your code.

Usually:

- a function
- a method
- a small class

## What unit tests should be

- fast (no DB, no network)
- deterministic (same input → same output)
- focused (one behavior per test)

## What unit tests should avoid

- real HTTP calls
- real databases
- time-dependent behavior (unless controlled)

## Example unit logic

```python title="price.py" showLineNumbers{1}
def apply_discount(price: float, percent: float) -> float:
    if percent < 0 or percent > 100:
        raise ValueError("percent must be between 0 and 100")
    return round(price * (1 - percent / 100), 2)
```

A unit test for this function is small and has no dependencies.

## Key takeaway

Unit tests are your **fastest safety net** for refactoring.

## Writing tests for apply_discount

The function above has three behaviours worth testing: normal discounts, the edge values, and invalid input.

```python title="test_price.py" showLineNumbers{1}
import pytest

from price import apply_discount


def test_ten_percent_off():
    assert apply_discount(200.0, 10) == 180.0


@pytest.mark.parametrize("percent, expected", [(0, 50.0), (100, 0.0)])
def test_edges(percent, expected):
    assert apply_discount(50.0, percent) == expected


@pytest.mark.parametrize("bad", [-1, 101])
def test_invalid_percent(bad):
    with pytest.raises(ValueError):
        apply_discount(50.0, bad)
```

Each test has a name that states the behaviour, one reason to fail and no outside dependencies. When one fails you know which rule broke without reading a stack trace.

## Testing code that depends on something

Real code often calls a clock, a database or an API. Pass the dependency in, so the test can replace it:

```python title="greeting.py" showLineNumbers{1}
from datetime import datetime


def greeting(now=None):
    now = now or datetime.now()
    return "Good morning" if now.hour < 12 else "Good afternoon"
```

```python title="test_greeting.py" showLineNumbers{1}
from datetime import datetime

from greeting import greeting


def test_morning():
    assert greeting(datetime(2024, 1, 1, 9, 0)) == "Good morning"


def test_afternoon():
    assert greeting(datetime(2024, 1, 1, 15, 0)) == "Good afternoon"
```

No mocking library is needed. Designing for testability, with small functions that take inputs and return outputs, is more valuable than any tool.

## What goes wrong

- **Testing implementation, not behaviour.** A test that asserts which private function was called breaks on every refactor without finding a bug.
- **Several behaviours in one test.** The first failed assert hides the others.
- **Mocking everything.** If every collaborator is a mock, the test only checks the mocks. Use real objects when they are cheap and deterministic.
- **Chasing 100 percent coverage.** Coverage shows what ran, not what was checked.

## Where units fit

Unit tests are the base of the pyramid and the only level fast enough to run on every save. They cannot show that units work together, which is why integration tests come next. Phase 3 shows how to write them with unittest, and Phase 4 with pytest.
