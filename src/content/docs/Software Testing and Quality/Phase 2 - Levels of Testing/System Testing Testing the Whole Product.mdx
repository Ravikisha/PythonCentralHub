## What system testing means

System testing validates the **entire application** as a whole.

It checks:

- functional behavior
- performance constraints
- security requirements (basic checks)
- end-to-end workflows

## Typical environment

- staging environment
- production-like config
- real databases (test data)

## Example system test scenarios

- signup → login → purchase
- role-based access checks
- multi-service workflow

## Relationship to E2E tests

Many people use the words interchangeably.

A useful distinction:

- **System testing**: focus on system behavior vs spec
- **E2E**: focus on user flows (often UI-driven)

## What is being tested

Unit and integration tests look at parts. System testing treats the application as a black box and checks it against the requirements as one product, in an environment that resembles production. It is where you find problems that only exist when everything is connected: a background job that locks a table the checkout needs, a config value that differs between services, or an email that never sends because the queue is misconfigured.

## What it covers

System testing is broader than "does the feature work":

- **Functional.** Complete workflows such as signup, login, purchase and refund.
- **Non-functional.** Response times under expected load, security basics, recovery after a crash, compatibility with browsers or devices.
- **Configuration.** Behaviour with production-like settings, real data volumes and real integrations.

## Example: a workflow test

The following test drives a running staging system through the API from signup to purchase. It needs a real environment, so it is not a unit test.

```python title="test_system_purchase.py" showLineNumbers{1}
import os
import requests

BASE = os.environ["STAGING_URL"]


def test_signup_login_purchase():
    s = requests.Session()
    email = "qa+system@example.com"

    r = s.post(f"{BASE}/api/signup", json={"email": email, "password": "S3cret!pw"}, timeout=10)
    assert r.status_code == 201

    r = s.post(f"{BASE}/api/login", json={"email": email, "password": "S3cret!pw"}, timeout=10)
    assert r.status_code == 200

    r = s.post(f"{BASE}/api/orders", json={"sku": "BOOK-1", "qty": 1}, timeout=10)
    assert r.status_code == 201
    assert r.json()["status"] == "confirmed"
```

## Practical rules

- Keep test data isolated and cleaned up, or use a fresh account per run.
- Make the environment as close to production as you can afford. A test on a different database version proves little.
- Cover requirements, not screens. Trace each test to a requirement, as the V-Model does.
- Test failure paths too: payment declined, service down, invalid role.

## What goes wrong

System tests are slow and expensive, so teams write too many of them and end up with an inverted pyramid. Failures are hard to diagnose, because many components are involved. Shared staging environments produce failures caused by other people's changes. Keep them for the flows that matter, and rely on unit and integration tests for detail. The next level up, UAT, asks whether the business accepts the result.
