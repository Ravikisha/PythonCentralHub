Any tree question containing the words **"level"**, **"depth"**,
**"row"**, **"nearest"**, or **"width"** is a breadth-first traversal in
disguise. DFS visits a whole branch before its siblings, so it never has a
level assembled in one place; BFS processes the tree in **horizontal
layers**, which is exactly the shape those questions ask about.

There is one template. Once you can write it without thinking, roughly a
dozen Medium problems become five-minute problems.

## What you'll learn

- The **level-snapshot** trick -- the single line that turns a flat queue
  into "one iteration per level".
- Why `collections.deque` and not a list (and what it costs if you get it
  wrong).
- The five mutations of the template that cover the whole level-order
  family.
- **Four real LeetCode problems** solved here in the browser: 102, 199,
  103, and 111.

## The cue

:::tip[You are looking at tree BFS when…]
The problem asks for something **per level**, or about **distance from the
root**:

- "level order", "each row", "each level" -- 102, 107, 515, 637
- "right/left side view", "leftmost value in the last row" -- 199, 513
- "minimum depth", "shortest path to a leaf" -- 111
- "maximum width", "are these nodes cousins" -- 662, 993
- "connect each node to its right neighbour" -- 116, 117

**Prefer DFS instead** when the question is about a **root-to-leaf path**,
a subtree property, or anything needing values returned *up* from
children (path sums, diameter, validation). Those are the
[Tree DFS](../tree-dfs-paths-and-sums/) pattern.
:::

:::note[Why minimum depth is BFS but maximum depth is DFS]
For **minimum** depth, BFS can stop the instant it meets the first leaf --
no other leaf can be shallower, because BFS visits in non-decreasing depth
order. That is an early exit worth real time on a wide, shallow tree.

For **maximum** depth every node must be visited either way, so the simple
recursion `1 + max(left, right)` wins on clarity. Knowing *why* the two
mirror-image problems want different traversals is a genuine
discriminator in interviews.
:::

## The template

```python title="tree_bfs_template.py" showLineNumbers{1}
from collections import deque


def level_order(root):
    if not root:                       # always handle the empty tree first
        return []

    result = []
    queue = deque([root])

    while queue:
        level_width = len(queue)       # <-- THE snapshot: freeze this level's size
        level = []

        for _ in range(level_width):   # consume exactly this level
            node = queue.popleft()
            level.append(node.val)

            if node.left:              # children form the NEXT level
                queue.append(node.left)
            if node.right:
                queue.append(node.right)

        result.append(level)

    return result
```

Everything in the level-order family is this template with one of the
inner lines changed.

:::caution[The snapshot line is the whole pattern]
`level_width = len(queue)` **must** be read before the inner loop starts.
The loop appends children to the same queue, so `len(queue)` is changing
as you iterate. Writing `for _ in range(len(queue))` inline still works
in Python -- `range()` evaluates its argument once -- but
`while queue: node = queue.popleft()` **without** the snapshot silently
flattens every level into one, and that is the single most common bug in
this pattern.
:::

## How it works

Level by level, the queue holds exactly one complete level at the top of
each `while` iteration. The inner `for` drains that level and, in the
process, enqueues the entire next level behind it.

## Dry run

Same tree, written out the way you should write it on a whiteboard:

| Outer iteration | Queue at snapshot | `level_width` | Level emitted |
| --- | --- | --- | --- |
| 1 | `[3]` | 1 | `[3]` |
| 2 | `[9, 20]` | 2 | `[9, 20]` |
| 3 | `[15, 7]` | 2 | `[15, 7]` |
| 4 | `[]` | -- | loop ends |

Now the failure mode, so you recognise it instantly. Suppose the inner loop
reads `len(queue)` live instead of snapshotting it:

| Outer iteration | Queue | `range(len(queue))` re-read each step | Level emitted |
| --- | --- | --- | --- |
| 1 | `[3]` | grows to 2 as 9 and 20 are enqueued | `[3, 9, 20]` ← wrong |

One level bleeds into the next, and the output is a single flat list rather
than a list of levels. If your LC 102 submission returns `[[3,9,20,15,7]]`,
this is why.

## Time and space complexity

| | Time | Space |
| --- | --- | --- |
| Level-order BFS | $O(n)$ -- every node enqueued and dequeued once | $O(w)$ where $w$ is the **maximum level width** |

For a balanced tree the widest level holds about $n/2$ nodes, so space is
$O(n)$. For a degenerate "linked list" tree the queue never holds more
than one node, so space is $O(1)$ -- the exact opposite of DFS recursion,
which is $O(\log n)$ on a balanced tree and $O(n)$ on a degenerate one.

:::caution[Use deque, not a list]
`list.pop(0)` is $O(n)$ because every remaining element shifts left. Using
a list as a queue turns this $O(n)$ traversal into $O(n^2)$ -- fine on the
samples, TLE on the real tests. `collections.deque.popleft()` is $O(1)$.
:::

## The variant map

| Variant | What changes in the template | Canonical problem |
| --- | --- | --- |
| **Collect every level** | The template verbatim | 102 Binary Tree Level Order Traversal |
| **One value per level** | Keep only the last (or first, max, mean) node of each level | 199 Right Side View · 515 Largest Value · 637 Average |
| **Alternate direction** | Build the level in a `deque` and `appendleft` on odd levels | 103 Zigzag Level Order |
| **Early exit** | `return` mid-traversal on the first node meeting a condition | 111 Minimum Depth |
| **Carry extra state per node** | Enqueue `(node, depth)` or `(node, index)` tuples instead of bare nodes | 662 Maximum Width · 993 Cousins |

The "one value per level" variant is worth watching, because the trick is
smaller than people expect — there is no geometry involved at all:

:::note[Reverse the output instead of reversing the traversal]
For "bottom-up level order" (LC 107), do **not** try to traverse upwards.
Run the normal template and `return result[::-1]`. Same for zigzag: build
each level normally and flip alternate ones. Reversing at the end is
always cheaper and clearer than fighting the traversal order.
:::

<details>
<summary>Editorial — approach, complexity, follow-ups</summary>

Push the root, then repeat: read how many nodes are in the queue (that is
one full level), pop exactly that many, record their values, and enqueue
their children.

**Time** $O(n)$ -- each node is enqueued once and dequeued once.
**Space** $O(w)$ for the queue, where `w` is the widest level.

The empty-tree guard is not optional: `[]` must return `[]`, and without
the guard `deque([None])` would enqueue a `None` and crash on
`node.val`.

**Follow-ups you should expect:** "Bottom-up (LC 107)?" -- `return
out[::-1]`. "Can you do it with DFS?" -- yes: recurse with a `depth`
argument and append to `out[depth]`, creating the list when
`depth == len(out)`. It is $O(n)$ too, and worth mentioning as it shows
you understand the traversals are interchangeable here; BFS is just the
natural fit. "What about an N-ary tree (LC 429)?" -- replace the two
`if node.left / node.right` lines with `for child in node.children`.

The visible node on each level is simply its **last** node in left-to-right
order. So run the level template and record only the node at index

construction; the greedy spine walk is not.

<details>
<summary>Editorial — approach, complexity, follow-ups</summary>

The traversal never changes. Only the *assembly* of each level flips: for
right-to-left levels, prepend each value instead of appending.

Using a `deque` for the level makes prepending $O(1)$, so the whole thing
stays $O(n)$. Building a list and calling `level.insert(0, val)` is
$O(\text{level width})$ per insert and makes the level assembly
$O(w^2)$ -- a legitimate thing for an interviewer to poke at.

`level.append(...)` then `level.reverse()` on alternate levels is equally
$O(n)$ overall and just as acceptable. What is *not* acceptable is trying
to enqueue children in a different order to "naturally" produce zigzag --
the direction flips every level, so child ordering cannot express it.

**Time** $O(n)$. **Space** $O(w)$.

**Follow-ups you should expect:** "Spiral starting right-to-left?" --
initialise the flag to `False`. "Vertical order traversal (LC 314)?" --
different pattern: enqueue `(node, column)` and bucket by column.

</details>

<summary>Editorial — approach, complexity, follow-ups</summary>

BFS dequeues nodes in non-decreasing depth order, so the first leaf it
meets is a shallowest leaf. Return immediately -- no need to finish the
traversal.

**Time** $O(n)$ worst case, but only $O(\text{nodes above the shallowest

`1 + min(minDepth(left), minDepth(right))` is **wrong**. For
`[1, 2]` -- a root with only a left child -- the missing right subtree
returns `0`, giving `1`, but the only leaf is at depth `2`. A node with
exactly one child is *not* a leaf, so a recursive solution must special-case
it: if one side is missing, return `1 + minDepth(other side)`. This is
the most-failed detail on LC 111, and the second test case
(`[2,null,3,null,4,null,5,null,6]`, a right-leaning chain) is there to
catch exactly that.
:::

**Follow-ups you should expect:** "Maximum depth (LC 104)?" -- switch to
DFS, `1 + max(left, right)`; there is no early exit to win so recursion is
clearer. "Why not DFS here?" -- the early exit; say it explicitly. "What
if the tree is enormous and wide?" -- BFS memory is $O(w)$ which can be
huge; an iterative-deepening DFS trades time for $O(\text{depth})$ space.

</details>

## Interview follow-ups

| They ask | What they're checking | The answer |
| --- | --- | --- |
| "BFS or DFS here, and why?" | Whether you choose deliberately | Per-level or nearest-thing means BFS; path/subtree/return-value-upward means DFS |
| "What's the space complexity?" | Precision | $O(w)$ = widest level, which is $O(n)$ balanced and $O(1)$ degenerate -- the mirror image of DFS recursion |
| "Why deque and not a list?" | Python fluency | `list.pop(0)` is $O(n)$ and makes the traversal $O(n^2)$; `deque.popleft()` is $O(1)$ |
| "Can you do 116 in $O(1)$ space?" | Whether you can drop the queue | Yes -- once a level is linked, walk it via `next` pointers to link the level below; no queue needed |
| "Do it recursively" | Flexibility | Pass `depth` down and index into `out[depth]`, appending a new list when `depth == len(out)` |
| "The tree has a billion nodes" | Practical limits | BFS holds a whole level in memory; if `w` is too large, iterative-deepening DFS trades time for $O(\text{depth})$ space |

## Edge-case checklist

- **Empty tree** (`root is None`) -- must return `[]` / `0`, and must not
  enqueue `None`.
- **Single node** -- one level, and it is also a leaf. LC 111 must return
  `1`.
- **One-child nodes** -- the killer for LC 111: a node with one child is
  *not* a leaf.
- **Completely one-sided tree** (`[1,null,2,null,3]`) -- every level has
  width 1; verifies your snapshot logic doesn't assume two children.
- **Duplicate values** -- never identify nodes by `val`; use the node
  objects themselves.
- **Negative values** -- don't initialise a per-level max to `0`; use the
  first element or `float("-inf")`.
- **Very wide tree** -- mention the $O(w)$ queue memory before the
  interviewer does.

## Recall card

- **Cue** — the words *level, row, depth, nearest, width*, or "connect each
  node to its right neighbour".
- **Invariant** — at the top of each outer iteration, the queue holds exactly
  one complete level.
- **Template** — `deque`, `while queue:`, snapshot `n = len(queue)`, inner
  `for _ in range(n)` that pops one node and pushes its children.
- **Complexity** — $O(n)$ time, $O(w)$ space (widest level). Mirror image of
  DFS's $O(h)$.
- **Choose DFS instead when** — the answer is a root-to-leaf path, a subtree
  property, or anything returned *up* from children. Minimum depth is BFS;
  maximum depth is DFS.

## Recap

- Tree BFS = a `deque`, plus **one snapshot line** (`level_width =
  len(queue)`) that turns a flat queue into per-level iteration.
- The whole level-order family is that template with one inner line
  changed: keep all values, keep one value, flip the assembly order,
  exit early, or carry extra state per node.
- **BFS for "per level" and "nearest"; DFS for paths and subtree
  properties.** Minimum depth is BFS (early exit); maximum depth is DFS.
- $O(n)$ time, $O(w)$ space -- and `deque.popleft()`, never `list.pop(0)`.
- To reverse or zigzag, change the **assembly**, never the traversal.
