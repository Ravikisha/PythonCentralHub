A [sliding window](../sliding-window/) can maintain a **sum** in $O(1)$ per
step, because adding and removing are both reversible arithmetic. A
**maximum** is not: when the current maximum slides out of the window, you
have no idea what the new maximum is, and rescanning the window costs
$O(k)$ -- back to $O(n \cdot k)$ overall.

The fix is a **monotonic deque**: a double-ended queue holding *indices*
whose values are kept sorted. The window's maximum is then always at the
front, readable in $O(1)$, and the whole scan stays $O(n)$ because each
index is pushed once and popped once.

## What you'll learn

- Why a heap is the *wrong* tool here, and what a deque gives you instead.
- The "pop from the back while smaller, pop from the front when expired"
  template.
- The amortised argument that makes an inner `while` loop still $O(n)$.
- **Three real LeetCode problems** solved in the browser: 239, 1696, 1438.

## The cue

:::tip[You are looking at a monotonic deque when…]
- You need the **max or min of a sliding window**, not its sum -- 239.
- You need "the best `dp` value within the last `k` positions" as a DP
  transition -- 1696 and the whole *windowed DP* family.
- You need **both** the window max and min at once, usually to test a
  spread against a limit -- 1438, 2762.
- A sum-based window would work, except **negative numbers** broke the
  monotonic-sum assumption -- 862.

The tell is that the quantity you need is an **extremum over a moving
range**, and the element achieving it can leave the range.
:::

:::note[Why not a heap?]
A max-heap gives you the maximum in $O(1)$ and inserts in $O(\log k)$ --
but it cannot *remove an arbitrary element* when it slides out of the
window. The usual workaround, "lazy deletion", means leaving stale entries
in and discarding them when they surface, which needs `(value, index)`
pairs and gives $O(n \log n)$.

A deque beats it to $O(n)$ by exploiting something a heap ignores: if
`nums[j] >= nums[i]` and `j > i`, then **`i` can never again be the
maximum** -- `j` is both bigger and outlives it. So `i` can be discarded
permanently, not lazily. That single observation is the pattern.
:::

## The template

```python title="monotonic_deque_template.py" showLineNumbers{1}
from collections import deque


def sliding_window_maximum(nums, k):
    dq = deque()          # holds INDICES; their values are strictly decreasing
    out = []

    for i, x in enumerate(nums):
        # 1. maintain monotonicity: anything smaller than x is now useless
        while dq and nums[dq[-1]] <= x:
            dq.pop()
        dq.append(i)

        # 2. evict the front if it has slid out of the window
        if dq[0] <= i - k:
            dq.popleft()

        # 3. the front is the window's maximum
        if i >= k - 1:
            out.append(nums[dq[0]])

    return out


print(sliding_window_maximum([1, 3, -1, -3, 5, 3, 6, 7], 3))   # [3, 3, 5, 5, 6, 7]
```

Three moves, always in this order: **pop the back** to restore
monotonicity, **pop the front** to drop expired indices, **read the front**
for the answer.

:::caution[Store indices, not values]
The deque must hold **indices**. Values alone cannot tell you whether the
front has expired -- you need `dq[0] <= i - k`, and two equal values are
indistinguishable. Storing values is the most common way this pattern
silently breaks.
:::

## Why it is O(n) despite the inner while

Each index is `append`ed exactly once and `pop`ped at most once, so the
total number of deque operations across the entire run is at most $2n$.
The inner `while` can run many times on one iteration, but only by
consuming pushes that already happened -- it can never run more times in
total than there were pushes.

| | Time | Space |
| --- | --- | --- |
| Rescan the window each step | $O(n \cdot k)$ | $O(1)$ |
| Max-heap with lazy deletion | $O(n \log n)$ | $O(n)$ |
| **Monotonic deque** | $O(n)$ | $O(k)$ |

## Complexity

| Approach | Time | Space |
| --- | --- | --- |
| Recompute `max()` per window | $O(n \cdot k)$ | $O(1)$ |
| Max-heap with lazy deletion | $O(n \log k)$ | $O(n)$ |
| **Monotonic deque** | $O(n)$ | $O(k)$ |

Each index is appended exactly once and removed exactly once across the whole
run, so the total deque work is at most $2n$ — the same amortised argument as
the monotonic stack. The heap solution is worth mentioning as the more obvious
answer before giving the deque, since it shows you know why $O(n)$ is possible.

## The variant map

| Variant | What changes | Canonical problem |
| --- | --- | --- |
| **Window maximum** | Pop back while `value <= x`; decreasing deque | 239 Sliding Window Maximum |
| **Window minimum** | Pop back while `value >= x`; increasing deque | 1438 (paired with a max deque) |
| **Both at once** | Run two deques side by side over the same window | 1438 · 2762 |
| **Windowed DP** | The deque holds indices into `dp`, not `nums` | 1696 Jump Game VI |

<details>
<summary>Editorial — approach, complexity, follow-ups</summary>

The invariant: the deque holds indices in increasing order, whose values
are **strictly decreasing**. Consequently `dq[0]` is always the index of
the window's maximum.

When a new value `x` arrives, every index at the back whose value is
`<= x` is permanently useless: `x` is at least as large *and* stays in the
window longer. Pop them. Then evict the front if it has aged out.

**Time** $O(n)$ amortised. **Space** $O(k)$.

Why `<=` and not `<`: with `<`, equal values pile up in the deque. That is
still *correct* (the front remains a maximum) but wastes space. Using
`<=` keeps the deque minimal. Either passes; be ready to justify yours.

**Follow-ups you should expect:** "Window minimum?" -- flip the comparison
to `>=`. "Why not a heap?" -- see the note above: a heap cannot evict an
arbitrary expired element, so it degrades to $O(n \log n)$. "Can you do
$O(1)$ space?" -- no; you provably need to remember up to `k` candidates.

</details>

class Solution:
    def maxResult(self, nums, k):
        n = len(nums)
        dp = [0] * n
        dp[0] = nums[0]
        dq = deque([0])                   # indices into dp, dp values decreasing
        for i in range(1, n):
            while dq and dq[0] < i - k:   # out of jump range
                dq.popleft()
            dp[i] = nums[i] + dp[dq[0]]   # best reachable predecessor
            while dq and dp[dq[-1]] <= dp[i]:
                dq.pop()
            dq.append(i)
        return dp[-1]

<details>
<summary>Editorial — approach, complexity, follow-ups</summary>

The DP is immediate: `dp[i] = nums[i] + max(dp[i-k] … dp[i-1])`, with
`dp[0] = nums[0]`. Evaluated naively that is $O(n \cdot k)$, which TLEs at
$n = k = 10^5$.

The inner `max` is a maximum over a sliding window of `dp` -- so it is
LC 239 embedded in a DP recurrence. The deque holds indices into `dp`,
front = best reachable predecessor.

**Time** $O(n)$. **Space** $O(n)$ for `dp`, $O(k)$ for the deque.

Order matters here in a way it does not in 239: **evict the expired front
first**, then read `dp[dq[0]]`, then push `i`. Pushing before reading
would let `i` be its own predecessor.

This "max over the last `k` states" shape is worth memorising -- it turns
up in constrained-jump, stock-cooldown, and bounded-knapsack problems, and
a deque removes the `k` factor every time.

**Follow-ups you should expect:** "Greedy instead?" -- no, greedy fails
because a locally poor landing can be the only route to a large later
value. "Can you drop the `dp` array?" -- you only need the last `k`
entries, so a ring buffer of size `k` gives $O(k)$ space.

</details>

class Solution:
    def longestSubarray(self, nums, limit):
        max_dq, min_dq = deque(), deque()      # indices; decreasing / increasing
        left = best = 0
        for right, x in enumerate(nums):
            while max_dq and nums[max_dq[-1]] <= x:
                max_dq.pop()
            max_dq.append(right)
            while min_dq and nums[min_dq[-1]] >= x:
                min_dq.pop()
            min_dq.append(right)

            while nums[max_dq[0]] - nums[min_dq[0]] > limit:
                if max_dq[0] == left:          # only evict if left IS the extremum
                    max_dq.popleft()
                if min_dq[0] == left:
                    min_dq.popleft()
                left += 1

            best = max(best, right - left + 1)
        return best


sol = Solution()

<details>
<summary>Editorial — approach, complexity, follow-ups</summary>

This is a longest-valid sliding window whose validity test is
`window_max - window_min <= limit`. Neither extremum is maintainable by
arithmetic, so keep one deque for each.

**Time** $O(n)$. **Space** $O(n)$ worst case for the two deques.

:::caution[Evict the front only when it equals `left`]
Inside the shrink loop, `max_dq.popleft()` must be guarded by
`if max_dq[0] == left`. The element leaving the window is `nums[left]`,
and it might not be the current extremum -- if it is not, its index is not
at the deque front and popping would discard a *live* candidate. Writing
an unconditional `popleft()` here is the classic bug, and it produces
answers that are too large on inputs like `[4,2,2,2,4,4,2,2]`.
:::

A `sortedcontainers.SortedList` also solves this in $O(n \log n)$ and is
a fine thing to mention -- but it is not in the standard library, so it is
unavailable in many interview environments.

**Follow-ups you should expect:** "Return the subarray?" -- track
`best_left` when `best` updates. "What if `limit` were on the *sum*
instead?" -- back to an ordinary prefix-sum window. "Count all valid
subarrays rather than the longest?" -- add `right - left + 1` per step
(that is LC 2762).

</details>

from the front while `prefix[i] - prefix[front] >= k` (recording the

the honest answer to the classic follow-up, and it is pure monotonic
deque.

## Dry run

`nums = [1, 3, -1, -3, 5, 3, 6, 7]`, `k = 3`. Deque holds **indices**; values
in brackets.

| `i` | `v` | front evicted | back evicted | deque after | output |
| --- | --- | --- | --- | --- | --- |
| 0 | 1 | — | — | `[0(1)]` | — |
| 1 | 3 | — | `0(1)` | `[1(3)]` | — |
| 2 | −1 | — | — | `[1(3), 2(-1)]` | **3** |
| 3 | −3 | — | — | `[1, 2, 3(-3)]` | **3** |
| 4 | 5 | `1(3)` out of range | `3(-3)`, `2(-1)` | `[4(5)]` | **5** |
| 5 | 3 | — | — | `[4(5), 5(3)]` | **5** |
| 6 | 6 | — | `5(3)`, `4(5)` | `[6(6)]` | **6** |
| 7 | 7 | — | `6(6)` | `[7(7)]` | **7** |

Output `[3, 3, 5, 5, 6, 7]`.

Step 4 is the one to study: **both** rules fire in the same iteration. Index 1
leaves from the front because the window has moved past it, and indices 2 and 3
leave from the back because 5 outclasses them. Those are independent
mechanisms — conflating them into one condition is the usual way this goes wrong.

:::caution[Why the deque holds indices and not values]
The front-eviction test is `dq[0] <= i - k` — a *position* comparison. Store
values and there is no way to know whether the front has slid out of the window.
This is the same reason the monotonic stack stores indices.
:::

| "Window minimum too?" | Whether the template generalises | Flip the comparison; run both deques together if you need max and min |

## Edge-case checklist

- **`k = 1`** -- every window is one element; output equals the input.
- **`k = len(nums)`** -- one window; the answer is a single global max.
- **All equal values** -- exercises the `<=` vs `<` choice; both work but
  only `<=` keeps the deque small.
- **Strictly increasing input** -- the deque never exceeds length 1.
- **Strictly decreasing input** -- the deque grows to `k`; this is the
  space worst case.
- **Negative values only** -- do not initialise a running best to `0`.
- **`limit = 0`** (1438) -- valid; only runs of identical values qualify.
- **Front eviction guard** (1438) -- pop the front *only* when its index
  equals `left`.

## Recall card

- **Cue** — the **maximum or minimum of a sliding window**, or any window
  aggregate that cannot be undone by subtraction (max and min cannot; a sum can,
  which is why a plain sliding window handles sums).
- **Invariant** — indices in the deque, values decreasing front to back. The
  **front is always the window's answer**.
- **Two evictions** — back: while the back's value ≤ the incoming value. Front:
  if `dq[0] <= i - k`.
- **Complexity** — $O(n)$ amortised, $O(k)$ space.
- **Remember** — store **indices**; the two eviction rules are independent;
  start recording output at `i >= k - 1`.
- **Alternative to name** — a max-heap with lazy deletion gives
  $O(n \log k)$; mention it, then give the deque.

## Recap

- A sliding window handles sums by arithmetic, but an **extremum** needs a
  monotonic deque: indices in, values sorted, extremum at the front.
- Three moves in order: **pop the back** while dominated, **pop the front**
  when expired, **read the front**.
- **Store indices, never values** -- expiry is positional.
- $O(n)$ amortised: each index is pushed once and popped once, so the
  inner `while` cannot exceed the total number of pushes.
- The pattern generalises past arrays: over `dp` it removes the `k` from
  windowed-DP transitions (1696), and over prefix sums it rescues
  sum-windows from negative numbers (862).
