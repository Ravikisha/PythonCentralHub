[Sliding window](../sliding-window/) fails the moment an array can contain
**negative numbers**: growing the window no longer grows the sum, so
"shrink while too big" stops making sense. It also fails when a problem
asks you to **count** subarrays rather than find the best one.

The pattern that handles both is prefix sums plus a hash map. It rests on
one identity:

$$\text{sum}(i..j) = \text{prefix}[j] - \text{prefix}[i-1]$$

Rearranged, a subarray ending at `j` sums to `k` exactly when some earlier
prefix equals $\text{prefix}[j] - k$. So instead of searching for
subarrays, you count **prefix values you have already seen** -- one pass,
one dict, $O(n)$.

## What you'll learn

- The prefix-sum identity, and the rearrangement that turns it into a
  lookup.
- Why the map must be seeded with `{0: 1}`, and what breaks without it.
- Counting **occurrences** vs. remembering the **earliest index** -- the
  two flavours, and which each problem needs.
- The remainder and balance transforms that make this pattern cover far
  more than plain sums.
- **Three real LeetCode problems** solved in the browser: 560, 974, 525.

## The cue

:::tip[You are looking at prefix sums + a hash map when…]
- **"How many subarrays"** have some sum property -- 560, 974, 930, 1248.
- The array can contain **negatives or zeros** and a window would be
  wrong -- 560 vs 209.
- The condition is about a **sum being divisible by k**, or a **remainder**
  -- 974, 523.
- The condition is a **balance** -- equal counts of two things, which
  becomes "sum is zero" after mapping one to `+1` and the other to `-1` --
  525, 1ND-style problems.
- The array is a **tree path** rather than a line -- 437 is this exact
  pattern with backtracking.
:::

:::caution[Window or prefix sums? The decision that matters]
Both patterns answer questions about contiguous subarrays. Pick with two
questions:

| | Sliding window | Prefix sums + map |
| --- | --- | --- |
| Values may be negative | **No** -- invariant breaks | **Yes** |
| Asks for longest/shortest | Yes | Possible, but awkward |
| Asks for a **count** | Rarely | **Yes** |
| Space | $O(1)$ | $O(n)$ |

"Minimum size subarray sum ≥ target, positive values" is a window (LC 209).
"Count subarrays summing to exactly k, any values" is prefix sums
(LC 560). Reaching for a window on LC 560 is the single most common
wrong turn in this area.
:::

## The template

Two flavours. Which one you need depends on whether the answer is a
**count** or a **length**.

```python title="prefix_sum_hashmap_template.py" showLineNumbers{1}
# FLAVOUR 1 -- COUNT subarrays. Map: prefix value -> how many times seen.
def count_subarrays_with_sum(nums, k):
    seen = {0: 1}          # one empty prefix, so subarrays starting at index 0 count
    running = 0
    count = 0
    for x in nums:
        running += x
        count += seen.get(running - k, 0)      # every earlier match is a subarray
        seen[running] = seen.get(running, 0) + 1
    return count


# FLAVOUR 2 -- LONGEST subarray. Map: prefix value -> EARLIEST index seen.
def longest_subarray_with_sum(nums, k):
    first = {0: -1}        # empty prefix sits "before" index 0
    running = 0
    best = 0
    for i, x in enumerate(nums):
        running += x
        if running - k in first:
            best = max(best, i - first[running - k])
        if running not in first:               # only record the FIRST occurrence
            first[running] = i
    return best


print(count_subarrays_with_sum([1, 1, 1], 2))          # 2
print(longest_subarray_with_sum([1, -1, 5, -2, 3], 3))  # 4
```

:::caution[The two details everything hinges on]
**1. Seed the map.** `{0: 1}` (count) or `{0: -1}` (index). Without it, a
subarray that starts at index `0` is never counted -- its prefix *is* the
target, and there is no earlier prefix of `0` to subtract. Missing this
gives answers that are off by exactly the number of valid prefixes.

**2. For "longest", keep only the earliest index.** Overwriting with later
indices shrinks every candidate. Guard with `if running not in first`.
For "count", you do the opposite -- increment every time.
:::

## How it works

Take `nums = [3, 4, 7, 2, -3, 1, 4, 2]`, `k = 7`:

| `i` | `nums[i]` | `running` | `running - k` | seen before? | count |
| --- | --- | --- | --- | --- | --- |
| 0 | 3 | 3 | -4 | no | 0 |
| 1 | 4 | 7 | 0 | **yes** (seed) | 1 |
| 2 | 7 | 14 | 7 | **yes** | 2 |
| 3 | 2 | 16 | 9 | no | 2 |
| 4 | -3 | 13 | 6 | no | 2 |
| 5 | 1 | 14 | 7 | **yes** | 3 |
| 6 | 4 | 18 | 11 | no | 3 |
| 7 | 2 | 20 | 13 | **yes** | 4 |

Four subarrays: `[3,4]`, `[7]`, `[7,2,-3,1]`, `[1,4,2]`. Notice the seed
firing at `i = 1` -- that is the subarray starting at index `0`, and it is
exactly what a missing `{0: 1}` would lose.

| | Time | Space |
| --- | --- | --- |
| Brute force over all subarrays | $O(n^2)$ | $O(1)$ |
| **Prefix sums + hash map** | $O(n)$ | $O(n)$ |

## Complexity

| Approach | Time | Space |
| --- | --- | --- |
| Every subarray, summed from scratch | $O(n^3)$ | $O(1)$ |
| Every subarray, running sum | $O(n^2)$ | $O(1)$ |
| **Prefix sum + hash map** | $O(n)$ | $O(n)$ |

The $O(n)$ space is unavoidable here and worth naming: the map can hold $n$
distinct prefix sums. That is the trade this pattern makes — memory for a factor
of $n$ in time — and it is the answer to "can you do it in $O(1)$ space?"
(you cannot, in general).

## The variant map

The power of this pattern is that you can **transform** the array first,
turning an unrelated-looking condition into "sum equals a target".

| Variant | The transform | Canonical problem |
| --- | --- | --- |
| **Sum equals k** | None | 560 Subarray Sum Equals K |
| **Sum divisible by k** | Key on `running % k` instead of `running` | 974 · 523 |
| **Equal count of two symbols** | Map one to `+1`, the other to `-1`; look for sum `0` | 525 Contiguous Array |
| **Exactly k odd numbers** | Map odd to `1`, even to `0`; look for sum `k` | 1248 Nice Subarrays |
| **Count on a tree path** | Same map, but **undo** the entry when leaving the node | 437 Path Sum III |
| **2D submatrix sums** | Fix a row pair, collapse columns to 1D, apply the template | 1074 |

:::note[The "equal counts" transform is worth internalising]
"Longest subarray with equal numbers of 0s and 1s" looks nothing like a
sum problem. Map `0 -> -1` and `1 -> +1`; now equal counts means the
mapped values **sum to zero**, and the whole problem is
`longest_subarray_with_sum(mapped, 0)`. The same trick handles equal
counts of any two categories, and generalises to three-plus categories by
keying the map on a *tuple* of pairwise differences.
:::

<details>
<summary>Editorial — approach, complexity, follow-ups</summary>

A subarray ending at the current index sums to `k` exactly when some
earlier prefix equals `running - k`. So the number of such subarrays is
the number of times `running - k` has been seen -- which is what the map
stores.

**Time** $O(n)$. **Space** $O(n)$.

:::caution[Count before you record]
`count += seen.get(running - k, 0)` must come **before**
`seen[running] += 1`. When `k == 0`, `running - k == running`, so
recording first would let the current prefix match itself and count a
zero-length subarray. Test case `[1,-1,0], k = 0` (expected `3`) exists to
catch this ordering.
:::

Note the answer counts subarrays, so equal prefix values must be *tallied*,
not overwritten -- `[1,-1,0]` reaches prefix `0` three times and each
pairing is a distinct valid subarray.

**Follow-ups you should expect:** "Longest such subarray instead?" --
switch to flavour 2, storing earliest indices. "All values positive?" --
then a sliding window works and gives $O(1)$ space; say so, it shows you
know the trade. "Do it on a binary tree?" -- LC 437: same map, but
decrement the entry as you unwind so only the current root-to-node path is
in scope.

**Problem.** Return the number of contiguous subarrays whose sum is
divisible by `k`.

**Constraints.** `1 <= len(nums) <= 3 * 10^4`,
`-10^4 <= nums[i] <= 10^4`, `2 <= k <= 10^4`.

**Examples.** `nums = [4,5,0,-2,-3,1], k = 5` gives `7` ·
`nums = [5], k = 9` gives `0` · `nums = [-1,2,9], k = 2` gives `2`

<details>
<summary>Editorial — approach, complexity, follow-ups</summary>

$\text{sum}(i..j)$ is divisible by `k` exactly when
$\text{prefix}[j] \equiv \text{prefix}[i-1] \pmod{k}$. So instead of
looking up `running - k`, look up `running` itself -- among prefixes
already reduced mod `k`.

**Time** $O(n)$. **Space** $O(k)$ -- only `k` distinct remainders exist,
which is tighter than the $O(n)$ of LC 560.

:::note[A place Python is quietly kinder than C++ or Java]
For negative operands, Python's `%` returns a result with the sign of the
**divisor**, so `-3 % 5 == 2`. In C++ and Java, `-3 % 5 == -3`, and the
same code needs `((x % k) + k) % k` to normalise. Test case `[-1,2,9]`
exercises exactly this. Worth saying out loud -- it shows you know the
language semantics rather than having memorised a snippet.
:::

**Follow-ups you should expect:** "Is there a subarray of length ≥ 2 whose
sum is divisible by `k`?" -- LC 523, same idea plus an index check for the
length constraint. "Why is space $O(k)$ not $O(n)$?" -- because remainders
live in `[0, k)`, so a `k`-slot list beats a dict here.

</details>

### LC 525 -- Contiguous Array · Medium

**Problem.** Given a binary array `nums`, return the length of the longest
contiguous subarray with an **equal number of `0`s and `1`s**.

**Constraints.** `1 <= len(nums) <= 10^5`, `nums[i]` is `0` or `1`.

**Examples.** `nums = [0,1]` gives `2` · `nums = [0,1,0]` gives `2` ·
`nums = [0,1,1,1,1,1,0,0,0]` gives `6` · `nums = [1,1,1]` gives `0`

  code={`class Solution:
    def findMaxLength(self, nums):

        # whose mapped sum is 0. Store the EARLIEST index per balance.

sol = Solution()

    def findMaxLength(self, nums):

        best = 0
        for i, x in enumerate(nums):
            running += 1 if x == 1 else -1     # the +1 / -1 transform
            if running in first:
                best = max(best, i - first[running])
            else:
                first[running] = i             # record first occurrence only
        return best

<details>
<summary>Editorial — approach, complexity, follow-ups</summary>

Map `0 -> -1` and `1 -> +1`. A subarray has equal counts exactly when its
mapped sum is `0`, i.e. when two prefixes share the same running balance.
The longest such subarray for a given balance spans from its **earliest**
occurrence to the current index.

**Time** $O(n)$. **Space** $O(n)$.

:::caution[Earliest index, and the `{0: -1}` seed]
Two details, both worth a test case:

- **Never overwrite** an existing balance. `first[running] = i` must be
  guarded by `else` / `if running not in first`, otherwise you always
  measure from the most recent occurrence and report a shorter answer.
- **Seed `{0: -1}`, not `{0: 0}`.** The empty prefix sits *before* index
  `0`, so a balanced subarray starting at index `0` has length
  `i - (-1) = i + 1`. Seeding with `0` would report one less. On `[0,1]`
  that is the difference between the correct `2` and a wrong `1`.
:::

`[1,1,1]` returning `0` is the "no valid subarray" case -- the balance
never repeats, so `best` stays at its initial `0`.

**Follow-ups you should expect:** "Equal counts of three symbols?" -- key
the map on a tuple of differences, e.g. `(count_a - count_b, count_b -
count_c)`. "Return the subarray itself?" -- also store the index where
`best` was set. "Equal counts of *any* two values in a non-binary array?"
-- same idea, one map per pair of interest.

</details>

## Dry run

LC 560 with `k = 3`, `nums = [1, 2, 3, -3, 1, 1, 1]`. The `want` column is the
whole idea: a subarray ending here sums to `k` exactly when some earlier prefix
equals `running − k`.

| `i` | `v` | `running` | `want = running − k` | seen count | `count` | map after |
| --- | --- | --- | --- | --- | --- | --- |
| — | — | 0 | — | — | 0 | `{0: 1}` |
| 0 | 1 | 1 | −2 | 0 | 0 | `{0:1, 1:1}` |
| 1 | 2 | 3 | **0** | **1** | **1** | `{0:1, 1:1, 3:1}` |
| 2 | 3 | 6 | **3** | **1** | **2** | `{0:1, 1:1, 3:1, 6:1}` |
| 3 | −3 | 3 | 0 | 1 | **3** | `{0:1, 1:1, 3:2, 6:1}` |
| 4 | 1 | 4 | 1 | 1 | **4** | `{0:1, 1:1, 3:2, 4:1, 6:1}` |
| 5 | 1 | 5 | 2 | 0 | 4 | `… 5:1` |
| 6 | 1 | 6 | **3** | **2** | **6** | `… 6:2` |

Answer: 6 subarrays.

Three things that table makes concrete:

- **The `{0: 1}` sentinel earns its keep at `i = 1`.** The subarray `[1, 2]`
  starts at index 0, so the "earlier prefix" it needs is the *empty* prefix. Omit
  the sentinel and every subarray starting at index 0 is missed — the single most
  common bug in this pattern.
- **At `i = 3` the running sum returns to 3, a value already seen.** That is only
  possible because of the negative number, and it is exactly why the map counts
  occurrences rather than storing a boolean.
- **At `i = 6`, `want = 3` has been seen twice, so the count jumps by 2.** Using
  a set instead of a counter would add 1 and silently undercount.

:::caution[Order matters: look up before you insert]
`count += seen[running - k]` must happen **before** `seen[running] += 1`. With
`k = 0` the two are the same key, and inserting first counts the current prefix
against itself — producing a phantom empty subarray at every index.
:::

## Interview follow-ups

| They ask | What they're checking | The answer |
| --- | --- | --- |
| "Why not a sliding window?" | Whether you know each pattern's limits | Negative values break the window's monotonic sum; and windows find extremes, not counts |
| "Why seed with `{0: 1}`?" | Whether you derived it or copied it | It represents the empty prefix, so subarrays starting at index `0` are counted |
| "Count vs. earliest index?" | Whether you match the map to the question | Counting a total means tally every occurrence; measuring a length means keep only the first |
| "What if all values are positive?" | Trade-off awareness | A window then works and needs $O(1)$ space instead of $O(n)$ |
| "Space is $O(n)$ -- can you do better?" | Precision | For the divisibility variant, yes: $O(k)$, since only `k` remainders exist |
| "Extend to 2D" | Composition | Fix a pair of rows, collapse each column into a running sum, and run the 1D template -- $O(rows^2 \cdot cols)$ |

## Edge-case checklist

- **`k = 0`** -- forces the count-before-record ordering; `[1,-1,0]` is the
  test.
- **Negative numbers** -- the entire reason for this pattern; make sure
  nothing in your solution assumes monotonicity.
- **Zeros in the array** -- create repeated prefix values and therefore
  extra valid subarrays; they must be tallied, not deduplicated.
- **Whole array is the answer** -- verifies the seed entry works.
- **No valid subarray** -- must return `0`, not `-1` or `float("inf")`.
- **Single element** -- `[5], k = 5` gives `1`; `[5], k = 9` gives `0`.
- **Overflow** -- irrelevant in Python (arbitrary-precision ints), but
  worth naming if the interviewer thinks in C++ or Java.
- **Earliest-index guard** (length variants) -- never overwrite a balance
  already in the map.

## Recall card

- **Cue** — count or measure **contiguous** subarrays with a target sum, **and**
  negatives are possible (which rules out a sliding window).
- **Key identity** — `sum(i..j) == running[j] − running[i-1]`. So a subarray
  ending at `j` sums to `k` exactly when some earlier prefix equals
  `running[j] − k`.
- **Template** — `seen = {0: 1}`; per element: `running += v`;
  `count += seen.get(running - k, 0)`; then `seen[running] += 1`.
- **Complexity** — $O(n)$ time, $O(n)$ space. The space is unavoidable.
- **Remember** — the `{0: 1}` sentinel; **count** occurrences, do not use a set;
  look up **before** inserting.
- **Variants** — longest instead of count (store the *first* index); divisible by
  k (key on `running % k`); equal 0s and 1s (map 0 → −1 and look for sum 0).

## Recap

- $\text{sum}(i..j) = \text{prefix}[j] - \text{prefix}[i-1]$, rearranged
  into a lookup: a subarray ending here hits the target when
  `running - k` has been seen before.
- **Two flavours:** count occurrences (`{0: 1}`) for "how many", earliest
  index (`{0: -1}`) for "how long".
- **Seed the map**, and for length variants **never overwrite** an
  existing key.
- **Count before recording** so `k = 0` cannot match a zero-length
  subarray.
- **Transform first, then apply the template**: `% k` for divisibility,
  `+1/-1` for equal counts, `odd/even` for parity counts. That is what
  makes one small template cover a dozen problems.
- Choose this over a window whenever values can be negative, or the
  question asks for a **count**.
