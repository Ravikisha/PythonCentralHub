## What you'll learn

- Why `list.append` is amortized $O(1)$ thanks to geometric over-allocation.
- The real complexity of index, append, insert, and pop at different positions.
- The **two-pointer** technique for in-place array work.
- **Prefix sums** for O(1) range-sum queries after one O(n) pre-pass.
- LeetCode-style problems to drill the pattern.

## The cue

:::tip[Reach for an array when…]
- Access is **by position** and you need it in $O(1)$.
- You iterate far more often than you insert or delete in the middle.
- **Cache locality matters** — a contiguous block is dramatically faster to scan
  than a linked structure, and that constant factor is often the whole reason a
  solution passes.

**Reach for something else** when you insert or delete at the front repeatedly
(`collections.deque`, $O(1)$ at both ends versus $O(n)$ for `list.pop(0)`), when
lookup is by key rather than position (a `dict`), or when you need the smallest
element repeatedly (`heapq`).
:::

## Fixed array vs dynamic array

A **fixed-size array** (like a C array) reserves one contiguous block of
memory for exactly `n` elements, decided up front. Growing it means
allocating a whole new block and copying everything over — there's no
"just add one more".

A **dynamic array** hides that pain behind a friendly `append`. Python's
built-in `list` *is* a dynamic array: contiguous storage under the hood, but
it **over-allocates** — when it runs out of room it grabs a bigger block
(roughly 1.125x the old capacity once the list is large) and copies the
existing pointers across, once. Because that expensive copy happens less and
less often as the list grows, the **average** cost per `append` stays
$O(1)$ — this is called **amortized** analysis.

```python title="array_growth.py" showLineNumbers{1}
import sys

arr = []
prev_capacity_hint = sys.getsizeof(arr)
growths = 0

for i in range(25):
    arr.append(i)
    size = sys.getsizeof(arr)
    if size != prev_capacity_hint:
        growths += 1
        print(f"n={i + 1:<3} underlying buffer resized (event #{growths})")
        prev_capacity_hint = size

print(f"\n25 appends, only {growths} real reallocations — the rest were free.")
```

Notice the buffer only resizes a handful of times across 25 appends, not
once per element. Each resize is $O(n)$, but it happens on a shrinking
fraction of the appends, so the *total* cost for `n` appends is $O(n)$,
which averages out to $O(1)$ **per** append.

## Watch a dynamic array double

When the backing block fills up, CPython allocates a bigger one and copies
every existing element across before the new item is written in:

```p5 title="Dynamic array growth on append" desc="The array starts with room for 4 items. Once full, a new, bigger block is allocated and every old element is copied across (shown in amber) before the new element (green) is added." height="300"
let capacity = 4;
let count = 0;
let phase = "filling"; // "filling" | "copying" | "grown"
let copyIndex = 0;
let pauseTimer = 0;

function setup() {
  createCanvas(600, 300);
  textFont("monospace");
}

function draw() {
  background(13, 17, 23);

  if (pauseTimer > 0) {
    pauseTimer--;
  } else if (phase === "filling") {
    if (count < capacity) {
      count++;
      if (count === capacity) {
        phase = "copying";
        copyIndex = 0;
      }
      pauseTimer = 25;
    }
  } else if (phase === "copying") {
    if (copyIndex < capacity) {
      copyIndex++;
      pauseTimer = 8;
    } else {
      capacity *= 2;
      phase = "filling";
      pauseTimer = 25;
      if (capacity > 32) {
        capacity = 4;
        count = 0;
      }
    }
  }

  const boxW = 40, boxH = 40, gap = 6;
  const startX = 30, rowY = 120;

  noStroke();
  fill(200);
  textSize(13);
  textAlign(LEFT, CENTER);
  text(`capacity = ${capacity}    count = ${Math.min(count, capacity)}`, startX, 40);

  for (let i = 0; i < capacity; i++) {
    const x = startX + i * (boxW + gap);
    const filled = i < count;
    const beingCopied = phase === "copying" && i < copyIndex;
    if (phase === "copying") {
      fill(beingCopied ? color(219, 171, 90) : color(60, 66, 74));
    } else {
      fill(filled ? color(75, 139, 190) : color(40, 46, 54));
    }
    rect(x, rowY, boxW, boxH, 6);
    if (filled || beingCopied) {
      fill(20);
      textAlign(CENTER, CENTER);
      text(i, x + boxW / 2, rowY + boxH / 2);
      textAlign(LEFT, CENTER);
    }
  }

  noStroke();
  fill(140);
  textSize(11);
  const msg = phase === "copying"
    ? "buffer full -> allocating a bigger block, copying every old element (O(n), rare)"
    : "appending into pre-reserved space (O(1), common)";
  text(msg, startX, rowY + boxH + 30);
}
```

## Complexity of common list operations

| Operation | Example | Complexity |
| --- | --- | --- |
| Index / update | `arr[i]`, `arr[i] = x` | $O(1)$ |
| Append (end) | `arr.append(x)` | $O(1)$ amortized |
| Pop (end) | `arr.pop()` | $O(1)$ amortized |
| Insert at front/middle | `arr.insert(0, x)` | $O(n)$ |
| Pop from front/middle | `arr.pop(0)` | $O(n)$ |
| Search / membership | `x in arr` | $O(n)$ |
| Length | `len(arr)` | $O(1)$ |

:::tip[Rule of thumb]
Anything at the **end** of a Python list is cheap. Anything at the **front**
or **middle** forces every element after it to shift — that's the hidden
$O(n)$ that turns an innocent-looking loop into $O(n^2)$.
:::

## Two pointers

The two-pointer technique uses two indices moving through the array —
usually from both ends inward, or both from the same side at different
speeds — to solve problems in one pass instead of a nested loop.

```python title="two_pointers.py" showLineNumbers{1}
def reverse_in_place(arr):
    left, right = 0, len(arr) - 1
    while left < right:
        arr[left], arr[right] = arr[right], arr[left]
        left += 1
        right -= 1
    return arr


def is_palindrome_array(arr):
    left, right = 0, len(arr) - 1
    while left < right:
        if arr[left] != arr[right]:
            return False
        left += 1
        right -= 1
    return True


print(reverse_in_place([1, 2, 3, 4, 5]))
print(is_palindrome_array([1, 2, 3, 2, 1]))
print(is_palindrome_array([1, 2, 3]))
```

Both functions do a single $O(n)$ pass with $O(1)$ extra space — no
temporary copy of the array needed.

## Prefix sums

If you need the sum of many *sub-ranges* of the same array, don't re-sum
each range from scratch (that's $O(n)$ per query). Precompute a **prefix
sum** array once, then answer every range-sum query in $O(1)$.

```python title="prefix_sums.py" showLineNumbers{1}
def build_prefix(arr):
    prefix = [0] * (len(arr) + 1)
    for i, x in enumerate(arr):
        prefix[i + 1] = prefix[i] + x
    return prefix


def range_sum(prefix, left, right):
    # inclusive sum of arr[left..right], O(1) after the O(n) pre-pass
    return prefix[right + 1] - prefix[left]


nums = [2, 4, 6, 8, 10, 12]
prefix = build_prefix(nums)

print("sum(1..3):", range_sum(prefix, 1, 3))   # 4 + 6 + 8
print("sum(0..5):", range_sum(prefix, 0, 5))   # whole array
```

$$
\text{prefix}[i] = \sum_{k=0}^{i-1} \text{arr}[k]
\quad\Rightarrow\quad
\text{sum}(l, r) = \text{prefix}[r+1] - \text{prefix}[l].
$$

One $O(n)$ pass builds the prefix array; every query after that is $O(1)$.

**Constraints.** `1 <= len(nums) <= 10^4`,

<details>
<summary>Editorial</summary>

`write` marks where the next non-zero belongs. Every non-zero found is swapped
into that slot, which simultaneously pushes whatever was there -- necessarily a
zero, or the element itself -- to the read position.

**Time** $O(n)$. **Space** $O(1)$.

Swapping matters. Assigning `nums[write] = nums[read]` would also compact the
non-zeros, but you would then need a second loop to zero out the tail. The swap
does both jobs in one pass.

This is the same **read/write pointer** idea behind LC 26 and LC 27 -- a
same-direction two-pointer scan rather than the converging kind.

**Follow-ups:** "Minimise writes?" -- assign only when `read != write`, skipping
no-op swaps. "Move zeroes to the front?" -- scan from the right. "Remove all
instances of a value (LC 27)?" -- identical structure.

## Dry run

**Amortised growth.** CPython over-allocates on `append`, so most appends are
$O(1)$ and an occasional one copies everything:

| appends | capacity | copy? | cost |
| --- | --- | --- | --- |
| 1 | 4 | allocate | 1 |
| 2–4 | 4 | no | 1 each |
| 5 | 8 | copy 4 | 5 |
| 6–8 | 8 | no | 1 each |
| 9 | 16 | copy 8 | 9 |
| 10–16 | 16 | no | 1 each |

Total for 16 appends: 16 cheap steps plus 4 + 8 = 12 copies, so about 28
operations. Because capacity **multiplies** rather than adding a constant, the
copies form a geometric series that sums to $O(n)$ overall — hence $O(1)$
amortised per append. Grow by a fixed amount instead and the same argument gives
$O(n^2)$ total, which is the point of the question.

:::caution[list.pop(0) is O(n), and it is the most common accidental quadratic]
Removing the front element shifts every remaining element left. Inside a loop
that turns an $O(n)$ traversal into $O(n^2)$ — fine on the samples, TLE on the
real tests. Use `collections.deque` and `popleft()` whenever you consume from the
front.
:::

## The variant map

| Need | Structure | Front insert/remove | Access by index |
| --- | --- | --- | --- |
| Indexed sequence, append-heavy | `list` | $O(n)$ | $O(1)$ |
| Queue or sliding window | `collections.deque` | $O(1)$ | $O(n)$ |
| Fixed-size numeric buffer | `array.array` | $O(n)$ | $O(1)$ |
| Sorted, with binary search | `list` + `bisect` | $O(n)$ insert | $O(1)$ |
| Lookup by key | `dict` | — | — |

Two Python specifics worth knowing: slicing **copies**, so `arr[1:]` inside a
loop is a hidden $O(n^2)$; and `list.insert(0, x)` has the same problem as
`pop(0)`.

## Pitfalls

- **`pop(0)` or `insert(0, x)` in a loop.** $O(n)$ each, so $O(n^2)$ overall.
  Use a `deque`.
- **Slicing in a loop.** `arr[i:]` allocates a copy every iteration. Pass indices
  instead of slices, especially in recursion.
- **`[[0] * n] * m` for a 2-D grid.** That creates `m` references to the *same*
  row, so writing one cell writes a whole column. Use a comprehension:
  `[[0] * n for _ in range(m)]`.
- **Mutating a list while iterating it.** Skips elements silently. Iterate a copy,
  or build a new list.
- **Assuming `in` is fast.** `x in list` is $O(n)$; `x in set` is $O(1)$. This is
  the most common accidental quadratic after `pop(0)`.

## Interview follow-ups

| They ask | What they're checking | The answer |
| --- | --- | --- |
| "Why is `append` $O(1)$ if it sometimes reallocates?" | Amortised reasoning | Capacity multiplies rather than increments, so the copies form a geometric series summing to $O(n)$ across $n$ appends |
| "What if it grew by a fixed 10 slots?" | Whether you understand *why* | Copies become an arithmetic series, so total work is $O(n^2)$ — the multiplication is load-bearing |
| "Why not always use a linked list for insertions?" | Practical judgement | $O(1)$ insertion requires already holding the node. Finding the position is $O(n)$, and cache locality makes the array faster in practice for most sizes |
| "Delete from the middle in $O(1)$" | Whether you know the trick | If order does not matter, swap the target with the last element and pop. This is the idea behind LC 380 Insert Delete GetRandom |
| "How would you rotate by k in $O(1)$ space?" | In-place reasoning | Three reversals: whole array, first `k`, then the rest. Or a cyclic-replacement walk using `gcd(n, k)` cycles |

## Recall card

- **Use when** — access by position, iteration-heavy, cache locality matters.
- **Costs** — index $O(1)$; append $O(1)$ amortised; insert/delete at the front
  or middle $O(n)$; `in` $O(n)$.
- **Amortised argument** — capacity *multiplies*, so copies form a geometric
  series summing to $O(n)$.
- **Python traps** — `pop(0)` and `insert(0, x)` are $O(n)$; slicing copies;
  `[[0]*n]*m` shares rows; `x in list` is $O(n)$.
- **Swap-with-last** deletes in $O(1)$ when order does not matter.

## Recap

- Python's `list` is a dynamic array: contiguous storage that over-allocates
  so `append` is amortized $O(1)$.
- End operations are cheap ($O(1)$); front/middle operations are expensive
  ($O(n)$) because everything after them has to shift.
- Two pointers solve many array problems in one $O(n)$ pass with $O(1)$
  extra space.
- Prefix sums trade one $O(n)$ pre-pass for $O(1)$ range-sum queries
  afterward.
