Complexity is the one thing you're expected to know **cold**, without
looking it up mid-interview or mid-contest. This page is the single-place
reference: every operation, data structure, and algorithm from this track,
with its time and space complexity side by side. Treat it as a lookup
table, not a lesson -- if a row doesn't make sense, the phase that taught it
is linked from context in earlier pages.

## What you'll learn

- The real complexity of every common `list` / `dict` / `set` / `deque` /
  `heapq` operation -- including the ones that silently cost $O(n)$.
- Every sorting and searching algorithm from Phase 4, side by side.
- Every data structure's core operations, from arrays to segment trees,
  Fenwick trees, and DSU.
- The graph algorithm family -- BFS, DFS, Dijkstra, Bellman-Ford,
  Floyd-Warshall, MST, and topological sort.
- The Big-O growth hierarchy, and a rule of thumb for how large `n` can be
  under a typical time limit.

## Common Python operations

| Operation | `list` | `dict` | `set` | `deque` | `heapq` |
| --- | --- | --- | --- | --- | --- |
| Index / key access `x[i]` | $O(1)$ | $O(1)$ avg | -- | $O(n)$ | -- |
| Append / add | $O(1)$ amortized | $O(1)$ avg | $O(1)$ avg | $O(1)$ | $O(\log n)$ (`heappush`) |
| Append/insert at front | $O(n)$ | -- | -- | $O(1)$ | -- |
| Pop from end | $O(1)$ | -- | -- | $O(1)$ | -- |
| Pop from front | $O(n)$ | -- | -- | $O(1)$ | $O(\log n)$ (`heappop`, smallest only) |
| Insert / delete at arbitrary index | $O(n)$ | $O(1)$ avg (`del d[k]`) | $O(1)$ avg | $O(n)$ | not supported directly |
| Membership test `x in ...` | $O(n)$ | $O(1)$ avg | $O(1)$ avg | $O(n)$ | $O(n)$ |
| Search for min/max | $O(n)$ | $O(n)$ | $O(n)$ | $O(n)$ | $O(1)$ (min only, `heap[0]`) |
| Sort (`sorted(...)`, `.sort()`) | $O(n \log n)$ | $O(n \log n)$ on items | $O(n \log n)$ on items | $O(n \log n)$ | $O(n \log n)$ (heapify + drain) |
| `sorted(list)` from scratch | -- | -- | -- | -- | Building via `heapify` is $O(n)$ |

:::caution[The two `list` gotchas everyone hits]
`list.insert(0, x)` and `list.pop(0)` both shift every remaining element
down one slot -- $O(n)$, not $O(1)$. If you need fast operations at both
ends, reach for `collections.deque` instead; it's $O(1)$ at both ends by
design.
:::

## Sorting algorithms

| Algorithm | Best | Average | Worst | Space | Stable? | Notes |
| --- | --- | --- | --- | --- | --- | --- |
| Timsort (Python's `sorted`/`.sort()`) | $O(n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n)$ | Yes | Adaptive -- exploits existing runs of order |
| Merge Sort | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(n)$ | Yes | Guaranteed $O(n \log n)$, no worst-case cliff |
| Quick Sort | $O(n \log n)$ | $O(n \log n)$ | $O(n^2)$ | $O(\log n)$ | No | Worst case needs an adversarial/sorted input plus a bad pivot rule |
| Heap Sort | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ | $O(1)$ | No | In-place, but poor cache locality in practice |
| Insertion Sort | $O(n)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | Yes | Best-in-class for nearly-sorted or tiny arrays |
| Selection Sort | $O(n^2)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | No | Always $O(n^2)$ comparisons, minimal writes |
| Bubble Sort | $O(n)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | Yes | Teaching tool only -- never the right production choice |
| Counting Sort | $O(n + k)$ | $O(n + k)$ | $O(n + k)$ | $O(n + k)$ | Yes | `k` = range of key values; useless when `k` >> `n` |
| Radix Sort | $O(d(n + k))$ | $O(d(n + k))$ | $O(d(n + k))$ | $O(n + k)$ | Yes | `d` = number of digits/passes |
| Bucket Sort | $O(n + k)$ | $O(n + k)$ | $O(n^2)$ | $O(n)$ | Yes (with a stable inner sort) | Needs a roughly-uniform input distribution |

## Searching

| Technique | Time | Space | Requires |
| --- | --- | --- | --- |
| Linear search | $O(n)$ | $O(1)$ | Nothing |
| Binary search (exact match) | $O(\log n)$ | $O(1)$ | Sorted array |
| `lower_bound` / `upper_bound` (`bisect`) | $O(\log n)$ | $O(1)$ | Sorted array |
| Binary search on the answer | $O(f(n) \log(\text{range}))$ | Depends on `feasible()` | Monotonic feasibility |
| Hash-based lookup (`dict`/`set`) | $O(1)$ average, $O(n)$ worst | $O(n)$ | Hashable keys |
| Two pointers / sliding window | $O(n)$ | $O(1)$ | Sorted or monotonic structure |

## Core data structures

| Structure | Access | Search | Insert | Delete | Space | Notes |
| --- | --- | --- | --- | --- | --- | --- |
| Array / Python `list` | $O(1)$ | $O(n)$ | $O(n)$ worst (end: $O(1)$ amortized) | $O(n)$ | $O(n)$ | Contiguous, cache-friendly |
| Singly/doubly linked list | $O(n)$ | $O(n)$ | $O(1)$ at a known node | $O(1)$ at a known node | $O(n)$ | No random access; cheap splicing |
| Stack (`list` as stack) | $O(n)$ | $O(n)$ | $O(1)$ (`append`) | $O(1)$ (`pop`) | $O(n)$ | LIFO -- both ops at the same end |
| Queue (`collections.deque`) | $O(n)$ | $O(n)$ | $O(1)$ (`append`) | $O(1)$ (`popleft`) | $O(n)$ | FIFO -- never use `list.pop(0)` here |
| Hash table (`dict`/`set`) | -- | $O(1)$ avg, $O(n)$ worst | $O(1)$ avg | $O(1)$ avg | $O(n)$ | Worst case needs adversarial hash collisions |
| Binary heap (`heapq`) | $O(1)$ (min only) | $O(n)$ | $O(\log n)$ | $O(\log n)$ (min) | $O(n)$ | `heapify` builds from scratch in $O(n)$ |
| Binary Search Tree (unbalanced) | $O(n)$ worst | $O(n)$ worst | $O(n)$ worst | $O(n)$ worst | $O(n)$ | Degenerates to a linked list on sorted input |
| Balanced BST (AVL / Red-Black) | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | $O(n)$ | Guarantees hold even on adversarial input |
| Trie | $O(L)$ | $O(L)$ | $O(L)$ | $O(L)$ | $O(\text{total chars})$ | `L` = length of the key/word |
| Segment Tree | $O(\log n)$ query/update | -- | $O(\log n)$ update | -- | $O(n)$ | $O(n)$ build; lazy propagation keeps range updates $O(\log n)$ |
| Fenwick Tree (BIT) | $O(\log n)$ query | -- | $O(\log n)$ update | -- | $O(n)$ | Simpler and faster in practice than a segment tree for prefix sums |
| Disjoint Set Union (DSU) | -- | $O(\alpha(n))$ `find` | $O(\alpha(n))$ `union` | -- | $O(n)$ | With path compression + union by rank/size; $\alpha$ is the inverse Ackermann function -- effectively constant |

## Graph algorithms

| Algorithm | Time | Space | Answers |
| --- | --- | --- | --- |
| BFS | $O(V + E)$ | $O(V)$ | Shortest path in an unweighted graph, level order, multi-source distance |
| DFS | $O(V + E)$ | $O(V)$ | Reachability, cycle detection, topological order, connected components |
| Topological sort (Kahn's or DFS-based) | $O(V + E)$ | $O(V)$ | A valid linear order of a DAG |
| Dijkstra (binary heap) | $O((V + E) \log V)$ | $O(V)$ | Shortest path, non-negative weights only |
| Bellman-Ford | $O(V \cdot E)$ | $O(V)$ | Shortest path with negative weights; also detects negative cycles |
| Floyd-Warshall | $O(V^3)$ | $O(V^2)$ | All-pairs shortest paths, works with negative weights (no negative cycles) |
| Prim's MST (binary heap) | $O(E \log V)$ | $O(V)$ | Minimum spanning tree, dense-ish graphs |
| Kruskal's MST (with DSU) | $O(E \log E)$ | $O(V)$ | Minimum spanning tree, sparse graphs / edge lists |

:::note[Picking a shortest-path algorithm]
Unweighted -> BFS. Non-negative weights -> Dijkstra. Negative weights (no
negative cycle) -> Bellman-Ford. Need every pair's distance on a small
graph -> Floyd-Warshall. Reach for the cheapest algorithm that satisfies
your graph's actual constraints -- Floyd-Warshall's $O(V^3)$ becomes
infeasible well before Dijkstra's $O((V + E) \log V)$ does.
:::

## The Big-O growth hierarchy

From fastest-growing-*slowly* to fastest-growing-*explosively*:

$$
O(1) < O(\log n) < O(\sqrt{n}) < O(n) < O(n \log n) < O(n^2) < O(n^3) < O(2^n) < O(n!)
$$

| Complexity | Name | Feels like |
| --- | --- | --- |
| $O(1)$ | Constant | A dict lookup, an array index |
| $O(\log n)$ | Logarithmic | Binary search, balanced BST operations |
| $O(\sqrt{n})$ | Root | Trial-division primality check, sparse tables' build-adjacent factor |
| $O(n)$ | Linear | A single pass -- linear search, array sum |
| $O(n \log n)$ | Linearithmic | Comparison-based sorting, most divide-and-conquer |
| $O(n^2)$ | Quadratic | Nested loops over the same input -- naive pair comparisons |
| $O(n^3)$ | Cubic | Triple-nested loops -- Floyd-Warshall, naive matrix multiply |
| $O(2^n)$ | Exponential | Enumerating every subset, unmemoized exponential recursion |
| $O(n!)$ | Factorial | Enumerating every permutation |

The dashed line is the 10^8 budget from the table above. What matters is not the slope of any curve but where it crosses that line -- that crossing IS the maximum n the complexity can handle. Every crossing is solved on the fly by bisection, not read from a table." height="440"
const KINDS = [
  { name: "log n",   f: (n) => Math.max(1, Math.log2(n)),     tone: [140, 210, 160] },
  { name: "n",       f: (n) => n,                             tone: [88, 166, 255] },
  { name: "n log n", f: (n) => n * Math.max(1, Math.log2(n)), tone: [120, 200, 220] },
  { name: "n^2",     f: (n) => n * n,                         tone: [219, 171, 90] },
  { name: "n^3",     f: (n) => n * n * n,                     tone: [230, 140, 90] },
  { name: "2^n",     f: (n) => Math.pow(2, n),                tone: [255, 123, 114] },
  { name: "n!",      f: fact,                                 tone: [220, 110, 190] },
];

function fact(n) {
  let acc = 1;
  for (let i = 2; i <= n; i++) { acc *= i; if (acc > 1e300) return Infinity; }
  return acc;
}

const BUDGET = 1e8;
// bisect for the largest n whose cost still fits the budget
function maxN(f) {
  let lo = 1, hi = 1e9;
  while (hi - lo > 1) {
    const mid = Math.floor((lo + hi) / 2);
    if (f(mid) <= BUDGET) lo = mid; else hi = mid;
  }
  return lo;
}

let limits = [];
let hi = 0;
let last = 0;

function setup() {
  createCanvas(620, 440);
  textFont("monospace");
  for (let i = 0; i < KINDS.length; i++) limits.push(maxN(KINDS[i].f));
}

const PX = 60, PY = 40, PW = 400, PH = 300;
const LOGN_MAX = 9;    // n up to 10^9
const LOGY_MAX = 18;   // ops up to 10^18

function sx(logn) { return PX + (logn / LOGN_MAX) * PW; }
function sy(logy) { return PY + PH - (Math.min(logy, LOGY_MAX) / LOGY_MAX) * PH; }

function commas(v) {
  const s = String(Math.round(v));
  let out = "";
  for (let i = 0; i < s.length; i++) {
    if (i > 0 && (s.length - i) % 3 === 0) out += ",";
    out += s[i];
  }
  return out;
}

function draw() {
  background(13, 17, 23);
  if (millis() - last > 1700) { last = millis(); hi = (hi + 1) % KINDS.length; }

  noStroke();
  fill(200);
  textSize(12);
  textAlign(LEFT, TOP);
  text("operations vs n, both log scale", 20, 12);

  // grid
  for (let g = 0; g <= LOGN_MAX; g += 1) {
    stroke(28, 34, 41);
    line(sx(g), PY, sx(g), PY + PH);
  }
  for (let g = 0; g <= LOGY_MAX; g += 3) {
    stroke(28, 34, 41);
    line(PX, sy(g), PX + PW, sy(g));
    noStroke();
    fill(70, 78, 90);
    textSize(9);
    textAlign(RIGHT, CENTER);
    text("1e" + g, PX - 6, sy(g));
    stroke(28, 34, 41);
  }
  noStroke();
  for (let g = 0; g <= LOGN_MAX; g += 3) {
    fill(70, 78, 90);
    textSize(9);
    textAlign(CENTER, TOP);
    text("1e" + g, sx(g), PY + PH + 6);
  }

  // the budget line
  stroke(255, 123, 114);
  drawingContext.setLineDash([5, 4]);
  line(PX, sy(8), PX + PW, sy(8));
  drawingContext.setLineDash([]);
  noStroke();
  fill(255, 123, 114);
  textSize(9);
  textAlign(LEFT, BOTTOM);
  text("1e8 budget -- about one second", PX + 4, sy(8) - 3);

  // the curves
  for (let k = 0; k < KINDS.length; k++) {
    const K = KINDS[k];
    const on = k === hi;
    stroke(K.tone[0], K.tone[1], K.tone[2], on ? 255 : 90);
    strokeWeight(on ? 2.5 : 1.2);
    noFill();
    beginShape();
    for (let step = 0; step <= 180; step++) {
      const logn = (step / 180) * LOGN_MAX;
      const n = Math.pow(10, logn);
      const v = K.f(n);
      if (!isFinite(v) || v <= 0) break;
      const logy = Math.log10(v);
      if (logy > LOGY_MAX) { vertex(sx(logn), sy(LOGY_MAX)); break; }
      vertex(sx(logn), sy(logy));
    }
    endShape();
    strokeWeight(1);

    // mark the crossing
    const lim = limits[k];
    // Bisection tops out at 999,999,999, so test against 9e8 rather than 1e9.
    if (lim <= 9e8) {
      const cx = sx(Math.log10(lim));
      noStroke();
      fill(K.tone[0], K.tone[1], K.tone[2], on ? 255 : 110);
      circle(cx, sy(8), on ? 9 : 5);
    }
  }
  noStroke();

  // legend / limits table
  const lx = 476;
  fill(200);
  textSize(11);
  textAlign(LEFT, TOP);
  text("largest n that fits", lx, 12);
  for (let k = 0; k < KINDS.length; k++) {
    const y = 36 + k * 40;
    const on = k === hi;
    fill(on ? color(32, 38, 46) : color(20, 25, 31));
    rect(lx, y, 128, 34, 4);
    fill(KINDS[k].tone[0], KINDS[k].tone[1], KINDS[k].tone[2], on ? 255 : 120);
    rect(lx, y, 3, 34, 2, 0, 0, 2);
    fill(on ? 210 : 110);
    textSize(11);
    textAlign(LEFT, TOP);
    text(KINDS[k].name, lx + 10, y + 4);
    fill(KINDS[k].tone[0], KINDS[k].tone[1], KINDS[k].tone[2], on ? 255 : 110);
    textSize(10);
    text(limits[k] > 9e8 ? "1e9 and up" : commas(limits[k]), lx + 10, y + 19);
  }

  // the punchline for the highlighted curve
  const K = KINDS[hi];
  fill(210, 200, 160);
  textSize(11);
  textAlign(LEFT, TOP);
  const lim = limits[hi];
  text(
    "O(" + K.name + "): " +
      (lim > 9e8 ? "n barely matters -- the input size is not the constraint"
                  : "n up to " + commas(lim) + " fits; past that you need a better algorithm"),
    20, PY + PH + 30
  );
  fill(90, 100, 112);
  textSize(10);
  text("Pure-Python loops pay roughly 10x, so 1e7 is the safer working figure.", 20, PY + PH + 52);
  text("Work pushed into C -- sort, sum, set operations, NumPy -- does not pay that tax.", 20, PY + PH + 68);
}

### Max `n` per time limit -- a rule of thumb

Contest judges typically allow roughly $10^8$-$10^9$ simple operations per
second in Python (often with a looser limit than C++ for exactly this
reason). Working backward from a **1-2 second** limit gives a rough ceiling
on `n` for each complexity class:

| Complexity | Comfortable max `n` |
| --- | --- |
| $O(n!)$ | $n \le 10$-ish |
| $O(2^n)$ | $n \le 20$-25 |
| $O(n^3)$ | $n \le 300$-500 |
| $O(n^2)$ | $n \le 5{,}000$-10,000 |
| $O(n \log n)$ | $n \le 10^6$-$10^7$ |
| $O(n)$ | $n \le 10^7$-$10^8$ |
| $O(\log n)$ / $O(1)$ | $n$ up to $10^{18}$ (the input size barely matters) |

:::tip[Read the constraints backward]
Given a time limit and a constraint like $n \le 10^5$, work the table in
reverse: an $O(n^2)$ solution ($10^{10}$ operations) is almost certainly
too slow, while $O(n \log n)$ ($\approx 1.7 \times 10^6$ operations) has
room to spare. Constraints are a hint dropped by the problem setter about
which complexity class they expect -- always check them before writing a
single line of code.
:::

## How to use this cheatsheet

- Treat it as a **lookup**, not reading material -- bookmark it and come
  back mid-problem when you need to double-check a complexity before
  committing to an approach.
- When a problem gives you `n` and a time limit, use the "max `n` per time
  limit" table to shortlist which complexity classes are even in the
  running before you design an algorithm.
- When two data structures both "work," pick the one whose row here has
  the better guarantee for the operation your problem calls the most
  (e.g. a Fenwick tree over a segment tree when you only need prefix sums,
  not range updates).

```p5 title="Read the constraint, name the complexity" desc="The constraint in the problem statement tells you the intended complexity, and this is the arithmetic that turns one into the other. n sweeps upward; for each complexity the bar shows the operation count against the 10^8 budget, and a class flips from green to red the moment it no longer fits. const CLS = [
  { name: "n!",      f: factN },

  for (let i = 2; i <= n; i++) { acc *= i; if (acc > 1e300) return Infinity; }
  return acc;
}

  if (v < 1000) return String(Math.round(v));
  const e = Math.floor(Math.log10(v));
  return (v / Math.pow(10, e)).toFixed(1) + "e" + e;

    // frac == 1.0 means "exactly at the budget". Headroom to 1.25 so an
    // over-budget class visibly overshoots the tick instead of pinning to it.
    const bx = 140, bw = 300, MAXF = 1.25;
    const unit = bw / MAXF;                       // pixels per 1.0 of frac
    const frac = isFinite(v)
      ? Math.min(MAXF, Math.log10(Math.max(v, 1)) / Math.log10(BUDGET))
      : MAXF;
    noStroke();
    fill(28, 34, 41);
    rect(bx, y + 11, bw, 12, 3);
    fill(fits ? color(140, 210, 160) : color(255, 123, 114));
    rect(bx, y + 11, frac * unit, 12, 3);
    stroke(200);
    line(bx + unit, y + 8, bx + unit, y + 26);    // the 1e8 budget itself
    noStroke();

    fill(fits ? color(150) : color(255, 123, 114));
    textSize(11);
    textAlign(LEFT, CENTER);
    text(eng(v), bx + bw + 16, y + 17);

    if (isBest) {
      fill(140, 210, 160);
      textSize(10);
      textAlign(RIGHT, CENTER);
      text("<- aim here", 596, y + 17);
    }
  }

  fill(210, 200, 160);
  textSize(11);
  textAlign(LEFT, TOP);
  if (best >= 0) {
    text("At n <= " + eng(n) + " the most expensive class that still fits is O(" + CLS[best].name + ").", 20, 388);
  } else {
    text("Nothing here fits -- the intended solution is sublinear or closed form.", 20, 388);
  }
  fill(90, 100, 112);
  textSize(10);
  text("the white tick is the 1e8 budget; bars are log-scaled", 20, 404);
}

## Complexity

The one table this whole page exists to support -- **what fits in about one second**, at roughly
$10^8$ simple operations:

| Max `n` | Largest complexity that fits | Typical approach |
| --- | --- | --- |
| &lt;= 12 | $O(n!)$ | permutations, brute-force TSP |
| &lt;= 25 | $O(2^n)$ | subsets, [bitmask DP](../../phase-12-dynamic-programming/bitmask-and-tree-dp/) |
| &lt;= 500 | $O(n^3)$ | Floyd-Warshall, [interval DP](../../phase-12-dynamic-programming/dp-on-grids-and-intervals/) |
| &lt;= 5,000 | $O(n^2)$ | pairwise DP, LCS, edit distance |
| &lt;= 10^5-10^6 | $O(n \log n)$ | sorting, heaps, segment trees, binary search on the answer |
| &lt;= 10^7 | $O(n)$ | one pass, sliding window, prefix sums |
| >= 10^9 | $O(\log n)$ / $O(1)$ | binary search on the answer, closed form, [digit DP](../../phase-12-dynamic-programming/digit-dp/) |

Two adjustments that matter in practice:

- **Python's constant factor is roughly 10-100x C++.** Shift the table down about one order of
  magnitude for pure-Python loops -- $10^7$ simple operations per second is a safer working figure than
  $10^8$. Work pushed into C (`sort`, `sum`, `bytes`, `set` operations, NumPy) does not pay that tax.
- **Read the bound's variable.** "Binary search on the answer" is $O(n \log R)$ where $R$ is the
  *value* range, not `n`; a pseudo-polynomial DP like knapsack is $O(nW)$ in the *capacity*. Quoting
  either as a function of `n` alone is the usual mistake, and it is what makes a solution that looks
  fine time out.

## Interview follow-ups

| They ask | What they're checking | The answer |
| --- | --- | --- |
| "The constraint is `n <= 20`. What does that tell you?" | Reading constraints as hints | That exponential in `n` is expected -- $2^{20}$ is about a million. A bound that small is almost always pointing at a bitmask or a full enumeration |
| "What is the complexity of `list.insert(0, x)`?" | Whether you know the data model | $O(n)$ -- every element shifts. That is why a queue uses `collections.deque`, where both ends are $O(1)$ |
| "`in` on a list versus a set?" | The most common Python performance bug | $O(n)$ versus $O(1)$ average. A membership test inside a loop turns an $O(n)$ algorithm into $O(n^2)$ without changing a line of the logic |
| "Amortised versus worst case?" | Precision | A `list.append` is $O(1)$ amortised and $O(n)$ on the resize that copies. Over `n` appends the total is $O(n)$, so amortised is the honest figure to quote for a loop |
| "Your solution is $O(n \log n)$ but times out" | Diagnosing beyond the class | Either the constant is the problem -- Python-level loops, per-iteration allocation, string concatenation in a loop -- or the bound's variable is not what you assumed. Check both before rewriting the algorithm |
| "Space complexity of your recursion?" | The invisible cost | $O(h)$ stack frames, which is $O(n)$ on a degenerate input and invisible in the source. It is also why CPython's ~1000-frame limit turns some correct solutions into crashes |
| "Sorting is $O(n \log n)$ -- can you ever beat it?" | Knowing the model | Only by leaving the comparison model: counting or radix sort is $O(n + k)$ for small integer keys. The $\Omega(n \log n)$ bound applies to comparison sorts specifically |
| "Which of these bounds do people quote wrongly?" | Judgement | Pseudo-polynomial ones -- knapsack's $O(nW)$ and digit DP's -- because they are polynomial in a *value* rather than an input length. Naive Fibonacci is $O(\phi^n)$, not $O(2^n)$ |

## Recall card

- **The budget** -- about $10^8$ simple operations per second, and **an order of magnitude fewer in pure
  Python**. Do this arithmetic *before* choosing an approach.
- **Constraint to complexity** -- `n <= 12`: $O(n!)$ · `<= 25`: $O(2^n)$ · `<= 500`: $O(n^3)$ ·
  `<= 5000`: $O(n^2)$ · `<= 10^6`: $O(n \log n)$ · `<= 10^7`: $O(n)$ · beyond: $O(\log n)$ or a formula.
- **Python data model** -- `list.insert(0, ...)` and `list.pop(0)` are $O(n)$; `deque` is $O(1)$ at both
  ends. `x in list` is $O(n)$, `x in set` is $O(1)$ -- the most common accidental $O(n^2)$.
- **`append` is $O(1)$ amortised**, $O(n)$ on the resize. Quote the amortised figure for a loop.
- **Recursion costs $O(h)$ space** and dies at ~1000 frames in CPython.
- **Read the bound's variable** -- $O(nW)$ and $O(n \log R)$ are polynomial in a *value*, not a length.
  That is what makes a "fine" solution time out.
- **Beating $O(n \log n)$** requires leaving the comparison model: counting or radix sort.

## Recap

- Python's built-in containers hide real complexity costs -- `list.pop(0)`
  and `list.insert(0, x)` are $O(n)$, not $O(1)$; use `deque` when you need
  fast operations at both ends.
- Timsort's $O(n \log n)$ worst case and $O(n)$ best case (on
  already-sorted runs) is why `sorted()`/`.sort()` is almost always the
  right call over a hand-rolled sort.
- Balanced BSTs, Fenwick trees, and segment trees all trade a bit of extra
  bookkeeping for a **guaranteed** $O(\log n)$ where a naive structure would
  degrade to $O(n)$ on adversarial input.
- Shortest-path algorithm choice is driven entirely by what the graph
  allows: unweighted -> BFS, non-negative weights -> Dijkstra, negative
  weights -> Bellman-Ford, all-pairs on a small graph -> Floyd-Warshall.
- The Big-O hierarchy plus a rough "operations per second" budget is enough
  to sanity-check almost any algorithm choice before you write a line of
  code.
