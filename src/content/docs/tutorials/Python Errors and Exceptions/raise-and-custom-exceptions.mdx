:::note[What each form actually sets — verified]
Wrapping a `ZeroDivisionError` in a `ValueError`:

| Form | `__cause__` | `__context__` |
| --- | --- | --- |
| `raise ValueError(...) from e` | `ZeroDivisionError` | `ZeroDivisionError` |
| `raise ValueError(...)` | `None` | `ZeroDivisionError` |
| `raise ValueError(...) from None` | `None` | **`ZeroDivisionError`** |

The last row is the one worth noticing. `from None` does **not** erase the original — it only
stops the traceback printing it. The exception object is still reachable through
`__context__`, so a logger that walks the chain can still find it.

Which to use: **`from e`** when the original explains the new one — a library error wrapped in
your own type. **Bare `raise`** when the two are unrelated and you want both visible.
**`from None`** only when the original is genuinely noise, such as a lookup you deliberately
tried and expected to fail.
:::

## Why raise exceptions?

You can use `raise` to:

- validate function inputs
- enforce rules
- stop invalid workflows early

```python title="raise_example.py" showLineNumbers{1}
def set_age(age: int) -> int:
    if age < 0:
        raise ValueError("age must be >= 0")
    return age

print(set_age(10))
# print(set_age(-1))
```

## Raise with a custom message

```python title="raise_message.py" showLineNumbers{1}
score = -5
if score < 0:
    raise ValueError(f"score must be non-negative, got {score}")
```

## Creating custom exceptions

Custom exceptions help you represent domain-specific errors.

```python title="custom_exception.py" showLineNumbers{1}
class PaymentError(Exception):
    """Raised when a payment fails."""


def charge(amount: float) -> None:
    if amount <= 0:
        raise PaymentError("Amount must be positive")


try:
    charge(0)
except PaymentError as e:
    print("Payment failed:", e)
```

## Re-raising exceptions

Sometimes you want to log something and re-raise.

```python title="reraise.py" showLineNumbers{1}
try:
    int("abc")
except ValueError as e:
    print("Logging error:", e)
    raise
```

## Best practices

- Don’t leak secrets in error messages.
- Use clear messages: what went wrong + what to do.
- Prefer built-in exception types when they fit.
