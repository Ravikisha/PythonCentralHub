## What you'll learn

- why most ML algorithms need numbers, not text categories
- `OrdinalEncoder` — encoding categories as integers
- the hidden problem `OrdinalEncoder` introduces
- `OneHotEncoder` — encoding categories as binary vectors
- when one-hot encoding stops being practical

## The one text column: ocean_proximity

Everything so far has been numeric except `ocean_proximity`. It holds a limited set
of repeated string values — `<1H OCEAN`, `INLAND`, `NEAR OCEAN`, `NEAR BAY`, `ISLAND` —
which makes it a **categorical** attribute rather than free text. Most ML algorithms
prefer numbers, so this needs converting.

```python title="Isolate the categorical column" showLineNumbers{1}
housing_cat = housing[["ocean_proximity"]]
print(housing_cat.head(10))
```

## OrdinalEncoder: categories to integers

The simplest conversion maps each category to an integer:

```python title="OrdinalEncoder" showLineNumbers{1}
from sklearn.preprocessing import OrdinalEncoder

ordinal_encoder = OrdinalEncoder()
housing_cat_encoded = ordinal_encoder.fit_transform(housing_cat)

print(housing_cat_encoded[:5])
print(ordinal_encoder.categories_)
```

This works, but it introduces an assumption most algorithms make automatically: that
nearby numbers are more *similar*. That's true for genuinely ordered categories
("bad", "average", "good", "excellent"), but `ocean_proximity` isn't ordered — category
`0` (`<1H OCEAN`) and category `4` (`NEAR OCEAN`) aren't inherently "close" just because
`0` and `4` are far apart numerically, and category `0` and `1` aren't inherently
similar just because their integers are adjacent.

## OneHotEncoder: one binary column per category

The standard fix is **one-hot encoding**: create one binary column per category, set
to `1` when a row belongs to that category and `0` otherwise. Only one column is "hot"
(1) per row — the rest are "cold" (0).

```python title="OneHotEncoder" showLineNumbers{1}
from sklearn.preprocessing import OneHotEncoder

cat_encoder = OneHotEncoder()
housing_cat_1hot = cat_encoder.fit_transform(housing_cat)

print(housing_cat_1hot.toarray()[:5])
print(cat_encoder.categories_)
```

By default, `OneHotEncoder` returns a **sparse matrix** — it only stores the location
of non-zero entries instead of every zero, which matters a lot once you have
categorical columns with hundreds or thousands of categories. Call `.toarray()` only
when you actually need a dense NumPy array (e.g., to print or inspect it).

```mermaid title="Ordinal vs. one-hot encoding" desc="Same categorical column, two very different numeric representations."
flowchart LR
  A["ocean_proximity<br/>(text categories)"] --> B["OrdinalEncoder<br/>0, 1, 2, 3, 4"]
  A --> C["OneHotEncoder<br/>one binary column per category"]
  B --> D["Implies false ordering<br/>(0 vs 4 look 'far apart')"]
  C --> E["No false ordering,<br/>more columns"]
```

## When one-hot encoding isn't practical

If a categorical attribute has a huge number of possible values (a country code, a
user ID, a product SKU), one-hot encoding explodes into a huge number of mostly-zero
columns, which can slow down training. In that case, consider:

- replacing the category with a related numeric feature (e.g., country code →
  population and GDP per capita)
- learning a low-dimensional **embedding** per category (common in deep learning —
  each category's representation is learned during training, not fixed up front)

For a handful of categories like `ocean_proximity`, though, plain one-hot encoding is
the right default.

:::tip[From the book]
Géron's example makes the risk concrete: "categories 0 and 4 are clearly more similar
than categories 0 and 1" under ordinal encoding, even though nothing about
`<1H OCEAN` and `NEAR OCEAN` makes them more alike than `<1H OCEAN` and `INLAND`. One-hot
encoding avoids inventing an ordering that doesn't exist in the data.
:::
