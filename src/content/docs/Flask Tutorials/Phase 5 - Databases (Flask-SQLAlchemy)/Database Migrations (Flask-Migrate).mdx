Migrations solve a dangerous problem:

- your models change over time
- your database schema must change too
- you need a safe, repeatable way to apply those changes

Flask-Migrate wraps Alembic to manage migrations.

```mermaid title="why create_all is not migrations" desc="create_all only creates tables that do not exist yet. It will never alter one that does, so the moment you add a column to a model that is already in the database, the two drift apart silently. Flask-Migrate records each change as a versioned script, so the database can be moved forward -- and back -- deliberately."

```

## Install

```bash
pip install Flask-Migrate
```

## Setup

```python
from flask_migrate import Migrate

migrate = Migrate(app, db)
```

## Typical workflow

1) Initialize migrations folder:

```bash
flask db init
```

2) Create a migration script:

```bash
flask db migrate -m "create users table"
```

3) Apply it:

```bash
flask db upgrade
```

## Key idea

- `migrate` generates migration scripts from model diffs
- `upgrade` applies them to the database

## Best practices

- review generated scripts before applying
- commit migrations to git
- run migrations in CI/staging before production

## The problem migrations solve

Suppose your app is live with a `users` table, and you add a `bio` column to the `User` model. If you run the app again, nothing happens to the database. `db.create_all()` only creates tables that are missing, and it never alters one that exists. The first query that touches `bio` fails with a "no such column" error.

You could delete the database and start over, but that destroys real data. You could write `ALTER TABLE` by hand, but then your laptop, your teammate's laptop, and production each need the same change applied in the same order. A migration is that change written down once, as a small versioned script, so everyone applies the same steps.

## A worked example

Start with a working project that has `Migrate(app, db)` set up and a `User` model. Run these once:

```bash
flask db init
flask db migrate -m "create users table"
flask db upgrade
```

`init` makes a `migrations/` folder. `migrate` compares your models with the database and writes a script describing the difference. `upgrade` runs that script. Now add a column to the model:

```python
class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    username = db.Column(db.String(80), unique=True, nullable=False)
    bio = db.Column(db.String(200), nullable=True)   # new
```

Then repeat the last two steps:

```bash
flask db migrate -m "add user bio"
flask db upgrade
```

The database gains the column, existing rows are kept, and a new file in `migrations/versions/` records the change. If it turns out to be a mistake, `flask db downgrade` reverses the last step.

## Read the script before you apply it

Autogenerate is a guess. It can miss a renamed column, treating it as a drop plus an add, which deletes the data in that column. Adding a `nullable=False` column to a table that already has rows also fails unless you give it a default. Open the generated file and check it.

## Common mistakes

- **Running `flask db migrate` and forgetting `upgrade`.** The script exists, but the database is unchanged.
- **Not committing the `migrations/` folder.** Teammates and production cannot reproduce your schema.
- **Editing a migration that others have already applied.** Create a new migration instead.
- **Using `create_all` alongside migrations.** The two disagree about what exists. Pick migrations.
