A **many-to-many** relationship means:

- many A relate to many B

Example:

- a `Post` can have many `Tag`s
- a `Tag` can apply to many `Post`s

## Association table

```python
post_tags = db.Table(
    "post_tags",
    db.Column("post_id", db.Integer, db.ForeignKey("posts.id"), primary_key=True),
    db.Column("tag_id", db.Integer, db.ForeignKey("tags.id"), primary_key=True),
)
```

## Models

```python
class Post(db.Model):
    __tablename__ = "posts"
    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200), nullable=False)

    tags = db.relationship("Tag", secondary=post_tags, back_populates="posts")


class Tag(db.Model):
    __tablename__ = "tags"
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(50), unique=True, nullable=False)

    posts = db.relationship("Post", secondary=post_tags, back_populates="tags")
```

## Using it

```python
post = Post(title="Flask Tips")
tag = Tag(name="flask")
post.tags.append(tag)

db.session.add(post)
db.session.commit()
```

## When you need an association *model*

If the relationship needs extra fields (e.g., `created_at`, `role`), use an association model instead of `db.Table`.

## Why a third table is needed

In a one-to-many relationship you put a foreign key on the "many" side. That trick fails here. A post has many tags, so a single `tag_id` column on `posts` is not enough. A tag belongs to many posts, so a single `post_id` on `tags` is not enough either. The only way to store all the pairings is a separate table with one row per pair: post 1 with tag 3, post 1 with tag 5, post 2 with tag 3, and so on.

That table is the association table. It usually holds nothing but two foreign keys, and the pair together is the primary key, so the same pairing cannot be stored twice. You rarely touch it directly. `relationship(secondary=post_tags)` tells SQLAlchemy to use it behind the scenes, so `post.tags` looks like an ordinary Python list.

## A worked example

Using the models above, add and read tags like this:

```python title="tags_demo.py" showLineNumbers{1}
with app.app_context():
    db.create_all()

    flask_tag = Tag(name="flask")
    python_tag = Tag(name="python")

    post1 = Post(title="Flask Tips", tags=[flask_tag, python_tag])
    post2 = Post(title="Python Tricks", tags=[python_tag])
    db.session.add_all([post1, post2])
    db.session.commit()

    print([t.name for t in post1.tags])       # ['flask', 'python']
    print([p.title for p in python_tag.posts])  # ['Flask Tips', 'Python Tricks']
```

The same `python_tag` object is shared by both posts. SQLAlchemy inserts one row into `tags` and two rows into `post_tags`. Because both sides use `back_populates`, appending a tag to `post.tags` also updates `tag.posts` in memory, so the two views of the data agree.

To remove a link, use `post1.tags.remove(flask_tag)` and commit. That deletes a row from `post_tags` only. The post and the tag both remain.

## When to use an association model

`db.Table` is right when the link carries no data of its own. If you need to record when the tag was added, who added it, or a role such as "editor", the link has become a real entity. Replace the table with a full model class that has two foreign keys plus the extra columns. You then work with those link objects directly.

## Common mistakes

- **Forgetting `secondary`.** Without it SQLAlchemy looks for a foreign key between the two tables and fails.
- **Creating duplicate tags.** Looking up an existing tag first (`Tag.query.filter_by(name=...).first()`) avoids a unique constraint error.
- **Using a model class as `secondary`.** A plain `db.Table` is required for the simple form.
- **Deleting rows of the association table by hand.** Modify the relationship list instead and let SQLAlchemy write the SQL.

## How it connects

The previous lesson, One-to-Many Relationships, put a foreign key on one side. This lesson needs a third table because both sides are "many". After this phase the same models will support features such as tag pages and post filters, and any schema change goes through a migration.
