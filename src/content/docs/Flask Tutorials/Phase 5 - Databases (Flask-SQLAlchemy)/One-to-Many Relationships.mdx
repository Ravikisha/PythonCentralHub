A **one-to-many** relationship means:

- one parent row relates to many child rows

Example:

- one `User` has many `Post`s

```mermaid title="one-to-many: the foreign key lives on the many side" desc="The column that does the work sits on the child table, pointing back at the parent. relationship() adds the convenient attributes on top -- a list on the parent and, with backref, a reference on the child -- but the database only knows about the foreign key."

## Models

```python
class User(db.Model):
    __tablename__ = "users"

    id = db.Column(db.Integer, primary_key=True)
    username = db.Column(db.String(80), unique=True, nullable=False)

    posts = db.relationship("Post", back_populates="author", lazy=True)


class Post(db.Model):
    __tablename__ = "posts"

    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200), nullable=False)

    user_id = db.Column(db.Integer, db.ForeignKey("users.id"), nullable=False)
    author = db.relationship("User", back_populates="posts")
```

## How to use it

```python
user = User.query.first()
for post in user.posts:
    print(post.title)
```

## lazy loading

- `lazy=True` means posts are loaded when accessed

Be careful in loops (can cause N+1 queries).

You can optimize with eager loading later.

## How the link works

In a one-to-many relationship, the database only stores one thing: a foreign key column on the child table. In the models above, `Post.user_id` holds the id of the user who wrote the post. That is all SQL needs to join the two tables.

`db.relationship` is a Python convenience layered on top. On the `User` side it gives you `user.posts`, a list of that user's posts. On the `Post` side it gives you `post.author`, a single `User`. With `back_populates`, the two attributes stay in sync: setting `post.author = user` also places the post in `user.posts`.

## A worked example

```python title="relationship_demo.py" showLineNumbers{1}
with app.app_context():
    db.create_all()

    ravi = User(username="ravi")
    p1 = Post(title="First post", author=ravi)
    p2 = Post(title="Second post", author=ravi)

    db.session.add(ravi)      # posts are saved too, through the relationship
    db.session.commit()

    print(p1.user_id == ravi.id)          # True
    print([p.title for p in ravi.posts])  # ['First post', 'Second post']
    print(p2.author.username)             # ravi
```

Notice that you never set `user_id` yourself. You assign the object (`author=ravi`) and SQLAlchemy fills in the foreign key when it flushes. Adding `ravi` to the session is enough, because SQLAlchemy follows the relationship and saves the posts as well.

## Lazy loading and the N+1 problem

By default `user.posts` is loaded on first access, with one extra query. That is fine for one user. In a loop over 100 users, printing each user's posts runs 1 query for the users plus 100 for the posts. This is the N+1 problem. When you know you need the posts, load them together with `selectinload` or `joinedload` from `sqlalchemy.orm`, for example `User.query.options(selectinload(User.posts)).all()`.

## Common mistakes

- **Putting the foreign key on the wrong side.** It belongs on the "many" table (`Post`), not on `User`.
- **Mismatched table names.** `ForeignKey("users.id")` uses the table name, not the class name. It must match `__tablename__`.
- **Inconsistent `back_populates`.** Each side must name the attribute on the other side exactly.
- **Assuming deleting a user deletes the posts.** Without a cascade setting, the posts either block the delete or are orphaned. Add `cascade="all, delete-orphan"` on the parent relationship if the children should go too.
