Gunicorn is a popular WSGI server for Python.

It runs your Flask app with:

- multiple worker processes
- better stability than the dev server

## Install

```bash
pip install gunicorn
```

## Create a WSGI entrypoint

`wsgi.py`:

```python
from myapp import create_app

app = create_app()
```

## Run gunicorn

```bash
gunicorn "wsgi:app" --bind 0.0.0.0:8000
```

## Workers

A common rule of thumb:

- `workers = 2 * CPU + 1`

Example:

```bash
gunicorn "wsgi:app" --workers 3 --bind 0.0.0.0:8000
```

## Timeouts

If requests can be slow, configure timeouts:

- `--timeout`

But also ask: should this work be moved to background jobs?

## Logging

Make sure logs go to stdout/stderr for containers:

- platforms can collect them automatically.

## Why not just use flask run

`flask run` starts Werkzeug's development server. It handles one kind of load, a developer clicking around, and it is not built for hardening or for many simultaneous visitors. Gunicorn is a production WSGI server. It starts a master process that manages several worker processes, each of which loads your app and handles requests. If a worker crashes or hangs, the master replaces it. Requests are spread across the workers, so several can be served at the same time.

This connects to the WSGI lesson in Phase 1: Gunicorn is the "WSGI server" and your `app` object is the "WSGI app". The command `gunicorn "wsgi:app"` means "import `wsgi.py` and use the variable named `app`".

## A worked example

Start with the factory-based entrypoint, then run it with a config file, which is easier to keep in git than a long command:

```python title="gunicorn.conf.py" showLineNumbers{1}
import multiprocessing

bind = "127.0.0.1:8000"
workers = multiprocessing.cpu_count() * 2 + 1
timeout = 30
accesslog = "-"      # "-" means stdout
errorlog = "-"       # stderr
```

```bash
gunicorn "wsgi:app" -c gunicorn.conf.py
```

Test it quickly with `curl http://127.0.0.1:8000/`. Gunicorn prints one line per request to stdout, and the master reports each worker it starts.

Two facts matter here. First, workers are separate processes. They do not share memory, so a global list or an in-memory cache changes in one worker and not the others. Requests for the same URL may see different data. Store shared state in a database or a cache such as Redis. Second, a worker that takes longer than `timeout` seconds is killed and restarted, and the client gets an error. Slow work like sending email or generating reports belongs in a background job, not in a request.

## Choosing worker numbers

The rule `2 * CPU + 1` is a starting point. On a one-CPU server that gives 3. Each worker uses memory for a full copy of your app, so a small machine may need fewer. Watch memory and response times, then adjust.

## Common mistakes

- **Binding to `0.0.0.0` behind Nginx.** Use `127.0.0.1` so only the proxy can reach it.
- **Storing state in module globals.** Workers each have their own copy.
- **Setting a huge timeout to hide slowness.** Fix the slow endpoint instead.
- **Running gunicorn on Windows.** It needs Unix. On Windows use Waitress, or WSL, or Docker.
