In many deployments:

- Nginx handles incoming HTTP/HTTPS traffic
- Gunicorn runs your Flask app

## Why use Nginx?

- HTTPS termination (TLS)
- better performance for static files
- request buffering
- security headers
- reverse proxy routing

## High-level flow

```mermaid
flowchart LR
  U[Users] -->|HTTPS| N[Nginx]
  N -->|HTTP| G[Gunicorn]
  G -->|WSGI| F[Flask App]
```

## Minimal Nginx config (conceptual)

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## Static files

Often you configure Nginx to serve `/static/` directly.

That reduces load on Gunicorn.

## Common gotcha

If you build absolute URLs, make sure Flask knows it’s behind HTTPS.

Forwarded headers (X-Forwarded-Proto) and proper proxy settings matter.

## What a reverse proxy does

A reverse proxy sits in front of your app and forwards requests to it. The visitor talks to Nginx. Nginx talks to Gunicorn on a private local port and passes the answer back. The visitor never connects to Gunicorn directly.

This split gives each program the job it is good at. Nginx is very good at handling many slow connections, terminating TLS, and serving files from disk. Gunicorn is good at running Python. Slow clients, such as someone on a bad mobile connection, would otherwise tie up a Gunicorn worker for the whole time they take to send or receive data. Nginx buffers the request, hands it to Gunicorn in one quick piece, and then feeds the response back to the slow client.

## Reading the config

In the config above, each `proxy_set_header` line matters. When Nginx forwards a request, Gunicorn sees a connection from `127.0.0.1`, not from the visitor. The headers carry the original details: `Host` is the domain the visitor used, `X-Forwarded-For` is their IP address, and `X-Forwarded-Proto` says whether they used `http` or `https`.

Flask ignores those headers unless you tell it to trust them. Add Werkzeug's `ProxyFix` in the app factory:

```python title="proxyfix.py" showLineNumbers{1}
from werkzeug.middleware.proxy_fix import ProxyFix

app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1)
```

Now `request.remote_addr` is the real client, `request.scheme` is `https` when the visitor used HTTPS, and `url_for(..., _external=True)` builds correct absolute links. Use `x_for=1` only when exactly one proxy is in front of the app. Trusting more hops than exist lets a visitor forge their IP address.

## Serving static files directly

Add a second location so Nginx serves `/static/` from disk without involving Python:

```nginx
location /static/ {
    alias /srv/myapp/myapp/static/;
    expires 7d;
}
```

Reload after any change with `sudo nginx -t && sudo systemctl reload nginx`. The `-t` flag checks the syntax first, so a typo does not take the site down.

## Common mistakes

- **Missing `proxy_set_header` lines.** Flask then thinks every visitor is `127.0.0.1` and every request is plain HTTP.
- **Redirect loops after enabling HTTPS.** Flask does not know the original request was HTTPS. Fix with `ProxyFix` and `X-Forwarded-Proto`.
- **A wrong `alias` path.** Static files return 404, and the error log shows the path Nginx tried.
- **Reloading without testing.** Always run `nginx -t` first.
- **Trusting forwarded headers when the app is reachable directly.** Only accept them from your own proxy.
