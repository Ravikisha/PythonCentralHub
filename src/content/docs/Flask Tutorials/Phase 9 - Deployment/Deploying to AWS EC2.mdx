An EC2 deployment is a classic “you manage the server” approach.

## High-level architecture

- EC2 instance (Linux)
- Gunicorn runs your app as a systemd service
- Nginx reverse proxies from port 80/443 to Gunicorn

```mermaid
flowchart LR
  Internet --> SG[Security Group]
  SG --> N[Nginx :80/:443]
  N --> G[Gunicorn :8000]
  G --> App[Flask]
```

## Key pieces to understand

- Security groups (open ports 80/443)
- SSH access
- systemd service files
- Nginx site config
- TLS certificates (Let’s Encrypt)

## Typical deployment approach

- configure environment variables (systemd service)
- start/restart service on code changes
- log to journald (systemctl logs)

## Operational caution

EC2 gives you full control but also full responsibility:

- patching OS
- firewall rules
- backups
- monitoring

It’s great for learning real-world deployment fundamentals.

## What you are actually building

On a platform like Heroku or Render you push code and the platform does the rest. On EC2 you rent a bare Linux machine and set up everything yourself. That is more work, but it shows you every layer of a real deployment. The layers are the ones from the last three lessons: Nginx receives traffic on ports 80 and 443, forwards it to Gunicorn on a local port, and Gunicorn runs your Flask app. Something must also start Gunicorn at boot and restart it if it crashes. On Linux that is `systemd`.

## A worked example

After launching an Ubuntu instance and opening ports 22, 80, and 443 in its security group, connect over SSH and set up the app:

```bash
sudo apt update && sudo apt install -y python3-venv nginx
git clone https://example.com/you/myapp.git /srv/myapp
cd /srv/myapp
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt gunicorn
```

Then describe the service in `/etc/systemd/system/myapp.service`:

```ini
[Unit]
Description=Gunicorn for myapp
After=network.target

[Service]
User=www-data
WorkingDirectory=/srv/myapp
Environment="SECRET_KEY=replace-me"
Environment="DATABASE_URL=sqlite:////srv/myapp/app.db"
ExecStart=/srv/myapp/.venv/bin/gunicorn "wsgi:app" --workers 3 --bind 127.0.0.1:8000
Restart=always

[Install]
WantedBy=multi-user.target
```

Start it and read its logs:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo journalctl -u myapp -f
```

Then add an Nginx `server` block that proxies to `127.0.0.1:8000`, as in the previous lesson, and get a free certificate with `sudo certbot --nginx -d example.com`.

Notice that Gunicorn binds to `127.0.0.1`, not `0.0.0.0`. Only Nginx on the same machine can reach it, and the outside world reaches Nginx alone. Secrets are set through `Environment=` lines in the service, never committed to the repository.

## Updating the app

For a new version: `git pull`, install new requirements, run `flask db upgrade` if there are migrations, then `sudo systemctl restart myapp`. Make it a script so it is repeatable.

## Common mistakes

- **Opening port 8000 in the security group.** It exposes Gunicorn without TLS. Open only 22, 80, and 443, and restrict 22 to your own IP if you can.
- **Running the service as root.** Use an unprivileged user.
- **Forgetting `Restart=always`.** A crash then leaves the site down until you notice.
- **Editing code on the server and not in git.** The next deploy overwrites your change.
- **Never taking backups or patching.** EC2 does not do this for you.
