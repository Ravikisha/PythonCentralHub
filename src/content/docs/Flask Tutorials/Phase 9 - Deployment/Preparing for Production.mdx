Production environments are not like your laptop.

A production-ready Flask app typically needs:

```mermaid title="what changes between the dev server and production" desc="flask run is a single-process development server with the reloader and debugger attached. In production the app is served by a WSGI server running several workers, usually behind a reverse proxy that terminates TLS and serves static files. The debugger must be off -- it executes arbitrary code by design."
flowchart TD
  subgraph Development
    A["flask run"] --> B["one process, reloader on"]
    B --> C["debug=True -- interactive debugger"]
  end
  subgraph Production
    D["nginx or the platform's proxy"] --> E["TLS, static files, timeouts"]
    E --> F["gunicorn / waitress, N workers"]
    F --> G["your app object"]
    G --> H["debug OFF, SECRET_KEY from the environment"]
  end
  C -.->|"never ship this"| I["the debugger console runs arbitrary code"]
```

## Must-do checklist

- Debug mode disabled
- Secrets stored in environment variables
- A production WSGI server (Gunicorn) instead of `flask run`
- Proper logging
- HTTPS termination (usually via Nginx or platform)
- Error handling (friendly pages or JSON)
- Database migrations
- Static file handling

## The biggest production mistake

Running:

- `flask run`

on a production server.

Use Gunicorn (or another WSGI server) instead.

## Configuration mindset

Your app should be configured by:

- environment variables

Not by editing code per environment.

## Health endpoints

Many deployments benefit from:

- `/health` endpoint returning 200

So monitoring systems can detect downtime.

## Observability

Have some plan for:

- request logs
- error logs
- basic metrics

Even a simple setup is better than none.

## Why each item is on the list

The checklist above is short, but every line answers a specific failure that has happened to real apps.

- **Debug off.** The interactive debugger lets anyone who reaches an error page run Python on your server.
- **Secrets in environment variables.** A `SECRET_KEY` or database password committed to git is visible to everyone with repository access, forever.
- **A real WSGI server.** The development server is not built for concurrency or hardening.
- **Logging.** When something breaks at 3 a.m. the log is all you have.
- **HTTPS.** Without it, passwords and session cookies cross the network in readable form.
- **Migrations.** The production database must change in step with the code.

## A worked example

This is a small production-ready base: config from the environment, a health endpoint, and logging to stdout.

```python title="prod_app.py" showLineNumbers{1}
import logging
import os
from flask import Flask


def create_app():
    app = Flask(__name__)
    app.config["SECRET_KEY"] = os.environ["SECRET_KEY"]        # fails fast if missing
    app.config["SQLALCHEMY_DATABASE_URI"] = os.environ.get("DATABASE_URL", "sqlite:///app.db")
    app.config["SESSION_COOKIE_SECURE"] = True
    app.config["SESSION_COOKIE_HTTPONLY"] = True
    app.config["SESSION_COOKIE_SAMESITE"] = "Lax"

    logging.basicConfig(level=logging.INFO)

    @app.get("/health")
    def health():
        return {"status": "ok"}, 200

    @app.errorhandler(500)
    def server_error(error):
        app.logger.exception("Unhandled error")
        return {"error": "server_error"}, 500

    return app
```

Read `os.environ["SECRET_KEY"]` with square brackets on purpose. If the variable is missing the app refuses to start, which is much better than silently running with a default key. Debug is not set anywhere, and it defaults to off. The cookie settings make session cookies HTTPS-only and unreadable to JavaScript.

The `/health` endpoint should be cheap. A load balancer or monitor calls it every few seconds. Have it return 200 if the process is up, and add a database check only if you need one.

Before launch, run through the list by hand: set the variables, run `flask db upgrade`, start Gunicorn, and request `/health` through the public URL.

## Common mistakes

- **A fallback secret such as `os.environ.get("SECRET_KEY", "dev")`.** Production then runs with a public key.
- **Leaving `app.run(debug=True)` in the entry file.** Guard it under `if __name__ == "__main__"` and never rely on it in production.
- **Logging secrets or full request bodies.** Logs are widely readable.
- **Assuming HTTPS is on because the site loads.** Check that HTTP redirects to HTTPS.
