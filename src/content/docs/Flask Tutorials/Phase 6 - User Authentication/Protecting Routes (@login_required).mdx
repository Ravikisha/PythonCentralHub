To protect a route so only logged-in users can access it:

```python
from flask_login import login_required


@app.route("/dashboard")
@login_required
def dashboard():
    return "Secret dashboard"
```

If a user is not logged in, Flask-Login will:

- redirect them to `login_view`

```mermaid title="what @login_required does on every request" desc="The decorator runs before your view function, so an unauthenticated request never reaches your code. Flask-Login stores where the user was trying to go, which is what makes the redirect after login land in the right place instead of on the home page."
flowchart TD
  A["request for a protected route"] --> B["@login_required runs first"]
  B --> C{"current_user.is_authenticated?"}
  C -->|yes| D["your view function runs"]
  C -->|no| E["save the target in the 'next' parameter"]
  E --> F["redirect to login_view"]
  F --> G["user logs in"]
  G --> H{"is 'next' a safe local URL?"}
  H -->|yes| I["redirect back to where they were going"]
  H -->|no| J["redirect to a known-safe default"]
```

## Configure login_view

```python
login_manager.login_view = "login"
```

Now anonymous users are redirected to `/login`.

## The "next" parameter

Flask-Login often preserves the originally requested URL via a `next` parameter.

Your login view can redirect back to it after successful login.

Be careful:

- validate `next` is a safe local URL (avoid open redirects)

## current_user

Inside protected routes, you can use:

```python
from flask_login import current_user

current_user.id
current_user.is_authenticated
```

This is how you tailor pages to the logged-in user.

## What the decorator does

`@login_required` is a gate placed in front of a view. Before your function runs, it checks `current_user.is_authenticated`. If the visitor is logged in, the view runs as normal. If not, your function never executes. Flask-Login redirects to `login_manager.login_view` (or returns 401 if you did not set one).

This matters because hiding a link is not security. If the "Dashboard" link only appears for logged-in users but the route itself is unprotected, anyone who types the URL gets in. The check has to be on the server, on the route.

## A worked example

```python title="protected.py" showLineNumbers{1}
from flask import request, redirect, url_for
from flask_login import login_required, current_user
from urllib.parse import urlparse


@app.route("/dashboard")
@login_required
def dashboard():
    return f"Welcome back, {current_user.username}"


@app.route("/login", methods=["GET", "POST"])
def login():
    if request.method == "POST":
        user = check_credentials(request.form)   # your own function
        if user:
            login_user(user)
            next_url = request.args.get("next", "")
            if next_url and urlparse(next_url).netloc == "":
                return redirect(next_url)          # local path only
            return redirect(url_for("dashboard"))
    return "Login form"
```

Follow the flow. An anonymous visitor asks for `/dashboard`. Flask-Login redirects them to `/login?next=/dashboard`. After they log in, the view sends them to the page they wanted in the first place.

The `next` value comes from the URL, so it can be tampered with. If you redirect to any address you are given, an attacker can craft a link like `/login?next=https://evil.example` and use your site to send people to a fake page. The check `netloc == ""` accepts only paths on your own site.

## Order of decorators

`@app.route` must be the outermost decorator, and `@login_required` must be directly above the function. If you reverse them, Flask registers the unprotected function and the check is silently skipped.

## Common mistakes

- **Wrong decorator order.** The route is registered without protection.
- **No `login_view` configured.** Guests receive a bare 401 error instead of a redirect.
- **Trusting `next` blindly.** Validate that it is a local path.
- **Protecting the page but not the API.** Data routes that return JSON need the decorator too.

## How it connects

The user loader and login view make `current_user` meaningful. This lesson uses it as a gate. The logout lesson ends the session, and the next phase uses blueprints so you can apply protection to a whole group of routes.
