Flask-Login stores a user id in the session.

On the next request, it needs to turn that id into a User object.

That’s what the **user loader** does.

```mermaid title="the user_loader runs once per request, not once per login" desc="The session only stores an id. On every single request Flask-Login takes that id and calls your user_loader to turn it back into a user object -- which is why the function must be cheap, and why returning None for a deleted user is what logs them out."
sequenceDiagram
  participant B as Browser
  participant F as Flask-Login
  participant L as your user_loader
  participant D as Database
  B->>F: request with session cookie
  F->>F: read user_id from the session
  F->>L: user_loader("7")
  L->>D: User.query.get(7)
  alt row exists
    D-->>L: User
    L-->>F: User object
    F-->>B: current_user is that user
  else row is gone
    D-->>L: None
    L-->>F: None
    F-->>B: current_user is anonymous -- effectively logged out
  end
```

## Example

```python
from flask_login import LoginManager

login_manager = LoginManager()


@login_manager.user_loader
def load_user(user_id: str):
    return User.query.get(int(user_id))
```

## Important notes

- `user_id` comes from the session, so it’s a string.
- Convert types carefully.
- Return `None` if the user doesn’t exist.

## Common pitfalls

- Forgetting to register the loader → Flask-Login can’t restore sessions
- Querying with the wrong type
- Returning something that isn’t a User model/UserMixin

## Where to put this code

In larger apps, user loader registration usually lives in:

- `auth` blueprint
- app factory initialization

So it’s registered exactly once.

## Why a loader is needed

The session cookie holds only a small string: the user id. Flask-Login has no idea how your users are stored. They might be in SQLAlchemy, in MongoDB, or in a file. So on every request it asks you, through the user loader: "Here is an id from the session. Give me the user."

Whatever you return becomes `current_user` for that request. If you return `None`, the visitor is treated as anonymous, which is exactly what you want when the user was deleted while their cookie was still valid.

## A worked example

```python title="loader.py" showLineNumbers{1}
from flask_login import LoginManager, UserMixin

login_manager = LoginManager()
login_manager.init_app(app)


class User(UserMixin, db.Model):
    id = db.Column(db.Integer, primary_key=True)
    username = db.Column(db.String(80), unique=True, nullable=False)


@login_manager.user_loader
def load_user(user_id):
    return db.session.get(User, int(user_id))
```

Here is the life of a request. The user logs in and `login_user(user)` writes `user.get_id()`, the string `"7"`, into the session. On the next request Flask-Login reads `"7"` and calls `load_user("7")`. The function converts it to an int, fetches the row, and returns a `User`. Your view can now use `current_user.username`.

`db.session.get(User, id)` returns `None` when there is no such row, which matches the loader contract. `User.query.get(...)` behaves the same but is marked legacy in SQLAlchemy 2.0.

## What runs, and how often

The loader runs on every request that touches `current_user`, so it should be fast. A lookup by primary key is fast. Do not put heavy queries or network calls in it.

## Common mistakes

- **Not registering the loader.** Flask-Login raises an error saying you need to provide a `user_loader` callback.
- **Forgetting the type conversion.** The session stores a string. Passing `"7"` to a query on an integer column works on some databases and fails on others.
- **Returning a dictionary or a raw row.** The loader must return an object with the properties Flask-Login expects, such as a `UserMixin` subclass.
- **Raising an exception for a missing user.** Return `None` and let the visitor be anonymous.
- **Registering it twice.** With an app factory, register it once inside `create_app`.

## How it connects

The previous lesson set up Flask-Login and introduced `current_user`. The loader is the piece that makes `current_user` real. Next comes the login view, which writes the id into the session, and route protection, which reads it.
