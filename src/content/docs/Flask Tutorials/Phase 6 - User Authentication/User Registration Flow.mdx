A typical registration flow:

1. User fills a registration form
2. Backend validates fields (username/email uniqueness)
3. Password is hashed
4. User row is created
5. Optionally log the user in

```mermaid title="the registration flow, and where it can refuse" desc="Every branch that sends the user back is a validation the server must do itself -- the browser cannot be trusted to have done it. Note the order: the password is hashed before anything is written, and the row is committed before the user is logged in."
flowchart TD
  A["GET /register"] --> B["render the form"]
  B --> C["POST /register"]
  C --> D{"all fields present?"}
  D -->|no| E["flash error, redirect back"]
  D -->|yes| F{"username already taken?"}
  F -->|yes| E
  F -->|no| G{"email already registered?"}
  G -->|yes| E
  G -->|no| H["generate_password_hash(password)"]
  H --> I["db.session.add(user)"]
  I --> J["db.session.commit()"]
  J --> K["login_user(user)"]
  K --> L["redirect to dashboard"]
  E --> B
```

## Model fields (example)

- `username` (unique)
- `email` (unique)
- `password_hash`

## Example (simplified)

```python
from flask import request, redirect, url_for, flash
from werkzeug.security import generate_password_hash
from flask_login import login_user

@app.route("/register", methods=["GET", "POST"])
def register():
    if request.method == "POST":
        username = request.form.get("username", "").strip()
        email = request.form.get("email", "").strip().lower()
        password = request.form.get("password", "")

        if not username or not email or not password:
            flash("All fields are required", "error")
            return redirect(url_for("register"))

        if User.query.filter_by(username=username).first():
            flash("Username already taken", "error")
            return redirect(url_for("register"))

        if User.query.filter_by(email=email).first():
            flash("Email already registered", "error")
            return redirect(url_for("register"))

        user = User(
            username=username,
            email=email,
            password_hash=generate_password_hash(password),
        )
        db.session.add(user)
        db.session.commit()

        login_user(user)
        flash("Welcome! Your account was created.", "success")
        return redirect(url_for("dashboard"))

    return "Register page"
```

## Why the order of steps matters

Registration looks simple: read a form, save a row. Each step has a reason, and skipping one creates a real problem.

1. **Validate first.** Empty fields, duplicate usernames, and malformed emails should be rejected before anything is written.
2. **Normalize.** Strip spaces and lowercase the email, so `Ravi@Example.com` and `ravi@example.com` are the same account.
3. **Hash the password.** Store only the hash. If the database leaks, plain passwords would expose every user, and probably their accounts on other sites too.
4. **Save, then commit.** Nothing is stored until `db.session.commit()`.
5. **Redirect.** Answer the POST with a redirect so that reloading the page does not submit the form again.

## Reading the example

The example above follows those steps. Each failed check flashes a message and redirects back to the form. On success it hashes with `generate_password_hash`, saves the user, logs them in with `login_user`, and redirects to the dashboard.

There is one gap worth knowing about. Checking `User.query.filter_by(...).first()` and then inserting leaves a tiny window. If two people submit the same username at the same instant, both checks pass and the second insert hits the `unique=True` constraint and raises `IntegrityError`. The database constraint is the real guarantee. Catch the error so users get a message instead of a 500:

```python title="register_safe.py" showLineNumbers{1}
from sqlalchemy.exc import IntegrityError

try:
    db.session.add(user)
    db.session.commit()
except IntegrityError:
    db.session.rollback()
    flash("That username or email is already in use", "error")
    return redirect(url_for("register"))
```

Keep the earlier checks anyway. They give friendlier messages in the normal case, and the constraint covers the rare race.

## Common mistakes

- **Storing `password` as text.** Always store `password_hash`.
- **Different cases for one email.** Lowercase before checking and saving.
- **Telling attackers too much.** A message such as "Email already registered" reveals which emails have accounts. For high-security apps, show a neutral message and send an email instead.
- **Skipping the database constraint.** Application checks alone can be raced.
- **Rendering the form on POST failure with a 200 and no message.** Users do not know what went wrong.
