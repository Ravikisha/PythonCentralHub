APIs commonly use token-based auth because they’re stateless.

## What is JWT?

JWT = JSON Web Token.

A JWT is a signed string that typically contains:

- user identity (subject)
- expiration time
- optional claims (roles, permissions)

## Common flow

```mermaid
sequenceDiagram
  participant C as Client
  participant A as API

  C->>A: POST /auth/login (username+password)
  A-->>C: 200 {access_token}

  A-->>C: 200 {profile}
```

## High-level usage (conceptual)

- create token on login
- require token on protected API routes

## Security notes

- Keep JWT secret keys safe (env vars)
- Use short expiration times
- For browser-based apps, be careful where you store tokens (XSS risk)
- Consider refresh tokens for longer sessions

JWT is powerful, but misuse can create security issues.

## Why tokens instead of sessions

Browser pages can rely on a session cookie, which the browser sends automatically. An API is often called by a mobile app or another server, where cookies are awkward. Token authentication solves this. The client logs in once with a username and password, receives a token, and sends that token in an `Authorization` header on every later request. The server does not need to look up a session, because the token itself proves who the caller is.

A JWT has three parts separated by dots: a header, a payload of claims such as the user id (`sub`) and expiry (`exp`), and a signature made with your secret key. Anyone can read the payload, because it is only encoded, not encrypted. What they cannot do is change it without invalidating the signature. So never put secrets in a JWT.

## A worked example with Flask-JWT-Extended

```python title="jwt_demo.py" showLineNumbers{1}
from datetime import timedelta
from flask import Flask, request
from flask_jwt_extended import (
    JWTManager, create_access_token, jwt_required, get_jwt_identity,
)

app = Flask(__name__)
app.config["JWT_SECRET_KEY"] = "change-me-and-load-from-env"
app.config["JWT_ACCESS_TOKEN_EXPIRES"] = timedelta(minutes=15)
jwt = JWTManager(app)

USERS = {"ravi": "pass1234"}   # demo only: real apps store password hashes


@app.post("/api/login")
def login():
    data = request.get_json(silent=True) or {}
    username = data.get("username", "")
    if USERS.get(username) != data.get("password"):
        return {"error": "bad_credentials"}, 401
    token = create_access_token(identity=username)
    return {"access_token": token}


@app.get("/api/me")
@jwt_required()
def me():
    return {"user": get_jwt_identity()}
```

The flow is: `POST /api/login` returns a token. The client then calls `GET /api/me` with the header `Authorization: Bearer <token>`. Without a valid token, `@jwt_required()` answers 401 and your function does not run. With one, `get_jwt_identity()` returns `"ravi"`.

The demo compares plain passwords to keep the example short. In a real app, look up the user and check the hash with `check_password_hash`, as covered in the password hashing lesson.

## Choosing expiry

A stolen token works until it expires, and the server cannot easily cancel it. That is why access tokens are short, often 5 to 15 minutes. A separate, longer-lived refresh token is used to get a new access token without logging in again.

## Common mistakes

- **Hardcoding the secret.** Load it from an environment variable, and use a long random value.
- **Long-lived access tokens.** A leak stays useful for too long.
- **Putting sensitive data in claims.** The payload is readable by anyone.
- **Sending tokens over plain HTTP.** Always use HTTPS.
- **Storing tokens in `localStorage` in a browser app.** Injected scripts can read them.
