The application factory pattern builds the app in a function:

- `create_app()`

This is the recommended pattern for larger Flask apps.

## Why use a factory?

- enables easy testing (create a test app)
- supports multiple environments (dev/test/prod)
- avoids import-time side effects
- helps extensions initialize consistently

## Example structure

```
myapp/
  __init__.py
  auth/
    routes.py
  models.py
config.py
wsgi.py
```

## create_app example

`myapp/__init__.py`:

```python
from flask import Flask
from .extensions import db, login_manager
from .auth.routes import auth_bp


def create_app(config_object="config.DevelopmentConfig"):
    app = Flask(__name__)
    app.config.from_object(config_object)

    db.init_app(app)
    login_manager.init_app(app)

    app.register_blueprint(auth_bp, url_prefix="/auth")

    return app
```

## wsgi entrypoint

`wsgi.py`:

```python
from myapp import create_app

app = create_app()
```

Now you can run:

- `gunicorn "wsgi:app"`

## Key takeaway

Factories make your app predictable and keep global state under control.

## The problem with a global app

In a small tutorial you write `app = Flask(__name__)` at the top of `app.py` and everything else imports `app`. That works until the project grows. Then other modules import `app`, and `app` imports them back, which produces circular import errors. Tests cannot get a fresh app with a clean in-memory database, because the app is created once at import time with whatever config it happened to load. Extensions are tied to that one instance.

A factory turns the app into something you build on demand. `create_app()` is an ordinary function that creates a `Flask` object, loads config, connects the extensions, registers blueprints, and returns the finished app. Nothing happens at import time, so you choose when and how to build it.

## Extensions are created first and attached later

The factory relies on a two-step habit. You create the extension object without an app, in its own module, then attach it inside the factory with `init_app`:

```python title="myapp/extensions.py" showLineNumbers{1}
from flask_sqlalchemy import SQLAlchemy
from flask_login import LoginManager

db = SQLAlchemy()
login_manager = LoginManager()
```

Any other module can now write `from .extensions import db` without needing an app. The link between `db` and a specific app is made in `create_app`, using `db.init_app(app)`, as shown above.

## Why tests get easier

```python title="tests/test_app.py" showLineNumbers{1}
from myapp import create_app
from myapp.extensions import db


def make_test_app():
    app = create_app("config.TestingConfig")   # in-memory database, CSRF off
    with app.app_context():
        db.create_all()
    return app


def test_home_page():
    app = make_test_app()
    client = app.test_client()
    assert client.get("/").status_code == 200
```

Each test builds its own app with its own database, so tests cannot leak data into each other. Production uses `create_app()` with the production config. Same code, different configuration.

## Common mistakes

- **Importing `app` from another module.** Inside routes use `current_app`. Inside blueprints use the blueprint object.
- **Calling `SQLAlchemy(app)` at import time.** Use `db = SQLAlchemy()` and `db.init_app(app)` later.
- **Registering blueprints outside the factory.** They must be registered on the app instance you are building.
- **Running database code outside an app context.** Extensions need `with app.app_context():` when used in scripts and tests.
- **Circular imports between `__init__.py` and blueprint modules.** Import blueprints inside `create_app` if the problem appears.
