Default error pages are fine for development, but real apps should have friendly error pages.

Flask lets you register error handlers.

```mermaid title="where an error handler sits in the request path" desc="An unhandled exception does not reach the browser as a stack trace unless debug is on. Flask catches it, turns it into a 500, and looks for a handler you registered. The same mechanism serves 404s from the router, which is why a custom 404 page is registered the same way as a custom 500."

  E -->|"any other exception"| H["500 Internal Server Error"]

  G --> J["@app.errorhandler(403)"]
  H --> K["@app.errorhandler(500)"]
  I --> L["return a template AND the status code"]
  J --> L
  K --> L
  H -.->|"debug=True"| M["the interactive debugger instead -- never in production"]

## Basic error handlers

```python
from flask import Flask

app = Flask(__name__)


@app.errorhandler(404)
def not_found(error):
    return "Page not found", 404


@app.errorhandler(500)
def server_error(error):
    return "Something went wrong", 500
```

## Using templates (recommended)

Once you start using templates (Phase 3), you can do:

```python
from flask import render_template

@app.errorhandler(404)
def not_found(error):
    return render_template("errors/404.html"), 404
```

Typical template structure:

```
templates/
  errors/
    404.html
    500.html
```

## Important: 500 handler and debugging

In debug mode, Flask shows an interactive debugger instead of your custom 500 handler.

That’s normal.

To see production-like behavior, disable debug.

## Bonus: handling exceptions consistently

As your app grows, you’ll likely:

- create custom exception types
- return JSON errors for APIs
- return HTML pages for browser routes

That’s a key reason to keep API routes and page routes organized (often via Blueprints).

## Why custom error pages matter

Every web app produces errors. A visitor mistypes a URL, follows a link to a page you deleted, or hits a bug you did not catch. Flask's built-in error pages are plain white pages with a single line of text. They tell the visitor nothing about what to do next, and they do not look like your site. A custom page keeps the navigation bar, explains what happened in plain language, and links back to somewhere useful.

The rule that trips most beginners is the status code. An error handler must return the page **and** the code, as in `return render_template("errors/404.html"), 404`. If you leave the code off, Flask sends `200 OK`. The browser then thinks the page exists, and search engines may index your "not found" page as real content.

## A worked example

This app has a real route, a handler for missing pages, and a handler for crashes. It uses plain strings so it runs without templates:

```python title="errors_demo.py" showLineNumbers{1}
from flask import Flask, abort

app = Flask(__name__)


@app.route("/item/<int:item_id>")
def item(item_id):
    if item_id > 100:
        abort(404)          # deliberately raise a 404
    return f"Item {item_id}"


@app.route("/crash")
def crash():
    return 1 / 0            # ZeroDivisionError -> 500


@app.errorhandler(404)
def not_found(error):
    return "We could not find that page.", 404


@app.errorhandler(500)
def server_error(error):
    return "Something broke on our side.", 500
```

Visiting `/item/5` returns the item. Visiting `/item/500`, or any URL that has no route, runs `not_found`. Visiting `/crash` runs `server_error`, provided debug mode is off.

## Common mistakes

- **Forgetting the status code.** The page looks right, but the response is a 200.
- **Testing the 500 page with debug on.** The interactive debugger takes over, so you never see your handler.
- **Doing risky work inside a 500 handler.** If the handler itself queries a database that is down, you get an error inside your error page. Keep it simple.
- **Leaking details.** Never print `error` or a traceback to the visitor. Log it instead.
