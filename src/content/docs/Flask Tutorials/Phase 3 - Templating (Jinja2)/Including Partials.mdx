Partials are reusable template fragments.

Examples:

- navbars
- footers
- alerts
- “card” components

```mermaid title="include and extends solve opposite problems" desc="extends is about a page fitting into a layout: the base is in charge and the child fills its holes. include is about dropping a fragment into the place you are already writing, and the fragment has no say in the surrounding page. ## Create a partial

`templates/partials/_navbar.html`:

```html
<nav>
  <a href="{{ url_for('home') }}">Home</a>
  <a href="{{ url_for('about') }}">About</a>
</nav>
```

## Include it in another template

```html
{% include "partials/_navbar.html" %}
```

## Where to use includes

- inside `base.html` to share nav/footer
- in pages to share repeated UI patterns

## Tip: naming convention

Many teams prefix partials with `_` (like `_navbar.html`) to signal “not a full page”.

Jinja doesn’t require it, but it helps humans.

## When to reach for an include

Templates get repetitive. The same navigation bar, the same flash message block, the same product card appear on many pages. Copying the HTML into each template works until you need to change it, and then you must find and edit every copy. An include lets you write the fragment once and paste it wherever it is needed. A change in the partial shows up on every page that uses it.

The difference from inheritance, shown in the diagram above, is direction. With `extends`, the child page fits into a base layout. With `include`, the page says "put this piece right here". A template can have only one parent, but it can include as many partials as you like.

## A worked example

Create a card partial that shows one post:

```html title="templates/partials/_post_card.html" showLineNumbers{1}
<article class="card">
  <h2>{{ post.title }}</h2>
  <p>{{ post.summary }}</p>
  <a href="{{ url_for('show_post', post_id=post.id) }}">Read more</a>
</article>
```

Use it in a page inside a loop:

```html title="templates/home.html" showLineNumbers{1}
{% extends "base.html" %}

{% block content %}
  {% include "partials/_navbar.html" %}

  {% for post in posts %}
    {% include "partials/_post_card.html" %}
  {% endfor %}
{% endblock %}
```

An included template sees the variables of the template that includes it. That is why `_post_card.html` can use `post`, the loop variable, without being passed anything. It also means a partial quietly depends on names that are defined elsewhere. Note in a comment at the top of the partial which variables it expects.

To keep a partial from seeing the caller's variables, write `{% include "partials/_card.html" without context %}`. That is rarely what you want. For reusable components that take arguments, Jinja macros are usually a cleaner tool.

## Where to place them

Keep partials in a `templates/partials/` folder and start file names with an underscore. Jinja does not need this, but it makes clear the file is a fragment and not a page you would ever render directly.

## Common mistakes

- **A wrong path.** The path is relative to the `templates` folder, so it is `partials/_navbar.html`, not `templates/partials/_navbar.html`.
- **Forgetting that the partial needs its variables.** A missing name renders as blank without an error.
- **Putting `extends` in a partial.** Partials are fragments and should hold plain HTML.
- **Including inside a block that the child overrides.** The include never runs if that block is replaced.

## How it connects

The previous lessons covered inheritance and blocks, which shape whole pages. Includes handle the smaller reusable pieces inside them.
