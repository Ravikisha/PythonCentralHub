## Why joins matter

Analytics questions often require multiple tables.

Example:

- Orders are in `orders`
- User attributes are in `users`

So we join.

## INNER JOIN

Keeps only matching rows.

```sql title="Orders with user country" showLineNumbers{1}
SELECT
  o.order_id,
  o.amount,
  u.country
FROM orders o
INNER JOIN users u
  ON u.user_id = o.user_id;
```

## LEFT JOIN

Keeps all rows from the left table (even if no match on the right).

Use case: users with or without orders.

```sql title="Users and their orders (if any)" showLineNumbers{1}
SELECT
  u.user_id,
  o.order_id,
  o.amount
FROM users u
LEFT JOIN orders o
  ON o.user_id = u.user_id;
```

## Common join pitfalls

### 1) Duplicated rows

If you join `users` to `events`, each user might have many events.

- Metrics can explode if you sum after the join.

Fix:

- Aggregate first, then join.

### 2) Filters in WHERE vs ON

With `LEFT JOIN`, putting conditions on the right table in `WHERE` can turn it into an inner join.

Prefer:

- conditions in the `ON` clause when you want to preserve rows.

## Visualize it

An INNER JOIN keeps only matching rows, while a LEFT JOIN keeps every row from the left table and fills in NULLs when there's no match.

```mermaid title="INNER JOIN vs LEFT JOIN" desc="How matching keys affect which rows survive the join"
flowchart LR
  A["Table A"] --> C["Table A + Table B"]
  B["Table B"] --> C
  C --> D["INNER JOIN: only rows where key matches in BOTH"]
  C --> E["LEFT JOIN: ALL rows from A, NULLs where B has no match"]
```

```p5 title="Row-by-row key matching" desc="Each row on the left looks for a matching user_id on the right; INNER JOIN drops the row that finds no partner." height="260"
function setup() {
  createCanvas(600, 260);
  textFont("monospace");
  noLoop();
}
function draw() {
  background(13, 17, 23);
  const left = [
    { id: 1, label: "order #1  (user 1)" },
    { id: 2, label: "order #2  (user 2)" },
    { id: 9, label: "order #3  (user 9)" },
  ];
  const right = [1, 2, 3];

  fill(200);
  textSize(11);
  textAlign(LEFT, CENTER);
  text("orders", 30, 20);
  text("users", 480, 20);

  let y = 60;
  for (const row of left) {
    const matched = right.includes(row.id);
    const c = matched ? [75, 139, 190] : [235, 90, 90];
    noStroke();
    fill(c[0], c[1], c[2]);
    circle(40, y, 14);
    fill(220);
    text(row.label, 55, y);

    if (matched) {
      stroke(75, 139, 190, 160);
      line(48, y, 500, y);
    } else {
      stroke(235, 90, 90, 160);
      drawingContext.setLineDash([4, 4]);
      line(48, y, 500, y + 20);
      drawingContext.setLineDash([]);
    }
    y += 55;
  }

  noStroke();
  fill(200);
  y = 60;
  for (const id of right) {
    fill(255, 211, 67);
    circle(500, y, 14);
    fill(220);
    textAlign(LEFT, CENTER);
    text("user " + id, 515, y);
    y += 55;
  }

  fill(235, 90, 90);
  textAlign(LEFT, TOP);
  textSize(10);
  text("no match -> dropped by INNER JOIN, kept as NULL by LEFT JOIN", 30, 230);
}
```

:::tip[Analyst's tip]
Every left row either matches one right row, matches several (a "fan-out" that duplicates the
left row once per match), or matches none. `INNER JOIN` only keeps the first two cases;
`LEFT JOIN` keeps all three, filling unmatched columns with `NULL`. If your row count grows
unexpectedly after a join, you likely have a fan-out — check for duplicate keys on the right
table before you aggregate.
:::
