## Why time zones are a special headache

A timestamp like `2024-03-09 09:30:00` is ambiguous on its own — 9:30 AM **where**?
Pandas timestamps start out **naive** (no time zone attached). Real analytics work
often needs them **aware** (tied to a specific zone) so you can convert safely between
regions, or compare data collected from different offices.

Two operations do all the work:

- `tz_localize` — attach a time zone to naive data ("this 9:30 was observed in X").
- `tz_convert` — reinterpret already-aware data in a different zone.

## Naive vs aware timestamps

```python title="Naive by default" showLineNumbers{1}
import pandas as pd

dates = pd.date_range("2024-03-09 09:30", periods=3, freq="D")
s = pd.Series([1, 2, 3], index=dates)

print(s.index.tz)  # None — no time zone attached yet
```

## Localizing: naive → aware

`tz_localize` doesn't shift the clock time — it just says "this time was recorded in
this zone":

```python title="tz_localize" showLineNumbers{1}
s_utc = s.tz_localize("UTC")
print(s_utc)
```

## Converting: aware → another zone

Once localized, `tz_convert` reinterprets the same instant in a different zone —
the clock time *does* change, but the underlying instant does not:

```python title="tz_convert" showLineNumbers{1}
print(s_utc.tz_convert("America/New_York"))
print(s_utc.tz_convert("Asia/Kolkata"))
```

Notice the New York offset flips from `-05:00` to `-04:00` between March 9 and
March 10 — that's a **daylight saving time (DST)** transition, handled automatically.

## Naive and aware don't mix

```python title="Mixing naive and aware raises an error" showLineNumbers{1}
try:
    s + s_utc
except TypeError as e:
    print("Error:", e)
```

If two aware series use *different* zones, pandas converts both to UTC before
combining them — you never have to do that conversion by hand.

## Common pitfalls

- `tz_localize` on a timestamp that falls exactly in a DST gap or overlap can raise
  an error (`NonExistentTimeError` / `AmbiguousTimeError`) — the clock time either
  doesn't exist or occurred twice that day.
- Calling `tz_localize` on already-aware data raises an error; use `tz_convert` instead.
- Store and process in UTC when possible; only convert to a local zone for display.

```p5 title="Same instant, two clocks" desc="Both clocks show the exact same moment in time — only the displayed hour differs because of the time zone offset." height="260"
function setup() {
  createCanvas(600, 260);
  textFont("monospace");
  noLoop();
}
function draw() {
  background(13, 17, 23);
  drawClock(160, 130, 9.5, "UTC", color(255, 211, 67));
  drawClock(430, 130, 15.0, "Asia/Kolkata (+5:30)", color(75, 139, 190));

  noStroke();
  fill(200);
  textAlign(CENTER, CENTER);
  textSize(12);
  text("same instant  →  two local readings", width / 2, 20);
}

function drawClock(cx, cy, hourFloat, label, ringColor) {
  noFill();
  stroke(90, 100, 116);
  strokeWeight(2);
  ellipse(cx, cy, 140, 140);

  // hour ticks
  for (let i = 0; i < 12; i++) {
    const a = TWO_PI * (i / 12) - HALF_PI;
    const x1 = cx + cos(a) * 62;
    const y1 = cy + sin(a) * 62;
    const x2 = cx + cos(a) * 68;
    const y2 = cy + sin(a) * 68;
    stroke(90, 100, 116);
    line(x1, y1, x2, y2);
  }

  // hour hand
  const angle = TWO_PI * ((hourFloat % 12) / 12) - HALF_PI;
  stroke(ringColor);
  strokeWeight(4);
  line(cx, cy, cx + cos(angle) * 45, cy + sin(angle) * 45);

  noStroke();
  fill(ringColor);
  ellipse(cx, cy, 8, 8);

  fill(230);
  textAlign(CENTER, CENTER);
  textSize(12);
  text(label, cx, cy + 95);
}
```

:::tip[From the book]
McKinney notes that time zone-aware `Timestamp` objects store their value internally
as UTC nanoseconds since the Unix epoch. Converting between zones with `tz_convert`
only changes how the value is *displayed* — `stamp_utc.value` is identical before and
after a `tz_convert` call, so no information is ever lost or recomputed.
:::
